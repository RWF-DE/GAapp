### 1-1. 「入力と出力」の前書き

変更前：

> 振り分けは DB に触れない純粋関数 `allocate(input): AllocateResult` として `packages/allocator` に置き、管理者のブラウザの Web Worker で実行する。画面は DB から入力を組み立てて呼び、結果を RPC `save_auto_allocations` で保存する。R8 のデータを JSON にして単体テストできる。

変更後：

### 1-4. 「定式化」の前処理

変更前（DB 設計の差分 3-2 を当てた後。3 は 3-2 の文）：

> 1. 長机(3人掛)を申請できない区分（企業以外）の申請は、長机(2人掛)に1対1で読み替える（S03。品目マスタの申請できる区分で判定）
> 2. fixed_request（S06）の団体・品目は、申請がなければその数を需要 D にする。申請があれば申請を使い、差を W106 で知らせる
> 3. keep（S08）の行をルールから作る（is_keep。保存は origin = auto・pinned = false。D-06）。固定行と同じように、需要と在庫から先に差し引き、結果の rows にも含める。管理者が固定した keep の行（fixedRows に入る）があれば、その団体・部屋・品目について、固定分を超える分だけを作る
> 4. 固定行（fixedRows）を差し引く。需要 D'(g,i) = max(0, D(g,i) − 固定分)、在庫 S'(r,j) = S(r,j) − 固定分。固定分が申請を超えたら W101、在庫を超えたら E001 で止める

変更後：

> 0. 入力を zod スキーマで検証し、id とルールの参照先（団体・場所・品目のコード）があること、fixed_request と keep の品目が対象の団体の区分で申請できる品目であること、ルールが重なっていないこと（同じ団体・品目の fixed_request、同じ代替で区分が重なる substitute）を確かめる。だめなら invalid_input（ルールの画面も保存の前に同じ確認をする）
> 1. 申請を団体・品目ごとに合計する。団体の区分で申請できない品目のうち、長机(3人掛)は長机(2人掛)に1対1で読み替える（S03・D-05。品目マスタの申請できる区分で判定。DB に長机(3人掛)のまま残っていてよい）。それ以外の申請できない品目の申請は、需要から除いて計算を続ける（止めない）。検証の E006 がその申請を示し、直すまで確定できない
> 2. fixed_request（S06）は、対象の団体が未提出（submitted_at が null）のときだけ、その数を需要にする（申請の数は使わない）。提出済みなら 0 を含めて申請の数を使い、違えば W106 で知らせる（D-07）。1・2 の結果を需要 D とする。E003・W101 と、画面の「団体別」の申請数は、この D と比べる
> 3. keep（S08）の行をルールから作る（is_keep。保存は origin = auto・pinned = false で、自動実行のたびにルールから作り直す。D-06）。固定行と同じように、需要と在庫から先に差し引き（4）、結果の rows にも含める。管理者が固定した keep の行など、同じ団体・部屋・品目の固定行（fixedRows に入る）があれば、固定分を超える分だけを作る。申請より多くても作る（多い分は W101）。部屋が団体の使用場所でなければ E005、使用不可なら E002 で止め、ルールを示す

> 6. 最小変更モードでは、前回の自動行（申請品目は 1 と同じ読み替えの後）を（運び元・団体・申請品目・品目）ごとに合計し、3 の残すの行の数を引いたものを x̂ の上限にする

### 1-6. 「定式化」の目的関数

変更前：

```latex
\min \sum \big( W\, c_{\mathrm{sub}}(g,i,j) + d(r,g) + \delta(g,j) \big)\, x(r,g,i,j) \; + \sum \big( W\, c_{\mathrm{sub}} + d(r,g) + \delta - \mu \big)\, \hat{x}(r,g,i,j)
```

> - c_sub：代替の重さ。j = i なら 0。S01・S02（不可机・不可椅子）は 0（普通の机・椅子と同じ扱い）。S04（企業の長机3→2）は 1。S07（キャスター机）は 3
> - W：代替の少なさを距離より必ず優先させる重み。W = 10 × d_max × N（d_max＝距離コストの最大値、N＝需要の合計）。R8 なら 10 × 5 × 1,295 ≒ 65,000
> - d(r,g)：距離コスト（次の節）
> - δ：不可椅子を同じ距離なら休憩所に先に回すための微小な差。休憩所への不可椅子は −0.1、それ以外は 0。距離の差（1 以上）より小さいので、距離が最優先になる
> - μ：最小変更モードで前回と同じ割り当てを優先する割引。μ = d_max + 1。代替の重さ W よりは小さいので、代替を減らせるときはそちらを優先する

変更後：

```latex
\min \sum \big( W\, c_{\mathrm{sub}}(g,i,j) + A\, d(r,g) + e(r,g) - B\, p(g,i,j) \big)\, x(r,g,i,j) \; + \sum \big( W\, c_{\mathrm{sub}} + A\, d + e - B\, p - \mu \big)\, \hat{x}(r,g,i,j)
```

> 求めるのは、次の順の辞書式の最小である：①代替の重さの合計 → ②（最小変更モードのとき）前回と同じ台数の最大 → ③距離の合計 → ④休憩所への不可椅子の台数の最大 → ⑤運び出す台数（同じ距離なら残す方）。係数はすべて整数にし、上の段の差が1でもあれば下の段の合計では覆せない値にする（P-02 を、休憩所の数や解の形に依らず成り立つ形にしたもの）。
>
> - c_sub：代替の重さ（ルールの cost。0〜10 の整数）。j = i なら 0。S01・S02（不可机・不可椅子）は 0（普通の机・椅子と同じ扱い）。S04（企業の長机3→2）は 1。S07（キャスター机）は 3
> - d(r,g)：距離コスト（次の節。整数）
> - e(r,g)：運び元が団体の使用場所でなければ 1、使用場所なら 0。距離が同じ解の中で、自室の備品を外へ出して運び込む形を避け、残す方を選ぶ
> - p(g,i,j)：preferCategory つきの代替で、団体の区分が preferCategory なら 1（S02 の休憩所への不可椅子）。それ以外は 0
> - K＝LP の需要の制約の数、P＝そのうち p = 1 の変数を含む制約の数、d_max＝作った変数の d の最大（1 未満なら 1）として
>   - B = K + 1、A = B·P + K + 1、U = A·d_max + B + 1
>   - μ = K·U + 1（最小変更モード。全体の実行では x̂ を作らないので 0）
>   - W = K·(U + μ) + 1
> - 上の値で足りる理由：2つの解の差は、二部グラフの単純な閉路と、在庫の点どうしを結ぶ単純な道に分けられる。どれも需要の点を高々 K 個通り、1点あたりの差は e・p・前回の台数が ±1、d が ±d_max に収まるので、閉路1つでの下の段の差の合計は、上の段の1単位より必ず小さい
> - μ は、前回の1台を守ることを、どれだけ距離を縮めることよりも優先する値にした。1台ぶんの値（d_max + 1）では、前回の1台を手放してほかの何台かの距離を縮める解が選ばれうる（T06 の設計で、小さな入力の総当たりで確認）。これにより次が成り立つ（D-08）：部屋 M を使用不可にしたとき、M から受け取っていた団体・申請品目の失った分を、前回のほかの行を変えずに、その団体がルール上使える場所の余りから、代替の重さの合計を増やさずに補えるなら、前回の M 以外の行は減らず、増えるのは M から受け取っていた団体・申請品目の行だけ（失った分を、その団体がすでに受け取っている場所から補うと、その行の数が増える）で、M と無関係な行は変わらない
> - 品目全体に余りがあっても、上の条件を満たすとは限らない。運び元の制限（S05）・代替の区分・了承の拒否で、M から受け取っていた団体の使える場所が限られると、代替を増やさないために無関係な団体の行を押し出す解が選ばれる（代替の重さが前回の維持より先なので、これも正しい最適解である）。例：設営が S05 で {M, R2} からしか受け取れず、R2 の机を団体 A も使っていたとき、M を使用不可にすると、設営は R2 の机を受け取り、A は別の部屋から受け取る形に変わる
> - R8 規模（T00 のダミー：K = 170、P = 2、d_max = 7）では、全体の実行で W = 639,711、最小変更モードで μ = 639,711・W = 109,390,581。係数の最大は約 3.3×10⁸ で、HiGHS は整数の解を返し、時間も変わらない（1回 40 ms 前後）。係数の最大 × 需要の合計が 2⁵³ を超えるときはエラーにする。係数が大きくても辞書式の最小が返ることは、段ごとに LP を解く検算と比べるテストで確かめる

## 7. notes/decisions.md（要件定義ではないが、同じ PR で直す）

- D-05〜D-08 の「状態」を、ロジックの部分を反映した PR の番号つきで「要件定義に反映済み」にする（DB の部分は DB 設計の PR）。D-08 の「決定」の文に、「余りが足りる」の意味（使用不可にした部屋から受け取っていた分を、前回のほかの行を変えずに、ルール上使える場所の余りから代替を増やさずに補えること。品目全体の余りではない）と、そのとき成り立つこと（前回の第一セミナー以外の行は減らず、増えるのはその部屋から受け取っていた団体・申請品目の行だけ。無関係な行は変わらない）を書き足す。

- 次を設計で決めた決定として足す（どれも業務のルールを変えず、確定を止める error の範囲も変えない）：
  - 前処理で止める（precheck）のは、固定行と残すの行で在庫を超える E001 と、残すのルールの部屋が使用不可（E002）・使用場所でない（E005）だけ。申請できない品目の申請（E006）は需要から除いて計算し、固定行の E002・E004・E005 では止めず、どれも validate が error として示す（直すまで確定できない）。理由：E006 で止めると、品目や団体の区分を後から変えたときに自動振り分けが一切動かなくなる。allocate は自分が作る行に error を出さないことだけを守る。
  - 解けないときの診断は、品目全体の不足や前処理7の団体ごとの不足があっても、ルールを1つずつ外して解き直す（S05 が原因の入力は前処理7で止まるため。fixed_request・keep は品目全体の不足を消しうるため。K-26）。
  - 同じ部屋を使う2団体（食堂の企業と休憩所など）が、その部屋の在庫を取り合うときは、どちらに残すかを決めない（コストが同じ。同じ入力なら同じ結果）。運搬の作業は変わらず、振り分け表の「使用用途」の名前が変わるだけなので。
