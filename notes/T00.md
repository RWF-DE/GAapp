# T00 スパイク：highs-js で R8 規模の輸送問題を解く

作業の記録と、T06 の判断材料。コードは `spikes/highs/`（本体からは参照しない。再現手順は [spikes/highs/README.md](../spikes/highs/README.md)）。計測の生の出力は `spikes/highs/results/`（`*.txt` がそのままの出力、`*.json` が数値）。

## 結論

- **R8 規模は一瞬で解ける。** 変数 5,630・制約 344 の LP を、Node でも Chromium でも 1 回あたり約 40〜45 ms（5 回の中央値）で解く。最初の 1 回だけ JIT のため約 110〜170 ms。wasm の読み込みは Chromium で約 150 ms（localhost。1.2 MB を gzip で配信）。「ブラウザで 2 秒以内」には、wasm の読み込みを含めても、Fast 4G 相当で約 1.3 秒＋計算 0.3 秒で収まる。Slow 4G 相当では読み込みだけで約 6 秒かかる（初回のみ。後述）。
- **解は整数で返る。** すべての変数で |x − round(x)| = 0（許容は 1e-6）。単体法のままで、0/1 変数は使っていない。
- **解は決定的。** 同じ入力で 5 回とも、全変数が同じ値（ハッシュ一致）。Node と Chromium でも、highs 1.15.3 と 1.15.4 でも同じ。入力の配列を並べ替えてから sort_order → 名前 → id で並べ直すと、LP の文字列が一致し、解も同じ。
- **P-02（コストの整数化）：** 解の質（距離の合計・代替の数）と時間は変わらない。K-12 の最小例では W107 が 6/12 → 0/12 になる（同点の解の選び方が並び順に依らなくなる）。一方、ダミーデータ 30 通りでは W107 の件数は変わらない（17 件 → 17 件。16 件は S05 の制限を受ける設営で、整数化では減らせない）。採用してよいが、「W107 が 0 件」の不変条件は S05 を考慮して直す必要がある（後述）。
- **wasm の読み込み：** `public/highs.wasm` に置き、`locateFile` で basePath 付きの URL を返す方法が、Vite（base=/GAapp/）と Next.js 16 の静的書き出し（basePath=/GAapp）の両方で動いた。basePath を付け忘れると 404 になり、`CompileError: expected magic word` で落ちる。`locateFile` を渡さなくても、Vite・Next.js（Turbopack）はバンドラが wasm を別アセットとして出すので動く。Next.js を `--webpack` でビルドすると highs.mjs の `import 'node:module'` で失敗する。

- **訂正：highs 1.15.4 は `loadHighs({ wasmModule })`・`wasmBinary` を無視する。** `types.d.ts` の `InitOptions` には `wasmBinary`・`wasmModule` が書いてあるが、`build/highs.js`・`highs.mjs` には `wasmModule` という文字列がなく、`wasmBinary` は内部変数が宣言されるだけで `Module` から読まれない（`wasmModule`・`Module["wasmBinary"]` は `grep` で 0 件）。Node で `loadHighs({ wasmModule, locateFile: () => '/nonexistent/highs.wasm' })` を呼ぶと（`wasmBinary` でも同じ） `locateFile` が呼ばれて ENOENT で落ちる（`results/node.txt` の「wasmModule の確認」）。以前の版は「`wasmModule` を共有」の列を測ったつもりだったが、実際は毎回取得して compile していた（ブラウザで wasm を 2 回取得していたのもこのため）。compile を 1 回にするには、Emscripten の `instantiateWasm` フック（`Module.instantiateWasm(imports, receive)`）で共有の `WebAssembly.Module` から instantiate する（表の 3 列目と `browser/worker.ts` の `mkShared`）。この方式だと load は Node で 13.8 → 3.7 ms、Chromium で約 1.6 ms。ただし使い回しなら不要。
- 落ちる・結果が変わる、ということはなかった。highs 1.15.4 の `highs.solve(lp, options)` は、**呼ぶたびに新しい内部の solver を作って壊す**（型定義の説明より）ので、同じインスタンスで続けて解いても前の解が残らない。診断で十数回解き直しても、1 回 40 ms 前後なので 1 秒以内。
- **使い回しを勧める。** 作り直すと load が Node で 4〜14 ms 加わるだけで利点がない。
- **落とし穴：`loadHighs(options)` に渡したオブジェクトは highs.js が書き換える。** 同じオブジェクトで 2 回目を呼ぶと `TypeError: Cannot redefine property: memoryBytes` で落ちる（Node でも再現。`print` だけの `{}` でも）。呼ぶたびに新しいオブジェクトを渡すこと。

| 入力 | `Status` |
| --- | --- |
| S05 の 6 部屋の机を 235 台にする（需要 241） | `"Infeasible"`（約 28 ms） |
| 教卓の在庫を 5 台にする（需要 10） | `"Infeasible"`（約 39 ms） |
| `time_limit` を 0.0001 秒にする | `"Time limit reached"` |
| 矛盾する小さな LP（`x1 >= 1`、`x1 <= 0`） | `"Infeasible"` |
| **教卓の在庫が 1 台もない（需要の行に変数が 1 つもない）** | **`"Optimal"`**。変数のない需要の行を LP に書けないので、その団体の教卓は 0 台のまま「最適」になる |

最後の行が重要：**LP を作る前に、候補の変数が 1 つもない（団体×申請品目）を見つけて、shortages に回すこと。** そうしないと「解けた」と誤る（独立した検証では E003 で見つかった）。status の型は `'Optimal' | 'Infeasible' | 'Primal infeasible or unbounded' | 'Unbounded' | 'Time limit reached' | 'Iteration limit reached' | …`（types.d.ts の HighsModelStatus）。**`Status === 'Optimal'` 以外は、すべてエラー（途中の解は使わない）**にする。`Primal infeasible or unbounded` も解けないとして扱う。

## P-02：コストの整数化（K-12）

整数化：d′ = 100·d ＋（運び元が使用場所でなければ 1）、休憩所への不可椅子は −10、W′ ＝ 10×d′_max×N、μ′ ＝ d′_max＋1（`src/lp.ts` の `costMode: 'integer'`）。元は δ = −0.1 を 0.1 刻みの整数（×10）で組み立てて、LP には `4.9` のように書く。

**(1) R8 規模のダミー 30 通り（シード 100〜129、`results/p02.txt`）**

| | 元 | 整数化 |
| --- | --- | --- |
| W107 の件数の合計 | 17 | 17 |
| W107 が 0 件のシード | 13 / 30 | 13 / 30 |
| 1 シードあたりの W107 の最大 | 1 | 1 |
| 実際の距離の合計の平均 | 2,114.2 | 2,114.2（30 通りとも元と一致） |
| キャスター机への置き換えの平均 | 97.0 | 97.0 |
| 解く時間の中央値（3 回の中央値の中央値） | 38.9 ms（最大 55） | 41.3 ms（最大 51） |
| 非整数・5 回の不一致・検証エラー | 0 | 0 |

- 17 件の内訳：**16 件は設営**（体育館に机の在庫がある配置で、S05 により設営は 1-1〜2-3 からしか受け取れない一方、体育館の机が他の団体へ出ていく）。K-12 の (3) の指摘のとおり。残り 1 件は、入れ替えると良くなるのに起きているもの（ルール上の制約と思われる）。**同点で入れ替えられる型（tie）は 0 件。**
- つまり、実データに近い配置では、W107 の主因は同点ではなく S05。整数化の「+1」は、この主因には効かない。

**(2) K-12 の最小例（同点が実際に起きる配置。`results/p02.txt` の末尾）**

団体 g（1 号棟 1 階の A を使用）と h（屋外）。A（1 階）と B（2 階）に机 5 台ずつ。g・h は机 5 台を申請。「A→g、B→h」（W107 なし）と「B→g、A→h」（W107 あり）はどちらも距離の合計 25 で同点。部屋 3 つ×団体 2 つの並び順を全部（12 通り）変えて解くと、

| | W107 が出た並び順 |
| --- | --- |
| 元の定式化 | **6 / 12** |
| 整数化 | **0 / 12** |

元の定式化では、単体法がどちらの頂点を選ぶかが並び順で変わる。整数化なら必ず「残す」側になる。**同点の解を並び順に依らず安定させる効果は実証できた。**

**(3) 同じ使用場所を共有する団体は整数化でも同点が残る。** 例：食堂を使う企業 2 と休憩所 2。食堂の在庫を取り合うとき、どちらも「自室（0）」なので、+1 では差が付かない。どちらが自室の在庫を取るかは決まらない。W107 の定義（後述）では「同じ部屋を使う別の団体へ渡す」のは「外へ出ている」に数えない。

**判断材料：** 採用して損はない（時間・距離・代替の数は同じ。目的関数値が 2.7×10⁹ になっても全変数が整数、30 通りで元と同じ距離の合計になった）。ただし効果は「同点のときに並び順に依らず『残す』が選ばれる」ことに限られ、W107 を 0 にするものではない。

## 最小変更モード（x̂・μ）

「MER」を使用不可にして解き直す（`bench-node.ts` の最後）。1 回目の解（5 回の最初の解）を前回の行として渡す。MER から運んでいた行は x̂ を作らない（K-14：使用不可の部屋には作らない）。変わった行は、（運び元・団体・申請品目・品目）ごとの数（x と x̂ の合計）が変わったもの。

| | 元の定式化 | 整数化 |
| --- | --- | --- |
| 前回 MER から運んでいた行・台数 | 13 行・73 台 | 13 行・71 台 |
| 変数（うち x̂） | 5,679（237） | 5,680（238） |
| 解く時間（x̂ なしの全解き直し） | 39.9 ms（37.5 ms） | 40.8 ms（38.6 ms） |
| **変わった行（最小変更）** | **50 件**・186 台（全 278 キー中） | **48 件**・178 台（全 280 キー中） |
| x̂ なしで解き直した場合の変わった行 | 246 件・828 台 | 242 件・818 台 |
| 上のうち、MER が原因でないもの（運び元が MER でなく、前回 MER を使っていた団体・品目でもない） | 14 件 | 11 件 |
| 独立した検証・整数性 | 問題なし・ずれ 0 | 問題なし・ずれ 0 |

- x̂ と μ により、変わる行は約 1/5（246 → 50）に減る。MER の 73 台は別の場所から補う必要があり、その連鎖で 50 件前後は変わる。机がぴったり足りている配置なので、MER の机 20 台がなくなる分は、キャスター机への置き換えが 20 台増えて吸収される（その連鎖で「MER が原因でない」行も 11〜14 件動く）。
- D-08 の基準（「ほかの場所の余りが足りるなら、その部屋と無関係な行は変わらない」）は、**机のように余りがない品目では成り立たない**（置き換えの連鎖で動く）。余りのある品目（椅子・椅子(青)・教卓）に限れば無関係な行は動かないか、テストで確かめる必要がある。T06 の受け入れ基準は「変わった行の数を記録し、上限（例：全体の 1/4）を決める」形にするのが現実的。
- ダミーの在庫を変えて、MER の長机(2人掛)の在庫を 10 台にした版では、MER を使用不可にすると長机の合計が足りず `Infeasible` になった（途中の版で確認）。「使用不可にしたら解けなくなる」ケースは実際に起きるので、最小変更モードでも「解けないときの扱い」を通ること。

## 静的書き出しのアプリで wasm を読み込む方法

### 結論

```ts
// Worker の中（Next.js なら app/.../solver.worker.ts）
import loadHighs from 'highs';

const basePath = process.env.NEXT_PUBLIC_BASE_PATH ?? '';   // next.config の basePath と同じ値
const highs = await loadHighs({
  // 注意：呼ぶたびに新しいオブジェクトを渡す（使い回すと 2 回目が TypeError）
  locateFile: (file) =>
    file.endsWith('.wasm') ? new URL(`${basePath}/${file}?v=1.15.4`, self.location.origin).href : file,
});
```

- **置き場所：`public/highs.wasm`**（`node_modules/highs/build/highs.wasm` を build 前にコピーする。git には入れない。`spikes/highs/next-export/package.json` の build スクリプトを参照）。Next.js の `output: 'export'` では `out/highs.wasm` になり、`https://<組織>.github.io/<リポジトリ>/highs.wasm` で配信される。
- **basePath は自分で付ける。** Next.js の basePath は `<Link>` や `next/image` には付くが、`public/` のファイルを自分で `fetch` する URL には付かない。`locateFile` に `/highs.wasm` と書くと、GitHub Pages では `https://<組織>.github.io/highs.wasm` になって 404。
- **Worker：** `new Worker(new URL('./solver.worker.ts', import.meta.url))`（Next.js の Turbopack・Vite とも動いた）。振り分け画面のコンポーネントでだけこれを書けば、Worker のチャンクと wasm はその画面を開くまで取得されない。
- wasm はファイル名にハッシュが付かないので、highs を上げたときの古いキャッシュ対策として `?v=<highs のバージョン>` を付けた（クエリを付けても読み込める）。

### 実際に動かした結果（`results/browser.txt`、`results/next.txt`）

| 設定 | Vite（base=/GAapp/） | Next.js 16 静的書き出し（basePath=/GAapp、Turbopack） |
| --- | --- | --- |
| `locateFile` で `${base}highs.wasm` を返す（public に置く） | 成功。`/GAapp/highs.wasm` を 200 で取得。初回の読み込み 154 ms | 成功。`/GAapp/highs.wasm?v=1.15.4` を 200 で取得。読み込み 156 ms |
| `locateFile` を渡さない（既定） | 成功。バンドラが wasm を `assets/highs-<hash>.wasm` として出し、その URL を書き込んでくれる | 成功。`_next/static/media/highs.<hash>.wasm` として出る（basePath 付きで解決された） |
| `locateFile` で `/highs.wasm`（basePath を忘れた例） | 失敗：`/highs.wasm` が 404 → `Aborted(CompileError: WebAssembly.instantiate(): expected magic word 00 61 73 6d, found 6e 6f 74 20)`（404 の本文 "not found" を wasm として読もうとして落ちる） | 同じ失敗 |

- **どちらの方法でも動く。CLAUDE.md の約束（public に置いて `locateFile`）に従えば、置き場所と URL を自分で決められる。** 既定（バンドラ任せ）はハッシュ付きなのでキャッシュの問題は出ないが、バンドラの挙動に依存する。どちらを使っても、ビルド成果物（`out/`）にはバンドラが出した wasm（3.5 MB）が常に入る（`public/` に置く方式だと同じものが 2 つ入る。ブラウザが取るのは使った 1 つだけ）。
- **Next.js を `--webpack` でビルドすると失敗する**：`UnhandledSchemeError: Reading from "node:module" is not handled`（`highs.mjs` が Node 用の分岐で `node:module` を import するため）。`resolve.alias` で false にしても直らなかった。Next.js 16 の既定（Turbopack）、Vite は問題なし。T01 で `next build --webpack` を使わないこと。
- Vite でも `Module "node:module" has been externalized for browser compatibility` の警告が出るが、動作に影響はない。
- 型：`import loadHighs from 'highs'` は同梱の `types.d.ts` で型が付く。

## T06 への注意点

1. **highs は `1.15.4` を exact で固定**（`^`・`~` なし）。上げるときは、R8 の回帰テストで解が変わらないことを確かめる。確かめ方は「全変数の値のハッシュ」か「rows の完全一致」（目的関数値だけでは足りない）。このスパイクの `hashValues`（値を `join(',')` した文字列の cyrb53）は Node・Chromium・1.15.3・1.15.4 で一致した。
2. **Worker の中で、1 回だけ `loadHighs` して使い回す。** **highs 1.15.4 では `wasmModule`・`wasmBinary` は効かない**（型にはあるが実装にない。渡しても無視され、`locateFile` か既定の URL から取り直す）。wasm を共有したいときは `Module.instantiateWasm` を使う（K-23 の表を参照）。 診断（解き直しを数回〜十数回）も同じインスタンスで続けて呼べる（1 回 40 ms 前後、メモリは増えない）。`loadHighs` に渡すオプションのオブジェクトは使い回さない。
3. **wasm は振り分け画面でだけ読む。** 初回 1.2 MB（gzip）。読み込み中の表示を出す。要件の「2 秒以内」は計算（0.1〜0.3 秒）にかかるものとし、読み込みは別枠にする（Slow 4G 相当で約 6 秒）。
4. **`Status === 'Optimal'` 以外は結果を使わない。** `time_limit` は 30 秒のままでよい（実測は 1 回 0.05 秒。`"Time limit reached"` という文字列で返る）。
5. **候補の変数が 1 つもない需要（団体×申請品目）は、LP を作る前に shortages に回す。** 行を落とすと HiGHS が `"Optimal"` を返し、その分が黙って 0 になる。
6. **四捨五入の検査は残す**（03 のとおり）。実測は全変数でずれ 0 だったが、検査は安い。
7. **入力は配列の並びではなく、組み立て時の並べ替えで決める。** sort_order → 名前 → id で団体・部屋・品目を並べ、ルールは code 順、在庫・申請・了承は並べ替えた部屋・団体・品目の順で走査して作る（`buildModel` の実装）。これで配列を並べ替えても LP の文字列が同一になった。
8. **LP の変数名は連番**（`x1`、`x2`…）で足りた。x̂ も同じ連番でよい（`Bounds` に `x5 <= 3` と書く）。結果の取り出しは `result.Columns[name].Primal`。5,600 列でも問題ない。
9. **LP は折り返さなくてよい**（最長 5.9 万字の行も読める）。デバッグ用に 1000 字で折る選択肢は残す。
10. **コストは整数にそろえる（P-02）のを勧める。** 同点の解を並び順に依らず安定させる。ただし W107 を 0 にするものではない（上記）。LP には整数だけが並ぶので、`4.9` のような小数の表記ゆれも避けられる。W′ ＝ 約 9×10⁶、目的関数値 ≒ 2.7×10⁹ でも、全変数は整数で返り、距離の合計は元と一致した。
11. **最小変更モードの x̂：** 使用不可の部屋・禁止された組み合わせには作らない（K-14）。結果の行は x と x̂ を（運び元・団体・申請品目・品目）ごとに足して 1 行にする。
12. **最初の 1 回は約 110〜170 ms**（JIT）。画面の「計算中」は 0.3 秒ほどは出るものとして作る。
13. **Next.js の `next build --webpack` は使わない**（`node:module` で失敗）。
14. （T01 へ）ルートの ESLint・tsc・Vitest の対象から `spikes/` を外すこと。`spikes/highs` は npm と独自の lockfile で動き、pnpm workspace に含めない。

## 03 の直すべき点

仕様（docs/requirements）は変えていない。以下は T06 の PR で、先に 03 を直すとよい点。

1. **「定式化」の W の例。** 「R8 なら 10 × 5 × 1,295 ≒ 65,000」は d_max ＝ 5 のとき。d_max の定義（距離表の最大・上書きの最大に extra_cost の最大を足す）に従うと、CI5 に extra_cost 2 があれば d_max ＝ 7、W ＝ 90,650。例を「extra_cost の最大が 0 なら約 65,000」と直すか、extra_cost を含めた値に変える。
2. **距離コストの穴（K-15 の具体化）。** このスパイクでは次のように仮置きした。(a) 運び元＝使用場所なら 0（extra_cost は足さない。足すと CI5 を使う団体が自室の在庫を取るより他所から取る方が安くなりうる）。(b) 運び元が屋外・階が null の部屋（体育館など）→ 屋外の使用場所へは「1 階から」（3）扱い。(c) 使用場所が体育館・その他でも、建物が同じなら同じ建物の規則（同じ階 1・別の階 2）。(d) distance_overrides は (A,B) と (B,A) のどちらでも効き、「別の建物」の 4 だけを置き換える。03 に書く。
3. **「同じ使用場所を共有する団体」の扱い。** 食堂のように 1 つの部屋を複数の団体が使うとき、その部屋の在庫の取り分は同点になる（整数化でも）。決める必要があれば sort_order 順に優先する、などと書く（コストの +1 では決まらない）。W107 の「外へ出ている」は、同じ部屋を使う別の団体へ渡す場合を含めないと明記する。
4. **W107 と S05 の関係（K-12 の (3) の確認）。** 設営が S05 で 1-1〜2-3 からしか受け取れない配置では、体育館に机の在庫があると、設営の W107 が毎回出る（30 通り中 16 件）。05 の不変条件「W107 が 0 件」は、R8 の fixtures の配置で成り立つかを T05・T06 で確かめ、成り立たないなら「S05 の対象団体は除く」または理由つきの warning（設営の机は S05 のため）と書く。
5. **変数のない需要の扱い。** 03「解けないときの扱い」の 1 の前に、「LP を作る前に、候補の変数が 1 つもない（団体×申請品目）を shortages にする」を足す（行を落とすと `Optimal` が返る）。
6. **status の文字列と time_limit。** 「超えたら解を返さずエラー」は、`Status !== 'Optimal'` をすべてエラーにする、と書き、文字列（`Infeasible`・`Time limit reached` など）を載せる。
7. **決定性の節。** 「入力の並び順を固定」に、ルールは code 順、在庫・申請・了承は並べ替えた部屋・団体・品目の順に走査する、を足す。`loadHighs` のオプションを使い回さない、も注意に。`output_flag: false` を指定しておくとログが出ない（highs 1.15 は既定で出さない）。
8. **x̂ の作り方（K-14）。** 使用不可の部屋・禁止された組み合わせには作らない。結果は x と x̂ を（運び元・団体・申請品目・品目）ごとに足す、と書く。x̂ の変数名も連番でよい。
9. **最小変更モードの受け入れ基準（D-08）。** 「ほかの場所の余りが足りるなら無関係な行は変わらない」は、余りのない品目（机）では成り立たない（置き換えの連鎖で 11〜14 行が動いた）。基準を「変わった行の数を記録する」「余りのある品目だけ無関係な行は変わらない」にするのがよい。
10. **性能要件（K-22）。** 00 の「振り分けの計算は R8 規模でブラウザ 2 秒以内」は、計算（0.1〜0.3 秒）と、wasm の初回読み込み（Fast 4G 相当で約 1.3 秒、Slow 4G 相当で約 6 秒）を分けて書く。
11. **04 の「ブラウザ側の処理」に wasm の置き場所の方針**（`public/highs.wasm`、basePath を付けた `locateFile`、振り分け画面でだけ読む）を書く。
