## 確かめたこと（ローカルの GoTrue v2.197.0・Supabase CLI 2.122.0）

設計の「試していないこと」のうち T04 の分。Google そのものは使えないので、GoTrue のメールのサインアップで実際に流したものと、GoTrue のソース（supabase/auth の v2.197.0 タグ）で確かめたものに分けて書く。

- **フックの入力の形（実際に流した）**：フックを一時的に「入力を表に書いて許可する」関数に差し替え、メールのサインアップを流した。入力は `{"metadata": {"name": "before-user-created", "uuid", "time", "ip_address"}, "user": {"id", "aud", "role": "", "email", "phone", "app_metadata": {"provider": "email", "providers": ["email"]}, "user_metadata": {…signup の data…}, "identities": [], "is_anonymous": false, "created_at", "updated_at"}}`。メールは GoTrue が小文字にしてから渡す。
- **Google のときの provider と hd（ソースで確認）**：外部プロバイダーの作成では `triggerBeforeUserCreatedExternal`（internal/api/hooks.go）が `SignupParams{Provider: "google", Data: identityData}` からユーザーを作ってフックに渡す。`ToUserModel`（internal/api/signup.go）が `app_metadata.provider = "google"` を入れる。user_metadata は `structs.Map(Claims)` で、Google の ID トークンに hd があれば `parseGoogleIDToken`（internal/api/provider/oidc.go）が `custom_claims.hd` に入れる。ID トークンが返らず userinfo の経路（google.go の後半）になったときは hd が入らない。設計の条件（provider = google、hd があれば hd とメールのドメイン、なければメールのドメイン）は、この形にそのまま合っていたので直していない。
- **確認済みになる時点（実際に流した）**：一時的なトリガーで記録すると、メールのサインアップ（自動確認）は `INSERT`（email_confirmed_at が null）→ 同じ要求の中の `UPDATE`（email_confirmed_at が入る）の順だった。Google も同じ（external.go の createAccountFromExternalIdentity が signupNewUser の後に `user.Confirm(tx)`）。したがって Google のユーザーの招待は on_auth_user_confirmed で付き、seed のように確認済みで insert したときは on_auth_user_created で付く。招待を入れておいたメールでサインアップすると、確認のトリガーで viewer が付き、招待が使用済みになり、監査の理由が「招待の受け入れ」になった（確認の後、一時的な関数とデータは消した）。
- **フックが呼ばれる経路**：GoTrue の `/auth/v1/signup` は呼ぶ（学校のドメイン・テスト用のドメインとも 403 `{"code":403,"error_code":"unknown","msg":"学校の Google アカウントでログインしてください"}`。E2E の auth-hook.spec.ts で毎回確かめる）。管理 API（secret キーの `/auth/v1/admin/users`）は呼ばない（internal/api/admin.go にフックの呼び出しがない。実際にユーザーができた）。seed・SQL Editor の insert も通らない。
- **seed のユーザーのパスワードログイン**：`/auth/v1/token?grant_type=password` でトークンが返る（設計 8.3 の列の入れ方で足りた）。フックはログインでは呼ばれない。
- `supabase db reset` → `supabase test db`：10 ファイル 4089 件すべて ok。

## 招待の受け入れの穴（T03 の security の指摘、D-17a）

指摘：invite・accept_my_invitations・auth.users のトリガーは「確認済みのメール」を auth.users.email_confirmed_at で判定していた。これは最初の確認の時刻で、あとで email を変えても null に戻らない。メールの変更に確認が要らない設定だと、ログイン済みの人が自分の email を招待された人のアドレスに変えて、その人あての招待（admin を含む）を受け取れる。

判定：`private.verified_email(user_id)`（0005）が今のメール（小文字）を返すときだけ招待を付ける。返すのは次をすべて満たすとき。

- 削除されていない・email がある・email_confirmed_at がある
- メールの変更の途中でない（`email_change` が空）
- auth.identities に、auth.users.email と同じメール（小文字で比べる）の identity があり、それが **Google の identity** か、identity_data の **email_verified が true の email の identity**
- （積み直しで T03 の版になった）Google の identity は identity_data の email_verified が真（真偽値の true か文字列の "true"）のときだけ。Google の identity があるアカウントは Google の identity のメールだけを見る（email の identity は見ない）。判定の関数・invite・accept_my_invitations は T03 の 0005 にあり、T04 の 0007 のトリガーはそれを呼ぶだけ

理由（GoTrue v2.197.0 のソースで確かめた）：

- identity_data は利用者が `/auth/v1/user` で書き換えられない（user_metadata と違う）。Google の identity のメールは Google の ID トークンの値で、Google でログインするたびに上書きされる（external.go の AccountExists）。auth.users.email を変えても Google の identity のメールは変わらない。
- email の identity は、受信箱で確かめたメールの変更のときだけ、新しいアドレスと `email_verified: true` に書き換わる（verify.go の emailChangeVerify）。管理 API で変えたときは `email_verified` は管理者が渡した値（admin.go）。
- v2.197.0 では、匿名でないユーザーのメールの変更は、設定によらず新しいアドレスの確認が要る（user.go の UserUpdate。自動確認は匿名ユーザーだけ）。それでも、GoTrue の版や設定の違い、SQL Editor・管理 API での変更で auth.users.email だけが変わることがあるので、DB の側でも identity と突き合わせる。
- メールの変更の途中を除くのは、確かめ終わる前の状態で判断しないため（変更が終わるか取り消されれば、次のログインの accept_my_invitations で付く）。

トリガーの付け方を変えた：auth.users の insert の時点では identity がまだないので、insert では profiles だけを作り、招待は auth.identities の insert（seed のように確認済みのユーザーに identity を足したとき）と、メールの確認（Google の初回ログイン。GoTrue は user の insert → identity の insert → 確認の update の順）で受け入れる。seed のテストユーザーと 030 の Google の経路は今までどおり付くことを確かめた。

設定：README の「4. ログイン」の 7 に「必ず守る Auth の設定」（Google だけ、Email・Phone・匿名は無効、Confirm email と Secure email change は有効のまま、Allow manual linking は無効のまま）を書いた。ローカルの config.toml も `enable_confirmations = true`（`double_confirm_changes = true` は前から）にした。GoTrue の環境変数が GOTRUE_MAILER_AUTOCONFIRM=false・GOTRUE_MAILER_SECURE_EMAIL_CHANGE_ENABLED=true になり、seed のテストユーザーのパスワードログインと E2E はそのまま通った。

テスト（030 の (5b)）：Google のユーザーが email を他人のアドレスに変えても accept_my_invitations は0件・invite は applied: false・ロールも団体代表も付かない。email の identity のメールが元のまま、または変わっても email_verified が false なら0件。メールの変更の途中なら確認のトリガーでも付かず、終われば1件。受信箱で確かめた変更（identity が新しいアドレスと email_verified: true）なら付く。判定を元の email_confirmed_at だけに戻すと、(5b) の 8 件が落ちることを確かめた。

残るもの：匿名ログインとメールの自動確認を両方有効にすると、GoTrue は匿名ユーザーが足したメールの identity を email_verified: true で作る（README で匿名を無効にし、フックも匿名の作成を拒否する）。メールのサインアップの確認では GoTrue が email_confirmed_at の後で identity を email_verified にするので、確認のトリガーでは付かず、次のログインで付く（本番ではメールのサインアップを使わない）。

## 画面の作り

- ログインは PKCE。`detectSessionInUrl: false` にして、/auth/callback/ で `exchangeCodeForSession` を1回だけ呼ぶ。戻り先は sessionStorage に置く（リダイレクト URL にクエリを付けない。Supabase の Redirect URLs は `/auth/callback/` だけ登録すればよい）。戻り先は同じサイトのパスだけ（`//`・`/\`・制御文字・/login・/auth は `/`）。E2E で `?next=//evil.example/` がサイトの外に出ないことを確かめた。
- URL に付いて戻ったエラーの文言はそのまま表示しない（他人が作ったリンクで任意の文言を出させない）。フックの拒否だけ「学校の Google アカウントで…」と案内する。
- ログイン状態は supabase-js が localStorage に保存し、トークンを自動で更新する。onAuthStateChange のコールバックでは状態を置くだけにした（中で supabase の非同期の関数を呼ぶと supabase-js のロックで止まる）。
- 立場は、ログインのたび（ページを開いたときも）に accept_my_invitations を呼んでから、自分の profiles・year_roles・group_members（groups を埋め込み）・years を読む。今の年度は「ロールか団体代表の行がある年度のうち1日目が最も遅いもの」（K-19 は T09 で決める）。どこにもなければ「総務から招待されていません」とログアウトだけ。
- RequireAudience は、立場を読み込み中（idle・loading）なら LoadingState を出す（前は「権限がありません」を出していて、読み込みの一瞬に誤った表示が出得た。AppShell の中では読み込み後にしか描かれないが、単体テストで決めた）。立場が合わない・読めないときは ForbiddenState。
- ナビゲーションは 00「画面一覧」のロールで出し分け（lib/navigation.ts）。まだない画面は「準備中」でリンクにしない。各チケットが画面を作ったら `ready: true` にする。viewer は今はホームだけ（確定後の振り分け表の閲覧は T13 で決める）。
- テスト用ログインの出し分け：`NEXT_PUBLIC_ENABLE_TEST_LOGIN` は next.config.ts の `env` で必ず 'true'／'false' を埋め込む。未設定のままだと Next.js（Turbopack）は置き換えず、実行時の判定になってフォームのチャンクが本番のビルドに残った（実際に確かめた）。埋め込むと `next/dynamic` の import ごと消える。さらに Supabase の URL がローカルでなければ出さない。

## セキュリティの観点での見直し（自分で）

- フックは表を読まず SECURITY DEFINER にしない。execute は supabase_auth_admin だけ（010・030）。provider は GoTrue がサーバー側で入れる値で、利用者は変えられない。hd（user_metadata.custom_claims）は Google の ID トークンから来る。メールのサインアップでは利用者が user_metadata を送れるが、provider が email なので hd を偽っても拒否される。
- トリガー関数と accept_invitations_of は誰にも execute を与えない。中の insert はすべて on conflict で、ユーザーの作成を失敗させない。
- 招待は確認済み・削除されていないアカウントだけ。未確認・削除済み・closed の年度・既存のロールの上書きを 030 で確かめた。
- 画面の出し分けは見た目だけで、守りは RLS・RPC（招待のない人は全表と v_remaining が0行、profiles は自分だけ。030）。
- GoTrue の `/auth/v1/user` でのメールアドレスの変更はフックを通らない（フックは作成だけ）。email を変えただけでは招待は付かない（D-17a。上の「招待の受け入れの穴」）。受信箱で確かめた変更の後は、次のログインの accept_my_invitations で付く（メールの変更で受け入れるトリガーは作っていない）。
- reviewer・security-reviewer のサブエージェントは、このセッションでは起動できなかった（使えるツールにない）。メインのセッションで回すこと。
