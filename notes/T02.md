## 設計からの変更点

1. rules.year_id は更新で変えられない（トリガー `guard_rules`、invalid_input）。設計書の改訂後に見つかった抜け (a)。ポリシーの with check だけに頼ると、admin が年度を closed のルールへ移せるため、DB 側で止めた。T03 のポリシーでも `with check` に year_id の一致を足すこと（二重の守り）。
2. distance_overrides の `building_a < building_b` は、C の照合順序の比較に変え（`collate "C"`）、BEFORE トリガー `normalize_pair` で小さい方を building_a に入れ替える。抜け (d)。DB の照合順序（ja_JP などで a < Z）と JavaScript の並び順が違っても、呼ぶ側は順序を気にしなくてよい。同じ建物どうしは CHECK で 23514。
3. トリガー名 `guard_closed`（rules）を `guard_rules` に変えた（year_id の不変も見るため）。
4. テストの補助 `personas.psql` に `tests.act_as(名前)` / `tests.act_clear()` を足した。T02 の時点ではポリシーがないので、postgres のまま `request.jwt.claims` だけ置いて auth.uid() を変える。`login_as`・`try_cell` は T03 の権限表のテスト用に設計のまま入れてあるが、T02 では使っていない（T03 で grant を入れてから動かすこと）。
5. fixture に中身のある検査用のデータを足した（抜け (c)）。T-G4（Y1、部門、使用場所なし）を作り、staff と viewer を G4 の団体代表にした（group_members(own) の staff・viewer）。rep を Y2 の viewer にした（year_roles(own) の rep）。staff あての使用済みのロール招待を足した（invitations(own) の staff）。**T03 の権限表の期待値を作るとき、この 3 つで staff・viewer・rep の見え方が変わることに注意**（例：staff は G4 の申請を団体代表として書ける。rep は Y2 を viewer として読める）。
6. 型の整形に oxfmt 0.74.0（exact）を devDependency に追加した。`supabase gen types` の出力は未整形（CLI 自身が oxfmt を案内している）で、整形しないと再生成の差分が読めない。

## 試したことで分かったこと

- pgTAP の `col_type_is`・`col_default_is`・`col_not_null`・`col_is_pk`・`col_is_unique`・`has_index` は、スキーマを付けた 3〜4 引数が別の多重定義（表, 列, 説明）に解釈され、「Column public.xxx does not exist」になる。スキーマなし（public は search_path にある）で書く。
- `col_default_is` に配列の既定値は渡せない（型変換で失敗）。`information_schema.columns.column_default` を `is()` で比べる。
- 団体を消すと fixture の受け渡し・振り分けも連鎖で消えるので、テストで消した団体の行を後で使わない。
- 年度の連鎖削除の監査は `id > :a0`（`\gset`）で絞らないと、その前の削除の記録が混ざる。
- seed を流した DB で fixture を作るので、距離の上書きは `pgtap棟A` 側のコスト 4 が 1 件ある。距離のテストは別のコスト値（31・41…）で絞る。

## T03 への申し送り

設計書の改訂後に見つかった抜けのうち、T03 で直すもの：

- (a) `rules_update` のポリシーの with check に、`year_id` が変わらないことを足す（DB 側は T02 のトリガーで止めた）。
- (b) T03 のテストから、T04 の 0007 がないと通らない検査（auth.users のトリガー、profiles の自動作成、supabase_auth_admin の execute）を外し、T04 の 030_auth.test.sql に移す。010_grants の「supabase_auth_admin が実行できる関数」は T04 で足す。fixture の `tests.create_user` は profiles を直接 insert している（`on conflict do nothing`）ので、0007 が入っても動く。
- (c) 権限表の期待値：上の fixture の追加分（invitations(own) の staff、year_roles(own) の rep、group_members(own) の staff・viewer）を、本当に行が返ることとして確かめる。
- (e) `private.year_role` と `private.is_request_open` は設計の 0003 で使われていない。消すか、ポリシー・RPC から使う。14 個という数（010_grants の set_eq）も合わせて直す。
- (f) `update_requests_after_deadline` に `submitted: false` を渡すと未提出に戻る。D-07 で振り分けの需要が変わるので、戻さない（null を渡しても submitted_at を触らない）か、明示的な引数にして 04 に書く。
- (g) `save_auto_allocations`・`set_consent` で CHECK 違反（23514）が生のまま返る。例外ブロックで invalid_input に直す（クラス 22 と合わせて）。
- (h) 04 に書く文案：「ダッシュボードの確定ボタンは、画面を開いたときにほかのデータより先に years.allocation_version を読み、その版で検証（validate）を実行する。確定のときは検証した版を `p_base_version` に渡す。conflict が返ったら、読み直して検証をやり直し、結果を見せてから、もう一度確定を押してもらう（自動では再送しない）」。画面は T09・T13。

そのほか：

- D-16〜D-19 を T03 が使う。T02 は D-09〜D-15 を使った。T03 で決めるもの（closed の読み取り専用と例外、staff が自分の行を読める、前年度の数の RPC、create_year_from の制限、profiles の範囲、招待は確認済みのアカウントだけ、submit_requests、W102）は 4 つにまとめるか、D-20 以降を使うロジック側と調整する。
- 0003 は 0002 の `private.fail`・`private.lock_year_guard` を使う。`revoke all on all functions in schema private from public` は 0002 の最後にあるが、0003 以降で関数を足したら、その最後にもう一度書く。
- 0002 のトリガー関数は 0003 の判定関数を呼ばない（T02 だけを当てても動く）。この約束を壊さない。
- 監査の `app.reason`：RPC は書き込みと同じ関数の中で `set_config('app.reason', …, true)` を呼ぶ。pgTAP は 1 つのトランザクションなので、理由を置く RPC の後の直接の書き込みにも理由が残る。理由を検査するテストは RPC の直後に読む。
- 権限表の `try_cell` は、確定中の守りの `invalid_state` を denied とみなす。それ以外の P0001 は error のまま。
- テストは `supabase db reset` の後（seed の品目 9 件がある状態）で流す。fixture が品目の件数を確かめて、足りなければ例外にする。
- 同時実行の手での確認（設計 9.6 の (1)〜(6)）のうち、T02 の分（(4) の 2 セッションの stocks の update）は上のとおり通した。(1)〜(3) は RPC が要るので T03。
- T04：`tests.create_user` が `@pgtap.test`、seed のユーザーは `@example.test`。ドメインをぶつけないこと。
