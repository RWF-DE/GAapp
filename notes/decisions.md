## D-02 テストユーザーとドメイン制限フック（2026-10-28、K-10）

- **決定**：E2E・CI のメール＋パスワードのテストユーザー（管理者・部員・団体代表・未招待）は、supabase/seed.sql で auth.users に直接入れて作る（フックを通らない）。フックが許可するのは学校のドメインだけ。seed は本番に流さず（migrate.yml は `supabase db push` だけ）、本番ではメールログインを無効にする。テストユーザーのメールは予約済みのドメイン（例：`admin@example.test`）にし、実在の人のメールは使わない。
- **T04 での追記（2026-10-29）**：
  - テストユーザーは閲覧のみ（viewer）を足して5人（R8 の年度に招待を入れてから auth.users に入れ、トリガーでロールを付ける。id は固定）。パスワードはローカル専用の固定値（秘密ではない）。

- **反映先**：02_data.md「権限とRLS」（ログインの箇条書き）、05_development.md「ブランチ・レビュー・CI」4・「リポジトリ構成と環境変数」、04_screens_api.md「ログイン」。

## D-05 長机(3人掛)の読み替えと E006（2026-10-28、K-08）

- **決定**：allocate の前処理1（企業以外の長机(3人掛)の申請を長机(2人掛)に1対1で読み替える）を残す。E006 は、長机(3人掛)以外の、申請できない区分の品目（不可机・不可椅子など）の申請だけを対象にする。DB の requests には長机(3人掛)のまま残ってよい。
- **これに伴うこと**：
  - 申請画面は今の仕様どおり、企業以外に長机(3人掛)の入力欄を出さない。CSV の取り込みも今の仕様どおり、取り込むときに長机(2人掛)に読み替える。DB に3人掛が入るのは、API を直接呼んだときと過去のデータだけ。

  - DB のトリガーで申請できない品目を止めるかは T03 で決める。止める場合も、企業以外の長机(3人掛)は例外にする。
- **反映先**：03_allocation.md「前処理」1と「検証コード一覧」（E006 の条件、E003・W101 の比べる相手）、01_rules.md S03 の注記。

## D-06 「残す」の行の保存のしかた（2026-10-28、K-02）

## D-08 最小変更モードの受け入れ基準（2026-10-28、K-04）

- **決定**：基準を条件つきに直す。「使用不可にした部屋から運んでいた品目に、ほかの場所の余りが足りるなら、その部屋と無関係な行は変わらない。足りないときは、変わった行の数を記録する」。「変わった行」は、（運び元・団体・申請品目・品目）ごとの数が変わったものと定義する（行の id は比べない）。
- **補足（T06 の設計、2026-10-29）**：「余りが足りる」は品目全体の余りではなく、「使用不可にした部屋 M から受け取っていた（団体・申請品目）の失った分を、前回のほかの行を変えずに、その団体がルール上使える場所の余りから、代替の重さの合計を増やさずに補える」ことを意味する（運び元の制限 S05 などで、品目全体に余りがあっても成り立たない反例がある。notes/T06-design/logic-design.md 6.3）。そのとき成り立つのは、「前回の M 以外の行は減らず、増えるのは M から受け取っていた（団体・申請品目）の行だけで、M と無関係な行は変わらない（同じキーで同じ数）」。判定は候補でつながる申請品目のまとまりごとに行う（03「目的関数」、05「不変条件」）。
- **これに伴うこと**：05 の不変条件のテストは、第一セミナーを使用可にして1回解く → 使用不可にする → 最小変更で解く、の手順で行う（R8 の fixtures では第一セミナーが最初から使用不可のため）。SPEC の E2E 手順7（MER）も同じ基準にそろえる。
- **反映先**：SPEC.md「受け入れ基準」「E2E の検証手順」7、05_development.md「不変条件」。
- **チケット**：T06、T14。
- **状態**：T06 の PR（feat/T06-allocator）で 03「目的関数」、05「不変条件」、SPEC「受け入れ基準」「E2E の検証手順」7 に反映済み。

## D-09 表の作りと入力の上限（2026-10-29、DB 設計）

- **決定**：全表（audit_logs を除く）の created_at・updated_at はトリガーが入れ、クライアントの値は使わない。年度の一致は、allocations・deliveries・invitations の複合外部キー `(group_id, year_id) → groups (id, year_id)` で保証する（トリガーにしない）。場所・品目への外部キーは restrict、年度・団体は cascade、記録のためのユーザー参照は set null。自由記述は 2000 字、名前は 100 字、数は 10000 までを CHECK で止める。
- **理由**：複合外部キーは、トリガーより確実でダンプからの復元でも壊れない。上限は、団体代表・部員が書ける列で無料プランの 500MB を使い切らせず、解けない申請や整数のあふれを防ぐため。
- **反映先**：02_data.md「テーブル定義」の前書きと DDL。
- **チケット**：T02。
- **状態**：要件定義に反映済み（T02 の PR）。

## D-13 確定中・終了の守りとロック（2026-10-29）

## D-16 年度・団体の付け替えを止める（2026-10-29）

- **決定**：年度を持つ表の year_id（room_years・stocks・groups・year_roles・invitations・allocations・slots・deliveries）と、団体を主キーに含む表の group_id（group_members・request_submissions・requests・substitution_consents）は、更新で変えられない（BEFORE UPDATE のトリガー `check_immutable`、`invalid_input`）。rules.year_id は D-15 のとおり別のトリガー。allocations・deliveries・invitations の group_id は、複合外部キーで年度が固定されるので同じ年度の別の団体にだけ動かせる。anon・authenticated には public・private の表・シーケンス・関数の権限を与えない（シーケンスの revoke を足し、PUBLIC の execute も含めて pgTAP で棚卸しする）。
- **理由**：D-13 の確定中・closed の守りと D-12 の版の増分は、更新後の行の年度しか見ない。年度と団体を一緒に書き換えると複合外部キーも通るので、確定中の年度から振り分けを抜き出せた。old table と new table の両方を見る案より、列を固定するほうが単純で、年度をまたぐ書き換えの用途もない。

## D-17a 招待を受け入れる「本人のメール」（2026-10-29、T03・T04、T03 の security の指摘）

- **決定**：
  - 招待を付ける（invite のその場の受け入れ・accept_my_invitations。T04 の auth のトリガーも同じ）のは、`private.verified_email(user_id)` が値を返すときだけ。条件は、削除されていない・email がある・email_confirmed_at がある・メールの変更の途中でない（email_change が空）、かつ auth.identities に auth.users.email と同じメール（小文字で比べる）の identity があり、それが identity_data の email_verified が真（真偽値の true か文字列の "true"。GoTrue の版で形が違う）の Google の identity か、email_verified が true（真偽値）の email の identity であること。招待のメールはこの値と比べる。
  - 自分あての招待の読み取り（ポリシー invitations_select）も同じ判定にする。JWT の email（auth.jwt() ->> 'email'）とは比べない。ポリシーは、自分の分だけを返す判定関数 `private.my_verified_email()` を呼ぶ（authenticated に execute を与える判定関数は 13 個になる）。`private.verified_email` は任意の user_id のメールを返すので、authenticated には execute を与えない。
  - Google の identity があるアカウントは、Google の identity のメールだけを信じる（email の identity は email_verified が true でも見ない）。
  - トリガーは、auth.identities への insert（seed のように確認済みのユーザーに identity を足したとき）と、email_confirmed_at が null から値に変わったとき（Google の初回ログイン。identity は確認の前に入る）。auth.users への insert では profiles だけを作る（identity がまだないため）。
  - verified_email は二重目の守りで、本番の Auth で必ず次の設定を守る（README「4. ログイン」の 7「必ず守る Auth の設定」。T04）。
    - ログインは Google だけ（Email・Phone・匿名のサインインは無効）。Google の identity のないアカウントを作らせない。
    - Confirm email と Secure email change は有効。
    - Allow manual linking は無効。ローカルの supabase/config.toml も T03 で `enable_confirmations = true`（`double_confirm_changes = true` は前から）にする（auth のトリガーには触れない）。
- **理由**：auth.users.email_confirmed_at は最初の確認の時刻で、あとでメールアドレスを変えても null に戻らない。メールの変更に確認が要らない設定（や GoTrue の版の違い、SQL・管理 API での変更）だと、ログイン済みの人が自分の email を招待された人のアドレスに変えて、その人あての招待（admin を含む）を受け取れ、JWT の email もそのアドレスになるので、その人あての未使用の招待（年度・ロール）を読めた。identity_data は利用者が書き換えられない（user_metadata と違う）。Google の identity のメールは Google が持ち主を確かめたアドレスで、ログインのたびに Google の値で上書きされる。ただし email の identity の email_verified が信じられるのは、Confirm email と Secure email change が有効なときだけ。有効なら GoTrue は、新しいアドレスを受信箱で確かめた変更のときだけ email の identity を新しいアドレスと email_verified: true に書き換える。無効（GOTRUE_MAILER_AUTOCONFIRM=true。T03 の前のローカルの enable_confirmations = false）だと、double_confirm_changes が有効でも、GoTrue（v2.197）は古いアドレスに届いたリンクだけで変更を終え、email の identity を新しいアドレスと email_verified: true に書き換える（email・パスワードのユーザーが自分のリンクだけで、他人あての admin の招待を受け取れた）。Google だけのユーザーでも、Email プロバイダーを無効にしていても、同じリンクで email_verified: true の email の identity が新しくでき、verified_email がそのアドレスを返した（T03 のレビューで確かめた）。設定が有効なら、古いアドレスのリンクだけでは変更が終わらず、identity も変わらない。Secure email change が無効だと、変更は新しいアドレスの確認だけで終わり、古いアドレスの持ち主に確かめない（盗まれたセッションからメールを付け替えられる）。Allow manual linking が有効だと、利用者が identity を外せる。Confirm email も無効なら、Google のユーザーがメールを変えて email の identity を作り、Google の identity を外して email だけのアカウントになれば、「Google の identity のメールだけを見る」守りを抜けて他人の招待を取れた（T03 の攻撃での確認）。無効なら Google の identity を外せないので、Confirm email が崩れても止まる。Email・Phone・匿名のサインインが有効だと、Google の identity のないアカウントができ、email だけのアカウントは Confirm email と Secure email change だけに頼る。Google の identity の email_verified も見るのは、Google が持ち主を確かめていないアドレスをメールが一致するだけで信じないため（T03 の攻撃での確認で、false でも信じていた）。本番は全員が Google の identity を持つので、Google の identity があるときに email の identity を見なければ、設定が崩れても止まる。メールの変更の途中を除くのは、確かめ終わる前の状態で判断しないため。T03 だけをマージしたときにも穴が残らないよう、T04 から T03 に移した（ローカルの config.toml の enable_confirmations も。auth のトリガーと、本番の Auth の設定を README に書くのは T04）。
- **反映先**：02_data.md「権限とRLS」（権限表の下の説明、招待の受け入れ・本番の Auth で必ず守る設定・テストユーザーの箇条書き）、04_screens_api.md「DB関数（RPC）」の invite・accept_my_invitations、supabase/config.toml、README「4. ログイン」の 7。
- **残るもの**：Google の identity のない email だけのアカウント（ローカルのテストユーザー。T04 の seed）は、Confirm email と Secure email change の設定に頼る（設計どおりの既知の依存。本番では Email・Phone・匿名のサインインを無効にし、email だけのアカウントを作らない）。匿名ユーザーとメールの自動確認を両方有効にすると、GoTrue は匿名ユーザーが足したメールの identity を email_verified: true で作る（確かめていない）。匿名ログインは無効（設定とフックの両方で止まる）にする。email のサインアップの確認（受信箱のリンク）では、GoTrue は email_confirmed_at を入れた後で identity の email_verified を true にするので、確認のトリガーでは付かず、次のログインの accept_my_invitations で付く（本番ではメールのサインアップを使わない）。
- **チケット**：T03（verified_email・invite・accept_my_invitations・invitations_select、ローカルの config.toml の enable_confirmations）、T04（auth のトリガー、本番の Auth の設定を README に書く、テストユーザーの identity）。
- **状態**：要件定義に反映済み（T03・T04 の PR）。

## D-18 年度の複製と確定（2026-10-29、DB 設計・T03）

## D-19 RPC の入力・エラー・提出（2026-10-29、T03）

- **決定**：
  - 申請の提出は RPC submit_requests（申請と提出を1トランザクションで書く）。D-07 は変えない。
  - update_requests_after_deadline の p_submission は `{ submitted: true, submittedAt, note }`（どれも省略可。ほかのキーは invalid_input）。submitted は true だけを受け付け、提出済みにする（最初の提出日時を保つ）。未提出には戻さない（`submitted: false` は invalid_input）。未提出に戻すと D-07 で需要が fixed_request に変わり、振り分けが変わるため。どうしても戻すときは、確定の前に SQL Editor で直す（記録は監査に残る）。
  - submittedAt（オフセットつきの ISO 8601 の日時。未来・特別な値は invalid_input）を渡すと、提出済みにして submitted_at をその値にする（提出済みでも置き換える）。CSV の取り込み（T11）でフォームのタイムスタンプを残し、K-27 の申請順をフォームの提出順にするため（ロジック設計の申し送り）。RPC はその書き込みの間だけ transaction-local の `app.keep_submitted_at` を立て、提出の記録のトリガーは値を now() に置き換えない。admin だけが呼べる RPC なので、団体代表は日時を偽れない。submit_requests と直接の書き込みは今までどおり now()。
  - RPC のトップレベルの型つきの引数（uuid・enum・date・integer）は PostgREST が関数の前に変換するので、形が違うと 22P02・22007 などがそのまま返る。画面は zod で先に確かめ、22 で始まる SQLSTATE は「入力の形が違う」として扱う。
  - RPC の中で起きた形の誤り（SQLSTATE のクラス 22）と CHECK 違反（23514）は、すべての書き込みの RPC で invalid_input に直す（save_auto_allocations・set_consent・submit_requests・update_requests_after_deadline・check_delivery に例外ブロックを足した。save_auto_allocations は数の上限 10000 も先に確かめる）。
  - revoke_invitation は、ロールを確かめてから招待の行をロックする（ロールのない人に行ロックを取らせない）。招待が見つからなければ forbidden（有無を漏らさない）。
  - update_year は、年度名（一意の列）を変えるときだけ別の文で書く。SET に年度名があると、値が同じでも行のロックが外部キーの確認（FOR KEY SHARE）とぶつかる強さになり、その年度を参照する行の insert（部員の在庫入力など）を update_year のコミットまで待たせ、デッドロックの元になる（ローカルの Supabase で再現して確かめた。notes/T03.md）。
  - rules.year_id の付け替えは、ポリシーの with check（更新後の行しか見ない）ではなく、T02 のトリガー guard_rules で止める（D-15）。T03 は pgTAP で、両方の年度の admin でも closed の年度へ移せないことを確かめる。
- **理由**：画面に生の SQLSTATE を返さず、エラーの扱いを message のコードだけで決められるようにするため。提出の状態を誤って戻して振り分けが変わるのを防ぐため。
- **反映先**：04_screens_api.md「DB関数（RPC）」の表と箇条書き。
- **チケット**：T03、T11（申請一覧・締切後の修正）。
- **状態**：要件定義に反映済み（T03 の PR）。

## D-20 W107 の定義（2026-10-29、T00「03 の直すべき点」4、T06 の設計 12.4・15 章の1）

- **決定**：W107 は、団体 g の使用場所 L から品目 j が外（使用場所が L でない団体 h）へ出ているのに g が L 以外の場所 r から同じ j を受け取っている組み合わせのうち、(1) 入れ替え（g が L の j を使い、h が r の j を使う）がルール（代替の区分・了承・運び元の制限・使用不可）の上でき、(2) 入れ替えても運ぶ距離の合計が増えない（d(r,h) ≤ d(r,g) ＋ d(L,h)）ものが1つでもあるときだけ出す。05 の不変条件「W107 が0件」はこの定義で満たす。
- **理由**：T00 のダミーで出た W107 はすべて S05（設営は体育館の机を使えない）によるもので、入れ替えるとルール違反になり管理者が直せない。距離の条件がないと、distance_overrides が三角不等式を崩すときに直しようのない W107 が出る。この定義なら、全体の実行の最適解には（距離の上書きがあっても）W107 は出ず、出るのは最小変更モードで前回の行を保った場合と手で決めた行だけになる。

## D-24 コストの整数化と辞書式の優先順位（2026-10-29、P-02・K-12、T06 の設計 6 章）

## D-33 画面のデータの読み書き（2026-10-29、画面の設計 1.5・1.7・2 章）

- **決定**：

  - 直接の更新は updated_at を条件に入れ（受け取った文字列をそのまま返す）、直接の削除も `.select()` で消えた行を受け取る。0 行なら読み直して not_found・conflict・権限や状態の変化を分ける（RLS で拒否された update・delete はエラーにならず 0 行で成功するため）。
  - 任意の文字列（建物・表示名・備考など）は、空なら null にして保存し、読むときも '' を null にそろえる（shared の型は空文字を許さない）。
  - エラーは lib/errors.ts の1か所で、code と details から種類（forbidden・not_found・state・conflict・input・reason・issue・blocked・deadlock・auth・network・unknown）に分け、日本語の文言と「読み直すか・入力を残すか」を決める。JWT のエラー（PGRST301〜303・HTTP 401）は、セッションの更新を1回試し、だめならその端末のセッションを消してからログインへ。文言にメールアドレスと CSV の中身を入れない。代表的な失敗は本物の DB の応答でもテストする。
  - 書き込みのボタンは送信中は押せない。通信の失敗で保存されたか分からない書き込みは、自動で送り直さず、版・updated_at・一意のキーで確かめてから送り直す。
  - 未保存の入力は、アプリの中の移動と年度の切り替えの前に確かめ（AppLink の onNavigate、ガードつきの router、ガードつきの setYear）、ブラウザの戻る・タブの破棄に備えて下書きとして localStorage に置く（利用者・年度・画面ごと。24 時間で捨て、保存に成功したら消す）。
  - ログアウトはその端末のセッションだけを終える（`signOut({ scope: 'local' })`）。手動のログアウトは、未保存の入力があれば確かめてから、キャッシュ・その人の下書き・選んだ年度を消す。401 などで強制的にログアウトするとき（ほかのタブのログアウトを含む）は、確かめず、下書きを消さない（キーに user_id があるので別の人には出ず、同じ人がログインし直せば戻せる）。別の user_id でログインしたときは、キャッシュと他人の下書きを消す。
  - 立場の読み直し（forbidden・state・確定の後）は裏で行い、読み直しの間も前の立場で画面を出す（isRefreshing）。ページを読み込み中に置き換えるのは、初回の読み込みと利用者が変わったときだけ。
  - DB の行から YearData を作るときに、allocator の createContext で参照を確かめる。参照の切れたルール（消した団体・場所を指すもの）はそのルールを外して入力の誤り（ルールのコードつき）にし、確定を止める。団体・場所の削除の確認で、参照している有効なルールのコードを出し、先に無効にするまで削除させない。
  - 版の見張りは、版だけを 60 秒ごとと画面に戻ったときに読み、進んでいれば帯で知らせる（自動では読み直さない）。
- **理由**：版を先に読めば、その後に読んだデータは版の時点か新しく、保存・確定のときに版の違いで取りこぼさない。編集中の画面を勝手に書き換えない。エラーの文言を画面ごとに書くと、同じエラーの言い方がばらばらになり、details の扱いも漏れる。削除の 0 行を成功と見ると、消えていない行を「削除しました」と言う。App Router にはルートの変化のイベントがなく、iOS は beforeunload をほとんど出さないので、移動の確認だけでは入力を守れない。既定の global のログアウトは、同じ人のほかの端末のセッションも終わらせる（共用 PC で抜けると本人のスマホも抜ける。E2E の保存したセッションも壊れる）。セッションの期限切れで下書きまで消すと、在庫や申請の入力を失う。年度の切り替えは画面の移動ではないので、移動の守りを通らない。T04 の AuthProvider のままでは、立場の読み直しのたびに画面が外れ、未保存の変更と理由の入力が消える。validate は参照の切れたルールで例外を投げ、ルールの params の団体・場所には外部キーがない。
- **反映先**：04「画面仕様」の前書き、「共通レイアウト」、「DB関数とブラウザ側の処理」、「マスタ設定」。

## D-34 振り分けの計算エンジンと手での編集（2026-10-29、画面の設計 3.9・4 章）

- **決定**：
  - Worker は1つだけ作って使い回す（振り分け画面を離れて戻っても同じ。ログアウトで止める）。管理者が振り分け中に振り分け画面を開いたときだけ、Worker を作って highs を読み込み始める（部員・閲覧のみと、振り分け中以外は読み込まない）。読み込みの失敗は覚えず、次の実行で読み直す（URL に回数を付ける）。
  - wasm は `require.resolve('highs/runtime')` で引いて apps/web/public/highs.wasm にコピーする（predev・prebuild）。
  - validate と Excel の作成は主スレッドで行う。exporter（ExcelJS）は動的 import。
  - 自動振り分けの保存の前には validate を回さず、保存して読み直した行（id つき）で検証する。
  - 自動振り分けの「中止」は、Worker の中の段階（読み込み・計算）と読み直しの段階だけで出す。保存を送った後は中止せず、結果を待つ。中止の後は版を読み直す。
  - 部屋を使用不可にするときは、先にその部屋からの固定・手動の行を一覧にして直して保存してもらい、その後で使用不可にする。使用不可の部屋の行と precheck の E002 には、運び元の変更と削除だけを出す（save_allocation_rows は使用不可の部屋の行の update を、固定だけの変更でも E002 で拒否し、手動の行は固定を外しても再実行で動かないため）。
  - 手での編集は「未保存の変更」として画面に溜め、理由をつけて save_allocation_rows で1回に送る（1000 件まで）。数は 1〜10000（0 は削除）。備考だけの変更も手動の行になる（DB と同じ）。ぶつかったときは読み直して当て直し、当て直せない変更を一覧で知らせる。応答が届かず保存されたか分からないときは、版を読み直し、進んでいれば読み直した行と突き合わせてから知らせる（行の追加が二重にならないように）。

- **状態**：採用（T09a と T13 で実装し、2026-10-30 に main にマージした）。

## D-36 E2E のデータ（2026-10-29、画面の設計 7.2）

- **決定**：E2E は、ローカルの DB（127.0.0.1・localhost 以外なら止める）に `pg` でつなぐ。
  - 年度をまたぐ表（テスト用のデータセットの場所と、合成データの距離の上書き）は、並行のテストを始める前の setup で1回だけ、名前で入れる（on conflict do nothing）。入った行の属性がデータセットと違えば止める（R8 の本データの seed と名前が重なったときも黙って進めない）。
  - 年度の作成のテストは、1日目を seed の R8 より後（2199 年台。新しい年度は 2200 年）にしたシナリオの年度から、使い捨てのテストユーザーの管理者で行う（create_year_from は全年度の中で最新の年度からしか作れない。seed のユーザーにはこの年度のロールを付けず、並行のテストでは使わない）。serial で年度をまたぐ表を変えるテストは、テスト専用の名前の行だけを作って変え、最後に消す（データセットと seed の行は変えない）。setup は最初に、前の実行の残り物（シナリオの年度・テスト用の行・使い捨てのユーザー）を消す。
  - テストごとに「シナリオの年度」（1日目は 2001 年台。状態・受付期間・データ〔空・小・合成データ r8like・解けない入力〕・ルールの有無・振り分けの行・追加の団体・前年度・場所の使用・ロールを選べる）を作り、終わったら消す。シナリオは年度の表だけに書き、場所の id は名前で引く。データセットにない場所は、その年度で使用不可にする。reference の振り分けの行の is_keep は、運び元と団体の使用場所から決める。
  - seed の admin・staff・viewer・団体代表には、シナリオの年度にだけロール・団体代表を付けてよい（cleanup で年度ごと消える）。seed の R8 の年度のロールと、未招待の outsider は変えない。ロール・招待・団体代表を変えるテストは、使い捨てのテストユーザー（seed と同じ形の auth.users と auth.identities）で行う。ログアウトを試すテストは、保存したセッション（storageState）を使わない。
  - ブラウザでは sessionStorage に年度を入れて、そのシナリオの年度を開く。
  - `pnpm e2e` は、並行のテスト（chromium）と、年度の作成・年度をまたぐ表の変更・通しの流れ（serial）を別の呼び出しで流し、片方が落ちてももう片方を流す。スクリーンショット・手での確かめのデータ作り・4G の測定は、環境変数のあるときだけ流す。
  - 画面からのサインアップとメールの変更は使わない（ローカルも Confirm email が有効）。この補助は e2e/ の中だけで、アプリとビルドには入らない（publishable キー以外の鍵も使わない）。
- **理由**：seed の R8 の年度を共有すると、並行のテストが互いのデータを変えて結果が揺れる。1日目を seed の R8 より前にすれば、既定の「今の年度」は R8 のままで、T04 のテストも変わらない。年度をまたぐ表は全年度で共有で、行を足すと振り分け中のすべての年度の版が上がる（批評の実験で確かめた）ので、テストの途中で足すと無関係なテストの保存・確定が conflict になり、計算の結果も先に走ったテストで変わる。seed のユーザーにシナリオの年度のロールを付けられないと、立場ごとの保存したセッションを使えず、テストが遅くなる。serial を並行のテストの依存にすると、1件の失敗で通しの流れが流れず、受け入れの結果が残らない。
- **反映先**：05「CI」の 4、SPEC.md「E2E の検証手順」。
- **チケット**：T09a（補助）、T09〜T14（使う）。
- **状態**：採用（T09a の PR #10 で実装し、T09〜T14 の E2E で使って、2026-10-30 に main にマージした）。

## D-42 通信の失敗の後の書き込みの扱い（2026-10-29、画面の設計 2.6、notes/T09a.md の 11・12）

- **決定**：応答が届かず保存されたか分からない（`isUnknownOutcome`：通信の失敗とタイムアウトだけ。コードつきで返った失敗は届いた失敗）とき、どの書き込みも自動では送り直さない。書き込みの種類で3つに分ける。
  - **(A) 数を絶対値で書く書き込み**（在庫の upsert、申請の submit_requests・申請一覧のセル・代理入力・締切後の修正・提出済みにする）：確かめるための状態を持たず、保存のたびに送る前に DB の行を読み直して `decideAbsoluteSave` で決める（入力と同じなら「保存されていました」、自分以外の人の変更があれば上書きするかを聞く、それ以外は送る）。
  - **(B1) 送り直しても DB が二重の書き込みを止める書き込み**（楽観ロックの更新と、一意のキーがある insert）：その場で1回だけ対象の行を読み直して `settleLockedWrite` で決める（saved・changed・not-saved・unread）。「確かめる」のボタンや押せなくした保存のボタンは持たない。
  - **(B2) 送り直すと二重になりうる書き込みと、ほかの RPC**（save_allocation_rows・save_auto_allocations・set_year_status・set_consent）：今までどおり版を読み直して確かめてから送り直す。
- **理由**：(A)・(B1) は同じ内容を2回送っても結果が同じか DB が止める。「分からない」状態を持ち回すと、読み直し・開き直し・下書きの組み合わせごとに穴が見つかり続けた（T10・T11・T09・T12・T13 のレビュー）。save_allocation_rows は insert に冪等の鍵がないので確かめる。
- **反映先**：04_screens_api.md「DB関数とブラウザ側の処理」、画面の設計 2.6（細部は notes/T09a.md の 11・12）。

- **状態**：採用（T09a〜T13 で実装し、2026-10-30 に main にマージした。D-31〜D-38 の状態と一緒に、マージの後の直し〔fix/review-followups〕で直した。D-32）。

## D-45 4G での表示の速さ（2026-10-29、2026-10-30 に直した。T14。00「性能と可用性」、画面の設計 7.7）

- **決定**：
  - 測り方：`pnpm e2e:perf`（CI では流さない）。Fast 4G 相当（下り 9 Mbps・上り 1.5 Mbps・遅延 170 ms）と CPU 4 倍で、/stock?room=・/request・/my をキャッシュなしで3回ずつ計り、中央値を notes/T14.md に記録する。配り方は E2E と同じ serve（HTTP/1.1）と、GitHub Pages に近い HTTP/2 の2つで計る。
  - 直したこと：立場の読み込みで accept_my_invitations と立場の読み取りを同時に送る（受け入れた招待があったときだけ読み直す。往復を1回減らす）。ルートのレイアウトで Supabase に preconnect する（本番の DNS・TCP・TLS を、JS を読み終える前に始める）。
  - 結果：このコンテナ（ほかの処理で負荷が高い）では、どの画面も中央値が 2 秒を超えた（notes/T14.md の表）。残りの原因は、JS を読み終えてから Supabase へ「立場 → 年度のデータ → 画面のデータ」と3回順に往復することと、CPU 4 倍での描画。
  - 最初に読む JS（gzip）は /stock 330.3 KB・/request 324.2 KB・/my 316.7 KB で、T09a の記録の 1.5 倍（394.8 KB）以内。ExcelJS と highs はこの3画面の最初の読み込みに入っていない。
  - 2026-10-30 の直し（feat/T14-speedup。notes/T14.md の「速さの改善（2026-10-30）」）：(1) 立場の読み込みで年度の行も読んでキャッシュに入れ、振り分けに関わらない画面（/stock・/request・/my）は画面のデータを年度の行と並行に読む（D-33 を改めた。/my は年度の行も毎回並行に読み直し、振り分けの行は読み直した年度の行が確定前なら使わない）。/request の使用場所の名前は groups に埋め込む。(2) 前に開いた年度・団体の id を利用者ごとに覚え、ページを開いたら立場と同時に画面のデータを読み始める（立場が届いて年度・団体が違えば捨てる。覚えた id がなければ立場が届いた時点で読み始める）。(3) 開いたときに送った Supabase への読み取りをパスごとに覚え、次に開いたときは `<head>` の async の script が JS より先に同じリクエストを送り、supabase-js が同じリクエスト・同じトークンの応答を受け取る。覚えたものは下書きと同じ扱いで消す。読める範囲は RLS のまま。記録と先送りは版を使わない画面（/stock・/request・/my。`EARLY_FETCH_PATHS`。許可リスト）だけで、振り分けに関わる画面（/・/allocation・/swaps）は記録も先送りもしない（スナップショットは版を読み終えてから残りを読む〔D-33〕。先送りすると版とデータが同時に読まれ、新しい版に古いデータを組み合わせた確定・保存が conflict にならずに通りうる）。先送りの応答は覚え終えたとき（立場が届いて 2 秒後）と、SPA の画面移動でパスが変わったときにも捨てる。(4) 測り方を、ページの中で表示された最初のフレームの時刻にした（Playwright の expect の再試行の間隔のぶん遅く出ていた）。first（覚えたものがない）と again（前に開いた）を分けて計る。
  - 結果（中央値。Fast 4G・CPU 4 倍、load average 1.8〜2.7、main と交互に2回ずつ）：main 2.16〜2.43 秒 → first 1.66〜1.93 秒・again 1.50〜1.81 秒。3 画面とも http1・h2 で 2 秒を切った。最初に読む JS は /stock 333.8 KB・/request 328.2 KB・/my 319.7 KB（1.5 倍の 394.8 KB 以内。ExcelJS・highs なし）。
