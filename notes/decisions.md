## D-08 最小変更モードの受け入れ基準（2026-10-28、K-04）

- **決定**：基準を条件つきに直す。「使用不可にした部屋から運んでいた品目に、ほかの場所の余りが足りるなら、その部屋と無関係な行は変わらない。足りないときは、変わった行の数を記録する」。「変わった行」は、（運び元・団体・申請品目・品目）ごとの数が変わったものと定義する（行の id は比べない）。
- **補足（T06 の設計、2026-10-29）**：「余りが足りる」は品目全体の余りではなく、「使用不可にした部屋 M から受け取っていた（団体・申請品目）の失った分を、前回のほかの行を変えずに、その団体がルール上使える場所の余りから、代替の重さの合計を増やさずに補える」ことを意味する（運び元の制限 S05 などで、品目全体に余りがあっても成り立たない反例がある。notes/T06-design/logic-design.md 6.3）。そのとき成り立つのは、「前回の M 以外の行は減らず、増えるのは M から受け取っていた（団体・申請品目）の行だけで、M と無関係な行は変わらない（同じキーで同じ数）」。判定は候補でつながる申請品目のまとまりごとに行う（03「目的関数」、05「不変条件」）。
- **これに伴うこと**：05 の不変条件のテストは、第一セミナーを使用可にして1回解く → 使用不可にする → 最小変更で解く、の手順で行う（R8 の fixtures では第一セミナーが最初から使用不可のため）。SPEC の E2E 手順7（MER）も同じ基準にそろえる。
- **反映先**：SPEC.md「受け入れ基準」「E2E の検証手順」7、05_development.md「不変条件」。
- **チケット**：T06、T14。
- **状態**：T06 の PR（feat/T06-allocator）で 03「目的関数」、05「不変条件」、SPEC「受け入れ基準」「E2E の検証手順」7 に反映済み。

## D-20 W107 の定義（2026-10-29、T00「03 の直すべき点」4、T06 の設計 12.4・15 章の1）

- **決定**：W107 は、団体 g の使用場所 L から品目 j が外（使用場所が L でない団体 h）へ出ているのに g が L 以外の場所 r から同じ j を受け取っている組み合わせのうち、(1) 入れ替え（g が L の j を使い、h が r の j を使う）がルール（代替の区分・了承・運び元の制限・使用不可）の上でき、(2) 入れ替えても運ぶ距離の合計が増えない（d(r,h) ≤ d(r,g) ＋ d(L,h)）ものが1つでもあるときだけ出す。05 の不変条件「W107 が0件」はこの定義で満たす。
- **理由**：T00 のダミーで出た W107 はすべて S05（設営は体育館の机を使えない）によるもので、入れ替えるとルール違反になり管理者が直せない。距離の条件がないと、distance_overrides が三角不等式を崩すときに直しようのない W107 が出る。この定義なら、全体の実行の最適解には（距離の上書きがあっても）W107 は出ず、出るのは最小変更モードで前回の行を保った場合と手で決めた行だけになる。
- **反映先**：03「検証コード一覧」W107、01 固定ルール5、05 不変条件、SPEC 受け入れ基準。
- **チケット**：T06（findW107）、T07（Issue にする）。
- **状態**：T06 の PR（feat/T06-allocator）で要件定義に反映済み。

## D-24 コストの整数化と辞書式の優先順位（2026-10-29、P-02・K-12、T06 の設計 6 章）

- **決定**：P-02 を形を変えて採用する。目的関数の係数をすべて整数にし、①代替の重さ → ②（最小変更モードの）前回と同じ台数 → ③距離 → ④休憩所への不可椅子 → ⑤運び出す台数（e：使用場所以外からなら 1）の辞書式の最小を、1回の LP で求める。倍率は固定の 100・−10 ではなく、LP の需要の行の数 K と、休憩所への不可椅子の変数を持つ行の数 P、距離の最大 d_max から決める（B = K+1、A = B·P+K+1、U = A·d_max+B+1、μ = K·U+1、W = K·(U+μ)+1）。最小変更の割引 μ も辞書式にする（前回の1台を守ることを、どれだけ距離を縮めることよりも優先する）。
- **理由**：固定の倍率は休憩所の需要の行が10以上、または閉路が100を超える需要の点を通ると距離の段が崩れる。1台ぶんの μ（d_max + 1）では前回の1台を手放して距離を縮める解が選ばれうる（小さな入力の総当たりで3例）。K から決めた倍率なら、2つの解の差を閉路と道に分けたときに、上の段の差1を下の段の合計が覆せない。R8 規模でも最大の係数は約 3.3×10⁸ で、HiGHS は整数の解を同じ時間で返す。
- **反映先**：03「目的関数」。
- **チケット**：T06（weights.ts）。
- **状態**：T06 の PR で要件定義に反映済み。

## D-25 前処理で止めるもの（2026-10-29、K-13、T06 の設計 5 章・9 章）

- **決定**：allocate が前処理で止める（reason ＝ precheck）のは、固定行と残すの行で在庫を超える E001 と、残すのルールの部屋が使用不可（E002）・使用場所でない（E005）だけ。申請できない品目の申請（E006）は需要から除いて計算を続け（stats.excludedRequests に件数）、固定行の E002・E004・E005 でも止めない。どれも validate が error として示し、直すまで確定できない。ok: false は reason（invalid_input・precheck・infeasible・solver_error）と inputErrors・issues・shortages・causes を持つ1つの形にする。
- **理由**：allocate は自分が作る行（計算した行と残すの行）に error を出さないことだけを守る。E006 で止めると、品目や団体の区分を後から変えたときに自動振り分けが一切動かなくなる。どちらでも error は確定を止めるので、業務の判断は変わらない。
- **反映先**：03「入力と出力」、前処理、「解けないときの扱い」。
- **チケット**：T06、T07、T13（reason ごとの表示）。
- **状態**：T06 の PR で要件定義に反映済み。

## D-29 CSV で取り込んだ団体の提出日時（2026-10-29、K-27、T06 の設計 3.7・16 章）

- **決定**：Googleフォームの回答を取り込んだ団体の提出日時（request_submissions.submitted_at）は、フォームのタイムスタンプ（同じ団体の最後の回答）にする。DB の対応（update_requests_after_deadline に submittedAt を足し、そのときだけトリガーが値を置き換えない）は DB 設計に申し送る。fixtures/r8 では、総務が代理入力した団体は R8 の申請締切の日時、未提出の団体は空にする。
