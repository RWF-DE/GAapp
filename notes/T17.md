## ユーザーの決定（承認した計画。D-53）

1. **宛先**（列挙 notice_audience）：soumu（総務内。総務のロールだけ）、all_groups（全団体）、groups（指定の団体。同じ年度の団体を1つ以上、notice_groups に並べる）。
2. **表**：notices（id・year_id・audience・title〔前後の空白を除いて 1〜100 字、空白だけは不可〕・body〔4000 字まで、空でもよい〕・pinned〔既定 false〕・created_by／created_at・updated_by／updated_at〔DB が入れる〕・unique (id, year_id)）、notice_groups（notice_id・year_id・group_id、主キー (notice_id, group_id)、複合外部キーで同じ年度、お知らせを消すと消える）。year_id は check_immutable、監査（tg_audit）は両方。
3. **読める人**：総務（admin・head・deputy_head・staff）はその年度の全部（お知らせと宛先の団体）。店長・副店長は、代表である年度の全団体あてと、自分の団体を宛先に含む指定の団体あて。宛先の団体の行は自分の団体の分だけ（ほかにどの団体へ出したかは見せない）。閲覧のみは、その年度の団体あて（全団体・指定の団体）とその宛先の団体の行。総務内は読めない。ほかの人は何も読めない。集合の関数で書く（D-47）。
4. **書き込み**（RPC だけ。表に insert・update・delete の権限を与えない）：save_notice（作る・直す）と delete_notice（消す）。終了した年度は読むだけ。総務内は総務、全団体・指定の団体は部門長以上、ピン留めは部門長以上、直す・消すのは書いた人か部門長以上。楽観ロック（updated_at）。理由を置く。
5. **エラー**：04 のコード（forbidden・not_found・invalid_input〔field〕・conflict・invalid_state）。not_found と forbidden で、読めないお知らせの有無を漏らさない。
6. **v1 で作らないもの**：既読、添付、予約の公開、メール・プッシュの通知。

## SQL の約束（0014_notices.sql）

### 列挙型と表

```sql
create type public.notice_audience as enum ('soumu', 'all_groups', 'groups');

create table public.notices (
  id uuid primary key default gen_random_uuid(),
  year_id uuid not null references public.years on delete cascade,
  audience public.notice_audience not null,
  title text not null,
  body text,                                   -- 任意。空白だけなら null（RPC が直す）
  pinned boolean not null default false,
  created_by uuid references auth.users on delete set null,
  updated_by uuid references auth.users on delete set null,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  constraint notices_title_check check (title <> ''
    and title = btrim(title, E'\t\n\u000b\f\r \u00a0\u1680\u2000\u2001\u2002\u2003\u2004\u2005\u2006\u2007\u2008\u2009\u200a\u2028\u2029\u202f\u205f\u3000\ufeff')
    and length(title) <= 100),
  constraint notices_body_check check (length(body) <= 4000),
  constraint notices_id_year_id_key unique (id, year_id)
);
create index notices_year_id_idx on public.notices (year_id, created_at desc);

create table public.notice_groups (
  notice_id uuid not null,
  year_id uuid not null,
  group_id uuid not null,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  primary key (notice_id, group_id),
  constraint notice_groups_notice_fkey foreign key (notice_id, year_id)
    references public.notices (id, year_id) on delete cascade,
  constraint notice_groups_group_fkey foreign key (group_id, year_id)
    references public.groups (id, year_id) on delete cascade
);
create index notice_groups_group_id_idx on public.notice_groups (group_id);
```

- 外部キーの on delete は 02 の決まりのとおり：年度・団体・お知らせへは cascade、記録のためのユーザー（created_by・updated_by）は set null。年度を消すと、お知らせ（と宛先の団体）も消える。団体を消すと宛先の団体の行だけが消え、お知らせは残る。
- 題名を除く空白は、JavaScript の String.prototype.trim が除く 25 文字（タブ・LF・垂直タブ・改ページ・CR・半角の空白・U+00A0・U+1680・U+2000〜U+200A・U+2028・U+2029・U+202F・U+205F・全角の空白 U+3000・U+FEFF。Node 22 で U+0000〜U+10FFFF の全部の文字に trim を当てて数えた）。画面の zod の trim と同じ文字にそろえ、画面を通さずに RPC を呼んでも、画面が空とみなす題名（空白に見える文字だけの題名）は入らない（レビューの T17A-1 で、半角の空白・タブ・LF・CR・全角の空白の5文字から広げた）。save_notice の c_space と CHECK は同じ文字。CHECK は「除いた形であること」も確かめる（SQL Editor から前後に空白のある題名を入れさせない）。
- 索引：notices は年度ごとの一覧とポリシーの `year_id in (…)` 用に (year_id, created_at desc)。notice_groups は主キー（notice_id が先頭）で、お知らせからの引きと連鎖削除が引ける。団体からの引き（集合の関数 my_group_notice_ids と、団体の連鎖削除）のために (group_id)。

### トリガー

| 表 | トリガー（BEFORE ROW は名前の順に動く） | 関数 | 中身 |
| --- | --- | --- | --- |
| notices | check_groups（before update of audience） | private.tg_notices_check_groups()（DEFINER） | 宛先を groups 以外にするとき、宛先の団体の行が残っていれば invalid_input（field: group_ids, reason: not_allowed） |
| notices | check_immutable（before update of year_id） | private.tg_immutable_columns('year_id')（0002） | year_id を変えると invalid_input（column: year_id, reason: immutable） |
| notices | set_actor（before insert or update） | private.tg_notices_set_actor()（INVOKER） | auth.uid() があれば、insert で created_by、いつも updated_by を auth.uid() にする。update では created_by を元の値に戻す。auth.uid() が null（seed・SQL Editor）なら入れた値のまま（D-10 と同じ） |
| notices | set_timestamps | private.tg_set_timestamps()（0002） | created_at・updated_at |
| notices | audit（after） | private.tg_audit('id')（0002） | 監査。year_id は行から、group_id は null |

| notice_groups | set_timestamps・audit | 0002 の関数 | 監査の row_pk は (notice_id, group_id)、group_id は宛先の団体、year_id は行から |

- check_audience・check_groups は「宛先の団体の行は、宛先が groups のお知らせにだけある」を守る（他の表を参照する CHECK は使わない決まり）。RLS（閲覧のみと店長・副店長の notice_groups の枝）はこれを前提にする。RPC は、groups から宛先を変えるときは先に行を消してからお知らせを直し、groups に変えるときはお知らせを直してから行を足す。
- check_audience がお知らせの行を for share で読むのは、宛先を変える同時の書き込み（SQL Editor など）と順に処理するため（宛先の update は for no key update の行ロックを取るので、for share と順になる）。RPC の中では、お知らせの行をもう持っている（直すときは for update、作るときは自分で入れた行）。
- 確定中・終了の守りのトリガー（lock_year_guard）と版の増分のトリガーは付けない（お知らせは振り分けの入力でない。終了の年度の読み取り専用は RPC が守る）。

### 読み取り（RLS。D-47 の形）

```sql
create function private.my_group_year_ids() returns setof uuid   -- 自分が団体の代表である年度
  language sql stable security definer set search_path = '' as $$
  select g.year_id from public.group_members gm join public.groups g on g.id = gm.group_id
  where gm.user_id = (select auth.uid()) $$;
create function private.my_group_notice_ids() returns setof uuid -- 自分が代表の団体を宛先の団体に含むお知らせ
  language sql stable security definer set search_path = '' as $$
  select ng.notice_id from public.notice_groups ng join public.group_members gm on gm.group_id = ng.group_id
  where gm.user_id = (select auth.uid()) $$;

create policy notices_select on public.notices for select to authenticated
  using (year_id in (select private.my_role_year_ids('{admin,head,deputy_head,staff}'))
         or (audience in ('all_groups', 'groups') and year_id in (select private.my_role_year_ids('{viewer}')))
         or (audience = 'all_groups' and year_id in (select private.my_group_year_ids()))
         or (audience = 'groups' and id in (select private.my_group_notice_ids())));

create policy notice_groups_select on public.notice_groups for select to authenticated
  using (year_id in (select private.my_role_year_ids('{admin,head,deputy_head,staff,viewer}'))
         or group_id in (select private.my_group_ids()));
```

- notices のポリシーから宛先の団体を読むので、RLS を通らない DEFINER の関数（my_group_notice_ids）で読む（ポリシーの中で RLS のある表を読み合うと再帰する。CLAUDE.md の落とし穴）。
- 宛先で分ける枝は宛先を名前で並べる（`audience in ('all_groups', 'groups')`。`<> 'soumu'` にしない）。宛先の種類を足しても、閲覧のみ・店長・副店長に黙って見えるようにならない。
- 店長・副店長の「指定の団体あて」の枝は audience = 'groups' も見る（宛先の団体の行が何かの間違いで総務内のお知らせに付いても、総務内は読めない。トリガーでそもそも付かない）。
- 閲覧のみの notice_groups の枝はその年度の全部（行は団体あてのお知らせにしかない。check_audience・check_groups）。店長・副店長は自分の団体の行だけ。
- 読み取りは年度の状態によらない（終了の年度も読める）。

### 書き込み（RPC）

**save_notice(p_year_id uuid, p_audience notice_audience, p_title text, p_body text default null, p_pinned boolean default false, p_group_ids uuid[] default '{}', p_notice_id uuid default null, p_base_updated_at timestamptz default null) returns notices**

エラーの順番（pgTAP はこの順で確かめる）：

1. `lock_year(p_year_id, '{preparing,requesting,allocating,confirmed}', '{admin,head,deputy_head,staff}')`：その年度の総務でない・年度がない → forbidden、終了 → invalid_state
2. 入力（invalid_input）：
   - audience が null → `{field: audience}`
   - 題名（前後の空白を除いた後）が null・空・101 字以上 → `{field: title}`
   - 本文（空白だけなら null にした後）が 4001 字以上 → `{field: body}`
   - pinned が null → `{field: pinned}`
   - 宛先が groups：団体が 0 → `{field: group_ids, reason: required}`、1001 以上 → `too_many`（unnest の前に数で見る）、null か重複 → `invalid`、その年度にない団体 → `not_in_year`。ほかの宛先で団体がある → `not_allowed`。p_group_ids が null は空とみなす
   - p_notice_id と p_base_updated_at の片方だけ（作るときに版を渡した、直すときに版がない）→ `{field: base_updated_at}`
3. 段：宛先が all_groups・groups で、部門長以上（`private.has_any_role(p_year_id, '{admin,head,deputy_head}')`）でない → forbidden
4. 作るとき：pinned が true で部門長以上でない → forbidden。理由「お知らせ」を置いて insert
5. 直すとき：`select … from notices where id = p_notice_id and year_id = p_year_id for update`。なければ not_found（呼んだ人はその年度の総務で、その年度のお知らせを全部読める。ほかの年度のお知らせも、ないお知らせも同じ not_found なので有無を漏らさない）
6. 書いた人（created_by = auth.uid()）でも部門長以上でもない → forbidden
7. pinned を変える（p_pinned と今の値が違う）のに部門長以上でない → forbidden
8. `date_trunc('milliseconds', updated_at)` と `date_trunc('milliseconds', p_base_updated_at)` が違う → conflict（`{id}`）
9. 理由「お知らせの更新」を置き、宛先から外す団体の行を消し（groups 以外の宛先なら全部）、お知らせを update する（何も変わらなくても書く）
10. 新しく宛先に足す団体の行を insert（`on conflict do nothing`。今ある行はそのまま）。返り値は insert・update の returning の行

- 例外の直し（D-19）：外部キーの違反（確かめた後に団体が消えた）→ invalid_input `{field: group_ids, reason: not_in_year}`、CHECK の違反 → invalid_input（notices_title_check は title、notices_body_check は body、ほかは notice）、クラス 22 → invalid_input `{field: notice}`。トップレベルの型つきの引数（uuid・enum・uuid[]・timestamptz）の形の誤りは、PostgREST が関数の前に 22P02 などで返す（今までどおり）。
- 段の確かめに使う部門長以上は、ロックの後に1回だけ読む（lock_year がロックの後にもう一度ロールを確かめた後なので、待っている間の変更も見える）。

**delete_notice(p_notice_id uuid, p_base_updated_at timestamptz) returns void**

1. お知らせの年度（`select year_id from notices where id = p_notice_id`。RLS を通らない）で lock_year（4つの状態、総務）：お知らせがない・その年度の総務でない → forbidden（revoke_invitation と同じく有無を漏らさない）、終了 → invalid_state
2. p_base_updated_at が null → invalid_input `{field: base_updated_at}`
3. `select … for update`：ロックを待つ間に消えた → not_found（その年度の総務なので、読めたお知らせ）
4. 書いた人でも部門長以上でもない → forbidden
5. 楽観ロック → conflict（`{id}`）
6. 理由「お知らせの削除」を置いて消す（宛先の団体の行は外部キーで消え、監査の理由も同じ）

### 権限

- 表：`revoke all on table notices, notice_groups from public, anon, authenticated` の後に `grant select … to authenticated` だけ（RPC でだけ書く表。02）。
- 集合の関数 my_group_year_ids・my_group_notice_ids：`revoke all … from public, anon`、`grant execute … to authenticated`（ポリシーの判定関数。authenticated が実行できる private の関数は 17 → 19 個）。
- トリガー関数3つ（tg_notices_set_actor・tg_notice_groups_check_audience・tg_notices_check_groups）：`revoke all … from public, anon, authenticated`（誰も実行できない）。最後に `revoke all on all functions in schema private from public`。
- RPC：0005 と同じ繰り返しで `revoke all … from public, anon`、`grant execute … to authenticated`（authenticated が実行できる public の関数は 18 → 20 個）。どちらも SECURITY DEFINER・`search_path = ''`。
- 関数の本体とポリシーの式の head・deputy_head は組で出てくる（010 の段の書き漏れの守り）。

### ロックの順と同時実行

- save_notice・delete_notice：年度の行（lock_year。for no key update）→ お知らせの行（for update）→ notice_groups の行。同じ年度のお知らせの書き込みは年度の行で順に処理される（ほかの書き込みの RPC と同じ）。招待・ロールのロック（勧告的ロック）には触れない。
- notice_groups の insert の外部キーの確かめは、団体の行に for key share を取る。管理者が同じ団体を同時に消すと（団体の行をロックしてから、守りのトリガー lock_year_guard が年度の行を待つ）、save_notice（年度の行を持ったまま団体の行を待つ）とデッドロックし得る（40P01。片方が失敗するだけ）。save_allocation_rows（allocations の団体への外部キー）と同じ形で、今までどおり受け入れる（画面は「ほかの人の保存と重なりました」）。
- 読み取りはロックを取らない。

## 判断したこと（計画にないもの・計画の読み方）

1. **引数の並び**：計画の `save_notice(p_year_id, p_notice_id default null, p_audience, p_title, p_body, p_pinned default false, p_group_ids default '{}', p_base_updated_at default null)` は、既定値のある引数（p_notice_id）の後に既定値のない引数があり、PostgreSQL では作れない（「input parameters after one with a default value must also have defaults」）。要る引数（p_year_id・p_audience・p_title）を先に、任意の引数（p_body・p_pinned・p_group_ids・p_notice_id・p_base_updated_at）を後にした。PostgREST（supabase-js）は名前で呼ぶので、呼び方は計画のまま。p_body は既定値 null（空でよい本文）にした（要る引数にすると p_title の後に置くしかなく、どちらでも同じなので、作るときに省けるほうにした）。直すときは全部の欄を置き換えるので、画面は今の値も含めて全部を送る（省くと本文は空、ピン留めは外す扱いになる。ピン留めを外すのは部門長以上なので、総務部門員が省くと forbidden）。
2. **ピン留めの規則の読み方**：計画の「pinned=true は部門長以上」を、「ピン留めを付ける・外す（作るときに付けるのを含む）のは部門長以上」とした。文字どおり（p_pinned が true なら部門長以上）だと、部門長以上がピン留めした総務部門員のお知らせを、書いた本人が直すには外すしかなく（外すのは段の外の変更）、直せない。今の値のまま（true のまま）なら書いた人も直せる。ピン留めの状態を決めるのはいつも部門長以上（「確認したいこと」の 1）。
3. **本文の空**：空白だけの本文は null で入れる（D-33 の任意の文字列と同じ。生成した型は `string | null`）。本文の前後の空白は除かない（行頭の字下げや改行をそのまま残す）。題名は前後の空白を除く（決定のとおり）。
4. **題名の空白**：画面の zod の trim（JavaScript の trim）と同じ 25 文字（全角の空白・タブ・改行・U+00A0 など）を除く（上の「列挙型と表」。最初は5文字で、レビューの T17A-1 で広げた）。
5. **宛先の団体の不変条件**：「宛先の団体の行は、宛先が groups のお知らせにだけある」をトリガー（check_audience・check_groups）で守る（計画にない。RPC だけなら守られるが、SQL Editor からの書き込みで崩れると、閲覧のみと店長・副店長の notice_groups の読み取りが、総務内・全団体のお知らせの id と団体を見せてしまうため）。
6. **notice_groups の鍵の列**：計画は year_id の check_immutable。notice_groups は鍵の列（notice_id・year_id・group_id）を全部変えられないようにした（D-16 の「団体を主キーに含む表の group_id」と同じ考え。行は足すか消すだけ）。
7. **宛先の団体の入れ替え**：差分で入れ替える（外す団体の行を消し、足す団体の行を入れる。変わらない団体の行は触らない）。全部を消して入れ直すと、変わらない団体の消す・入れるが監査に出るため。「1回で入れ替える」は同じトランザクションの中で行うことで満たす。
8. **何も変わらなくても書く**：直すときは、中身が同じでも update して updated_at を進める（お知らせと宛先の団体を1つの版で守る。宛先の団体だけを変えたときも、ほかの人の読んだ版は conflict になる）。監査は updated_at だけの変更を記録しない（ほかの人が同じ中身で保存すると updated_by の変更として残る）。
9. **削除の理由**：「お知らせの削除」（計画は削除の理由の文を決めていない）。
10. **まず総務であること**：書き込みは、宛先によらず最初にその年度の総務（admin・head・deputy_head・staff）であることを確かめる（lock_year）。ロールを外された人（閲覧のみに変えられた人を含む）は、自分が書いたお知らせも直せず消せない（計画の「書いた人か部門長以上」は、その年度の総務であることを前提にした）。
11. **直すときの元の宛先は見ない**：計画のとおり「直した後の宛先」の段だけを見る。部門長以上だった人が出した全団体あてのお知らせを、その人が総務部門員になった後で総務内に変えることはできる（書いた人は消すこともできる〔delete_notice は書いた人か部門長以上〕ので、取り下げる道は元からある）。全団体あてのまま直すのは部門長以上だけ。
12. **入力の誤りを段の forbidden より先に**：invite・update_year と同じ（入力の形 → 段）。総務はその年度の団体を全部読めるので、団体の誤り（not_in_year）を先に返しても漏れはない。
13. **作るときの版**：作るときに p_base_updated_at を渡すと invalid_input（呼ぶ側の誤りを早く見つける）。
14. **detail**：invalid_input の group_ids には reason（required・not_allowed・too_many・invalid・not_in_year）を付けた（画面がそれぞれの文を出せるように）。forbidden には detail を付けない（ほかの RPC と同じ。画面は自分の段と書いた人から理由を出せる）。conflict は `{id}`（save_allocation_rows と同じ）。
15. **件数の上限は持たない**：1件の大きさ（題名 100 字・本文 4000 字・宛先の団体 1000）だけを抑える。書けるのは招待した総務だけで、在庫の数え直し・申請の出し直しと同じく、書き込みの回数も抑えない。
16. **書いた人の id**：店長・副店長と閲覧のみにも created_by・updated_by（uuid）が見える（RLS は列を制限できない）。名前（profiles）は読めない（can_see_profile）。画面は店長・副店長に書いた人を出さない（後半）。
17. **作るときの冪等の鍵はない**：応答が届かなかったら一覧を読み直して確かめる（04 の (B2)）。直す・消すは楽観ロックなので (B1)。04 の通信の失敗の項に足した。

**読み直しの決まり**（2.6 の (B1)・(B2)。画面の設計）

- 編集（(B1)）：応答が届かない（isUnknownOutcome）か、conflict・not_found で止められた（isLockRejection）ときは、`settleLockedWrite({ reread: () => readNotice(id), matches: (r) => sameNoticeWrite(r, w), baseVersion: 読んだときの updated_at, versionOf: (r) => r.updated_at })`。
  - saved：成功と同じ（「保存されていました」と閉じて読み直す）。
  - changed で行がある：入力の元を読み直した行にし（次の保存は読み直した updated_at で送る）、`notice-conflict` に「ほかの人がこのお知らせを先に変えました。読み直しました。入力は残してあります。確かめてから、もう一度「保存」を押してください（押すと、この入力で上書きします）」と、読み直した今の題名と更新の日時（「今の題名：…」「更新：…」）を出す。一覧も読み直す。
  - changed で行がない（消えた）：`notice-missing` に「このお知らせは見つかりません（ほかの人が削除した可能性があります）」。「保存」を押せなくする（入力は残すので、写してから閉じられる）。一覧を読み直す。
  - not-saved：応答が届かなかったときは `unknown-outcome` に unknownOutcomeMessage()（「保存できたか分かりません。もう一度「保存」を押すと、確かめてから送ります」）。止められたときは changed と同じ扱い。
  - unread：入力を残し、読み直せなかったことを出す（「読み直しました」と言わない。「読み直す」のボタン）。
  - 総務部門員の次の保存は、読み直した行の宛先とピン留めで送る（上の 4 のピン留めの行）。読み直した行を今の段で直せなければ（canEditNoticeByTier が偽。宛先が総務内でなくなった）、`notice-conflict` の代わりに `notice-not-editable` に「ほかの人がこのお知らせを先に変えました。読み直しました。総務部門員が編集できるのは、自分が書いた総務内のお知らせだけなので、このお知らせは保存できません。入力は残してあります。必要なら写してから閉じてください」と、今の題名・宛先・更新の日時（「今の題名：…」「今の宛先：…」「更新：…」）を出し、「保存」を押せなくする（黙って総務内に戻さない。レビューの T17-R1）。
- 編集で forbidden（レビューの T17-R1 で足した）：save_notice はピン留めを変える確かめ（forbidden）を楽観ロック（conflict）より先に行うので、部門長以上が間にピン留めを付け外ししたお知らせを総務部門員が開いたときのピン留めで保存すると forbidden になる。readNotice で1回読み直し、行があって版が読んだときと違えば、中身が入力と同じなら saved（「保存されていました」）、違えば conflict（上の changed で行があるときと同じ。読み直した行を入力の元にする）。版が同じ・行がない・読み直せないときは failed（下の forbidden の扱い。総務のまま消えたお知らせなら save_notice は not_found を返すので、行がないのは総務でなくなって読めないとき）。
- 削除（(B1)）：応答が届かない・conflict・forbidden（delete_notice は、ないお知らせにも forbidden を返す）のときは readNotice で読み直す。ない → 削除できた（応答が届かなかったとき「「{題名}」を削除しました」）か、すでに消えていた（forbidden・conflict のとき「すでに削除されていました（ほかの人が削除した可能性があります）」。ただし、同じ確かめのダイアログで前の削除が消せたか分からずに終わった〔`notice-delete-error` が出ている〕後なら「「{題名}」は削除されていました」。前の削除が通っていた可能性があるので、ほかの人とは言わない。レビューの T17-R2）。あって版が同じ → 応答が届かなかったときは unknownOutcomeMessage('削除')、forbidden なら今の forbidden の扱い。あって版が違う → 「ほかの人がこのお知らせを先に変えました。読み直しました。内容を確かめてから、もう一度削除してください」。どれも一覧を読み直す。
- 出す（(B2)。冪等の鍵がない）：応答が届かないときは findCreatedNotice（自分が出したその年度のお知らせを created_at の新しい順に 20 件読み、ダイアログを開いたときの一覧の id〔knownIds〕にないもので sameNoticeWrite のもの）。あれば「お知らせ「{題名}」は出されていました」と閉じる。なければ入力を残し、もう一度「出す」を押せる。読み直せなければ `unknown-outcome` に「出せたか確かめられません。通信が戻ったら「確かめる」を押してください」と出し、確かめるまで「出す」の代わりに「確かめる」（findCreatedNotice をもう一度）を出す（(B2) だけが持つ状態）。
- forbidden・invalid_state（effectOf が 'year'）：年度の行と立場を読み直す（入力と開いているダイアログは残す）。書けなくなれば、ダイアログの送るボタンを押せなくし、一覧の操作を消す。
- invalid_input の not_in_year：団体（一覧のクエリ）を読み直し、入力は残す。
- deadlock（40P01）：今の文言（「ほかの人の保存と重なりました。もう一度保存してください」）。読み直さず、入力を残す。

1. **ナビの項目と h1 は「お知らせ一覧」**：見出し「お知らせ」の下に同じ「お知らせ」を並べないため（T16 は「ホーム」の見出しを見た目で隠したが、お知らせの見出しを隠すと項目が机椅子の見出しの続きに見える）。在庫一覧・申請一覧と同じ言い方。AppNav を変えない。カードの失敗の「{入口の画面}へ」も「お知らせ一覧へ」になる。
2. **欄の型の足し方**：PortalWidgetId に欄を2つ、PortalSection に任意の notices を足した（汎用の「新着の欄」の型にはしない。T18〜T21 に同じ形の欄が要るかが分からず、今決めると型が先走るため）。T16 の型を変えるので、04「ダッシュボード」と D-52 を先に直した（D-52 の決まり）。並行の機能のチケット（T18）に知らせる。
3. **要対応とカードを作らない**：既読を持たない（v1）ので「読んでいないお知らせ」が決められず、要対応にならない。カードは欄と同じものの数になるだけで、数えるには読み取りがもう1つ要る。
4. **欄は本文を読まない**：id・宛先・題名・ピン留め・出した日時だけ（4G の / を軽くする。本文は一覧で読む）。
5. **総務部門員の「編集」は自分が書いた総務内のお知らせだけ**（DB は、自分が書いた団体あてを総務内に変えて直すことも許す。リードの答えの 2）：総務部門員のダイアログは宛先を選べないので、団体あてを開くと保存で黙って総務内に変わる。画面では出さず、削除は出す（画面は DB より狭く出してよい）。
6. **書いた人は総務にだけ出す**：閲覧のみ・店長・副店長は profiles を読めない（02 の権限表）。id を出しても意味がないので、何も出さない（前半の判断 16）。
7. **宛先の団体の名前は、読めた行の分を誰にでも出す**（リードの「総務には団体の名前も」を、RLS で読める範囲に広げた）：閲覧のみはその年度の宛先の団体を全部読める（D-53）ので、隠す理由がない。店長・副店長は自団体の行しか読めないので、自団体の名前だけが出て、ほかにどの団体へ出したかは出ない。PR でリードに見てもらう（後半で決められなかったことの 1）。
8. **`?notice=<id>` で目立たせる**：ダッシュボードの欄の1件から、その1件を一覧で開くため（画面の中の切り替えをクエリ文字列に入れる 04 の決まり）。絞り込みより優先する。
9. **ダイアログの入力を下書きに置く**：04 の決まり（保存していない入力はブラウザに下書き。UnsavedChangesGuard の文言も「下書きに残り」）。本文は 4000 字まであり、スマホのタブの破棄で失いやすい。直すときは読んだときの updated_at も置き、戻した下書きで黙って上書きしない（DB の conflict に任せる）。
10. **字数はコードポイントで数える**：DB の length（文字の数）と同じにする（JavaScript の length は絵文字などを 2 と数え、DB より狭くなる）。

18. **更新の表示**：updated_at が created_at より後なら「（{日時} に更新）」（中身を変えない保存でも updated_at は進む〔前半の判断 8〕ので、保存すれば「更新」が出る）。

20. **一覧の表の並びは lg から**（実装で直した。04 と「後半の約束」3 は md と書いていた）：md（768〜1023px）では左のナビ（w-56）と余白の分だけ本文の幅が 500px ほどで、宛先・書いた人と日時・操作の列（合わせて 27rem ほど）を並べると、題名と本文の列がほとんど残らない。md ではスマホと同じ1件ずつのカードにする。T16 のダッシュボードの欄（要対応と締切と予定の横並び）を md から lg に直したのと同じ理由。04 と「後半の約束」3 を直した。
21. **RPC の引数の zod の小さなモジュール**（実装で足した。lib/schemas/notice-fields.ts）：RPC_ARGS（lib/rpc/payloads.ts）は申請・自団体の振り分けの画面の JS にも入るので、上限・字数の数え方・題名の zod だけを分け、ダイアログの入力の形（noticeFormSchema・checkNoticeForm・toSaveNoticeArgs）は lib/schemas/notices.ts に置いた（同じ名前で出し直す）。/request・/my の最初に読む JS にお知らせのダイアログの入力の形を入れない。
22. **削除の失敗の出し方**：確かめのダイアログ（ConfirmDialog）は、消せたか分からないとき（応答が届かず、読み直すと版が同じ・読み直せない）だけ開いたまま中に知らせる（`notice-delete-error`。もう一度「削除する」を押すと送る）。ほかは閉じて toast（「すでに削除されていました（…）」は info、版が違う〔「ほかの人がこのお知らせを先に変えました。…もう一度削除してください」〕・forbidden などは error）。
23. **出す（(B2)）で出されていなかったとき**：通信の失敗の帯（ErrorBanner。「通信できませんでした。電波の良い所でもう一度」）を出し、「出す」は押せるまま（04 の「なければ入力を残し、もう一度「出す」を押せる」）。
24. **下書きを戻すか決めるまでは上書きしない**（振り分けの未保存の変更と同じ）：開いたときに下書きがあれば DraftNotice（戻す・捨てる）を出し、決めるまで入力を下書きに書かない。開いたときの値に戻したら下書きを消す。保存できた・捨てて閉じたら消す。

### この段で決めたこと（変えるならこの記録を直す）

1. **お知らせは SQL で入れ、並びは入れる順で決める**：出した日時は日時のトリガー（set_timestamps）が DB の now() にするので、E2E では1件ずつ別のトランザクションで古いものから入れる（トリガーを止めない。並行のテストのお知らせの読み書きを止めないため）。撮影だけは日時をこの数日の間にばらけさせるため、backdateNotices が同じトランザクションの中でだけトリガーを止めて書き、すぐ戻す（表のロックを取る。shots は1つずつ流れるので、ほかのテストとは重ならない）。
2. **使い捨てのユーザーで画面からログインするコンテキストは空の storageState で作る**：`browser.newContext()` は describe の `test.use({ storageState })` を引き継ぐ（T15b と同じ）。1回目の流しでこれを忘れ、店長のテストの B の店長が seed の店長のままログインのフォームが出ず、30 秒で時間切れになった（テストの書き方。アプリは変えていない）。直した後は通る。
3. **欄の失敗は `route.abort()`**（T16 と同じ。supabase-js と TanStack Query の読み直しの後に出るので 15 秒ほど。テストは 120 秒）。
4. **撮影だけ1日目を今日の14日後に動かす**（「最新でない年度」の帯を出さない。T16 の撮影と同じ）。終了した年度は動かさない（ふつうは前の年度なので、帯も出る形を撮る）。
5. **宛先の団体が消えたお知らせは、足した団体（extraGroups）を消して作る**（データセットの団体を消すと、その団体の申請・提出なども連鎖で消えるので、宛先のためだけの団体にした）。

### T17-R1 総務部門員の編集が衝突した後、ピン留めを古い値のまま送り続けて forbidden になり、保存できなくなる（重さ：major）

- 指摘：総務部門員のダイアログにはピン留めの欄がなく、values.pinned（開いたときの行か、戻した下書きの値）をそのまま送っていた。部門長以上が間にピン留めを付け外しすると、save_notice が `p_pinned <> v_old.pinned and not v_is_lead` で forbidden を返し続け、部員は保存できない（`notice-pinned-note` も古い値で出る）。下書きを戻したときと (B1) の読み直しの後も同じ。部員は宛先も選べないので、間に部門長が宛先を団体あてに変えていると、上書きの保存で黙って総務内に戻してしまう（後半の判断したことの 5 が避けようとしたこと）。Vitest も E2E も、部員の衝突を確かめていなかった。
- 確かめて分かったこと：指摘は「1回目の保存は conflict になる」としていたが、save_notice の確かめの順は「宛先の段 → ない → 書いた人 → ピン留めを変える → 楽観ロック」（0014。025 の pgTAP と 04 の save_notice のエラーの順も同じ）なので、古いピン留めで送った1回目は、版が古くても conflict でなく forbidden になる（Vitest の偽の DB にこの順を入れ、E2E で本物の DB でも確かめた）。指摘の直し方（送るピン留めを入力の元の行から取る）だけでは、ピン留めが変わった後の1回目の forbidden で入力の元の行が読み直されず（立場の読み直しと失敗の帯だけ）、何度押しても forbidden のままになる。そこで、直すときの forbidden も1回読み直すことにした。
- 直したこと：
  - 04「お知らせ一覧」：「編集」（総務部門員の今の値〔宛先とピン留め〕は入力の元の行の値。下書きを戻しても宛先とピン留めは戻さない）、conflict（総務部門員の次の保存は読み直した行の宛先とピン留めで送る。読み直したお知らせが総務部門員の編集できないものなら「保存」を押せなくし、理由と今の題名・宛先・更新の日時を出す）、「直すときに forbidden が返ったとき」（1回読み直し、版が進んでいれば conflict と同じ。版が同じ・読み直せない・ないときは今の forbidden の扱い）。この記録の「後半（画面）の約束」3（testid `notice-not-editable`）・4（canEditNoticeByTier、ダイアログのピン留めの行・送った後の知らせ・送れないとき、下書き）・5（読み直しの決まり）もそろえた。
  - lib/modules/notices/permissions.ts：canEditNoticeByTier（段で直せるか。年度の状態は見ない。部門長以上はどれでも、総務部門員は自分が書いた総務内だけ）を足し、canEditNotice を canWriteNotices と canEditNoticeByTier の両方にした（結果は前と同じ。表のテストはそのまま通る）。
  - components/notices/notice-form-dialog.tsx：ピン留めを変えられない段（総務部門員）は、送る宛先・ピン留め・宛先の団体を入力の元の行（savedRow。開いたときの行、conflict の後は読み直した行。作るときは総務内・ピン留めなし）から取り、`notice-pinned-note` もその値で出す。下書きを戻すときは題名と本文だけを戻す。入力の元の行を今の段で直せない（canEditNoticeByTier が偽）ときは「保存」を押せなくし、足もとに「今の立場・年度の状態では保存できません」（書けないときと同じ文）、conflict の後なら `notice-conflict` の代わりに `notice-not-editable`（「ほかの人がこのお知らせを先に変えました。読み直しました。総務部門員が編集できるのは、自分が書いた総務内のお知らせだけなので、このお知らせは保存できません。入力は残してあります。必要なら写してから閉じてください」と、今の題名・宛先・更新の日時）を出す。立場の読み直しで部門長以上から総務部門員になったときも同じ形になる（ほかの人のお知らせ・団体あてを開いていれば保存できず、自分の総務内なら、画面に出ている宛先〔総務内〕とピン留めのまま送る）。
  - components/notices/notice-write.ts：runNoticeSave で、直すときの forbidden を settleForbiddenEdit で1回読み直す。行があって版が読んだときと違えば、中身が入力と同じなら saved（「保存されていました」）、違えば conflict（読み直した行を入力の元にする）。版が同じ・行がない・読み直せないときは failed（今の forbidden の扱い：失敗の帯と、年度の行と立場の読み直し）。行がないのを missing にしないのは、総務のまま消えたお知らせなら save_notice は not_found を返す（forbidden で行がないのは、総務でなくなって読めないとき）ため。部門長以上の forbidden（立場が変わったとき）も同じ道を通り、読み直しが1回増えるだけで扱いは今までと同じ。
- テスト：
  - Vitest（components/notices/notices.test.tsx）：偽の DB の save_notice に 0014 の段と確かめの順を入れた（今のテストはそのまま通る）。足したのは「部門長が間にピン留めを付けた・外した・付けた（1回目の応答が届かなかった）」（1回目は開いたときのピン留めと版で送り、DB は forbidden〔届かなかったときは読み直しで changed〕→ conflict の知らせ、失敗の帯と立場の読み直しはなし、ピン留めの知らせは読み直した値、入力は残る → もう一度で読み直した版とピン留めで保存）、「部門長が間に宛先を全団体に変えた」（`notice-not-editable`、今の題名・宛先・更新の日時、「保存」を押せず送らない、DB は全団体のまま）、「下書きを戻しても宛先とピン留めは開いたときの行のまま」（戻すのは題名と本文、下書きの古い版で conflict → 読み直した版で保存）、「forbidden で版が同じ（立場が変わった）」（今の扱いのままで、読み直しは1回）。lib/modules/notices/permissions.test.ts に canEditNoticeByTier の表（6 つの立場 × 書いた人 3 × 宛先 3）。
  - E2E（e2e/t17-notices.spec.ts の 10 件目「T17 総務部門員の編集の衝突」。「後半のテストの計画」の 10）：部員が自分の総務内を開いた後に、部門長が画面からピン留めを付けて保存 → 部員が本文を直して保存すると（DB は forbidden）conflict の知らせとピン留めの知らせが出て、失敗の帯は出ない（DB は部門長の保存のまま）→ もう一度でピン留めのまま保存（DB は総務内・ピン留め・部員の本文、書いた人と直した人は部員）。部員が開き直した後に部門長が宛先を全団体に変えて保存 → 部員が題名を直して保存すると `notice-not-editable`（今の宛先：全団体）で「保存」を押せず、入力は残り、DB は全団体あてのまま（部員の保存で総務内に戻らない）、部員の一覧も全団体あて。

### T17-R2 削除の結果が分からなかった後にもう一度押して消えていたとき、自分の削除なのに「ほかの人が削除した可能性があります」と出る（重さ：minor）

- 指摘：削除の応答が届かず、読み直しもできずに「削除できたか分かりません」で終わった後、もう一度「削除する」を押すと、前の削除が通っていれば delete_notice は forbidden（ないお知らせ）を返し、読み直すとないので「すでに削除されていました（ほかの人が削除した可能性があります）」と出ていた。
- 直したこと：04 の「削除で forbidden が返ったとき」に足し、components/notices/notices-screen.tsx の confirmDelete で、同じ確かめのダイアログで前の削除が消せたか分からずに終わった（`notice-delete-error` が出ている。deleteError は unknown のときだけ立ち、ダイアログを閉じると消える）後に、止められて読み直すとなかったときは「「{題名}」は削除されていました」（success）にした（「保存されていました」「出されていました」と同じ言い方）。ダイアログを閉じて開き直したときは持ち越さない（今までどおり「すでに削除されていました…」）。
- テスト：Vitest に「消せたか分からなかった後に、もう一度押すと消えていた」（「「総務の集合」は削除されていました」、「すでに削除されていました…」は出ない、ダイアログが閉じて一覧から消える）と「消せたか分からなかった後に「やめる」で閉じ、開き直して消えていた」（前の知らせを持ち越さず「すでに削除されていました…」）の2件。
