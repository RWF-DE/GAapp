## SQL の約束（0015_events.sql）

### 列挙型と表

```sql
create type public.event_kind as enum ('deadline', 'event');
create type public.event_audience as enum ('soumu', 'groups', 'all');

create table public.events (
  id uuid primary key default gen_random_uuid(),
  year_id uuid not null references public.years on delete cascade,
  kind public.event_kind not null,
  audience public.event_audience not null,
  title text not null,
  starts_at timestamptz not null,
  ends_at timestamptz,
  all_day boolean not null default false,
  note text,
  created_by uuid references auth.users on delete set null,
  updated_by uuid references auth.users on delete set null,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  constraint events_title_check check (title <> ''
    and title = btrim(title, E'\t\n\u000b\f\r \u00a0\u1680\u2000\u2001\u2002\u2003\u2004\u2005\u2006\u2007\u2008\u2009\u200a\u2028\u2029\u202f\u205f\u3000\ufeff')
    and length(title) <= 100),
  constraint events_note_check check (length(note) <= 1000),
  constraint events_ends_at_check check (ends_at >= starts_at),
  constraint events_all_day_check check (not all_day
    or ((starts_at at time zone 'Asia/Tokyo')::time = time '00:00'
        and (ends_at is null or (ends_at at time zone 'Asia/Tokyo')::time = time '00:00'))),
  constraint events_date_range_check check (
    (starts_at at time zone 'Asia/Tokyo')::date between date '2000-01-01' and date '2200-12-31'
    and (ends_at is null or (ends_at at time zone 'Asia/Tokyo')::date between date '2000-01-01' and date '2200-12-31'))
);
create index events_year_id_idx on public.events (year_id, starts_at);
```

- 外部キーの on delete は 02 の決まりのとおり：年度へは cascade（年度を消すと予定と締切も消える）、記録のためのユーザー（created_by・updated_by）は set null。団体への参照はない（対象は種類で決め、団体を名指ししない）。
- 題名：notices_title_check と同じ式（同じ 25 文字。JavaScript の String.prototype.trim が除く文字）。書き込みを RPC にしないので DB では除かず、前後に空白のある題名・空白だけの題名は CHECK で拒む（23514）。画面は zod の trim を通してから送る（同じ 25 文字を除くので CHECK と食い違わない）。
- メモ：1000 字まで。空なら画面が null にして送る（D-33。DB は空文字を止めない。ほかの表の note・memo と同じ）。
- 終わり：`ends_at >= starts_at`（同じ日時はよい）。ends_at が null なら CHECK は通る（終わりのない項目）。
- 終日（events_all_day_check）：終日の項目の starts_at・ends_at は Asia/Tokyo の 00:00 だけ（下の「終日の項目の保存のしかた」）。終日でない項目には時刻の決まりはない。
- 日付の範囲（events_date_range_check）：starts_at・ends_at の Asia/Tokyo の日付が 2000-01-01〜2200-12-31（年度の1日目と同じ範囲。D-18）。infinity・-infinity（日付にしても infinity で範囲の外）と、JavaScript の Date で扱えない日時（PostgreSQL は 294276 年まで入る）を入れさせない（ダッシュボードの「締切と予定」は店長・副店長も含めて全員が開く欄なので、表示できない値で欄を壊さない）。
- 索引：年度ごとの一覧（早い順）とポリシーの `year_id in (…)` 用に (year_id, starts_at)。
- 時刻の CHECK は `timezone('Asia/Tokyo', timestamptz)`（AT TIME ZONE）と date・time への変換だけで、どれも IMMUTABLE（タイムゾーンを名前で渡すので、セッションの TimeZone によらない）。

### 終日の項目の保存のしかた

| 項目 | all_day | starts_at | ends_at |
| --- | --- | --- | --- |
| 1日だけの終日（10月16日） | true | 2027-10-16 00:00+09:00（UTC では 2027-10-15 15:00） | null（2027-10-16 00:00+09:00 でもよい） |
| 2日間の終日（10月16日〜17日） | true | 2027-10-16 00:00+09:00 | 2027-10-17 00:00+09:00（最後の日を含む。翌日の 00:00 ではない） |
| 時刻つきの予定（10月14日 13:00〜15:00） | false | 2027-10-14 13:00+09:00 | 2027-10-14 15:00+09:00 |
| 締切（9月30日 17:00） | false | 2027-09-30 17:00+09:00 | null |

- 画面は終日の項目を日付だけで出し（時刻を出さない）、Asia/Tokyo の日付として読む（UTC の日付にしない）。
- 終日の ends_at を「最後の日の 00:00」にしたのは計画のとおり（最後の日を含む）。「翌日の 00:00 まで」（半開区間）にしない。

### 読み取り（RLS。D-47 の形）

```sql
create policy events_select on public.events for select to authenticated
  using (year_id in (select private.my_role_year_ids('{admin,head,deputy_head,staff}'))
         or (audience in ('groups', 'all')
             and (year_id in (select private.my_role_year_ids('{viewer}'))
                  or year_id in (select private.my_group_year_ids()))));
```

- 集合の関数は足さない（0010 の my_role_year_ids と、T17 の 0014 の my_group_year_ids〔自分が団体の代表である年度〕を使う）。
- 対象で分ける枝は対象を名前で並べる（`audience in ('groups', 'all')`。`<> 'soumu'` にしない）。対象の種類を足しても、閲覧のみ・店長・副店長に黙って見えるようにならない（お知らせと同じ）。
- 団体（groups）と全員（all）は、v1 では読める人が同じ（総務・閲覧のみ・その年度の店長・副店長）。違いは誰に向けた項目か（画面の出し方は後半）。
- 読み取りは年度の状態によらない（終了の年度も読める）。

### 書き込み（RLS。直接）

```sql
create policy events_insert on public.events for insert to authenticated
  with check (private.can_lead(year_id));
create policy events_update on public.events for update to authenticated
  using (private.can_lead(year_id)) with check (private.can_lead(year_id));
create policy events_delete on public.events for delete to authenticated
  using (private.can_lead(year_id));
```

- private.can_lead（0013）：その年度の部門長以上（admin・head・deputy_head）で、年度が closed でない。書き込みのポリシーは行ごとの形のまま（D-47：書き込みは書き込む数行にしか判定関数を呼ばない）。
- 書けない人：insert は 42501（with check）、update・delete はエラーにならず 0 行（using で見えない）。終了の年度でも同じ（部門長以上を含む）。
- year_id は変えられない（check_immutable。BEFORE ROW のトリガーは with check より先に動くので、両方の年度の部門長以上でも invalid_input）。
- created_by・updated_by は送っても使われない（set_actor が auth.uid() で上書きし、update では created_by を戻す）。
- 楽観ロックは画面が行う：`update(patch).eq('id', id).eq('updated_at', 受け取った文字列).select()`（updateWithLock。画面の設計 2.3）。0 行なら読み直して not_found・conflict・forbidden に分ける。消すときも `delete().eq('id', id).eq('updated_at', …).select()`（deleteChecked）。同時に同じ行を直したときは、後の update が行のロックを待ち、READ COMMITTED の再評価で updated_at が合わなくなって 0 行になる（conflict）。
- 登録は画面が id（uuid）を作って insert する（後半の約束。主キーが一意のキーになり、応答が届かず送り直しても 23505 で二重にならない。04 の (B1)）。DB は id を受け付けるだけ（既定の gen_random_uuid() でもよい）。

### 権限

- 表：`revoke all on table events from public, anon, authenticated` の後に `grant select, insert, update, delete on table events to authenticated`（W の表。truncate・references・trigger は与えない）。Supabase の既定の権限（public スキーマの新しい表に anon・authenticated の全部）を外すために、先に revoke する（0014 と同じ）。
- トリガー関数 tg_events_set_actor：`revoke all … from public, anon, authenticated`（誰も実行できない）。最後に `revoke all on all functions in schema private from public`。
- 判定関数は足さない（authenticated が実行できる private の関数は 19 個のまま）。RPC も足さない（authenticated が実行できる public の関数は 20 個のまま）。
- ポリシーは 54 → 58 個（W の表が 11 → 12）。関数の本体とポリシーの式の head・deputy_head は組で出てくる（010 の段の書き漏れの守り。events_select の配列に1回ずつ）。

### ロックと同時実行

- トリガーはロックを取らない（年度の行も読まない）。insert・update（year_id は変わらない）の外部キーの確かめは years の行に for key share を取るが、書き込みの RPC の lock_year（for no key update）とはぶつからない。予定と締切の書き込みは、振り分けの保存や状態の遷移を待たせず、待たない。
- 読み取りはロックを取らない。

## 判断したこと（計画にないもの・計画の読み方）

1. **終日の保存のしかたを CHECK で確かめる**（events_all_day_check）：計画は「書いておく」だったが、書き込みが直接で RPC がないので、DB で確かめないと、画面の誤りや API の直接の呼び出しで、時刻のずれた終日の項目（UTC の 00:00 で入れたものなど。日付が1日ずれて見える）が入る。計画の保存のしかたを崩す値だけを拒み、計画を広げも狭めもしない。
2. **日付の範囲**（events_date_range_check）：2000-01-01〜2200-12-31（Asia/Tokyo）。D-18（年度の1日目）と同じ考えで、infinity と JavaScript の Date で扱えない日時を入れさせない（予定と締切は全員が開くダッシュボードに出るので、表示できない値で欄を壊さない）。D-09（入力の上限）の日時の版。
3. **題名は DB で除かず CHECK で拒む**：お知らせは RPC が除いてから入れ、CHECK は除いた形を確かめる。予定と締切は直接の書き込みなので、除く所は画面（zod の trim）だけになる。前後に空白のある題名を送ると 23514（画面は「入力が範囲を超えています」。zod を通せば起きない）。除くトリガーを足す案（D-15 の「呼ぶ側に順序を求めない正規化」）もあるが、画面の trim と DB の CHECK が同じ 25 文字なので食い違いが起きず、足さない。
4. **set_actor の関数を表ごとに作る**（private.tg_events_set_actor。中身は tg_notices_set_actor と同じ）：トリガー関数の名前を表ごとにそろえ（tg_submissions_set_actor・tg_notices_set_actor）、片方を直したときにもう片方が変わらないように。0014 は書き換えない（足すだけのマイグレーション）。
5. **団体（groups）と全員（all）の読める人が同じ**：計画の読み取りの決まりのとおり。v1 には「団体でも閲覧のみでもない、年度に入れる人」がいないので、2つの違いは誰に向けた項目か（画面の出し方）だけになる。枝は対象を名前で並べたので、後で対象を足しても黙って広がらない。
6. **版も確定中の守りもない**：振り分けの入力でないので、allocation_version を増やさず（お知らせと同じ）、確定中も書ける。終了の年度は RLS（can_lead）で読むだけ。SQL Editor（postgres）からは終了の年度でも書ける（お知らせと同じ。トリガーの守りはない）。
7. **件数の上限は持たない**：1件の大きさ（題名 100 字・メモ 1000 字）だけを抑える。書けるのは招待した部門長以上だけ（お知らせの判断 15 と同じ）。
8. **年度の複製（create_year_from）は予定と締切を写さない**：計画にない。日付は年ごとに違い、前の年度の日時を写すと過去の日付が並ぶため。create_year_from は変えない（0015 は足すだけ）。
9. **登録の id は画面が作る**：計画の (B1) を登録にも当てるため（予定と締切には題名の一意などの自然な鍵がない）。DB の約束は変わらない（後半の画面の約束。04 の「予定と締切」と (B1) に書いた）。
10. **監査の理由は null**：直接の書き込みは理由を置けない（PostgREST は1リクエスト＝1トランザクションで、別の呼び出しの set_config は届かない）。履歴は表・した人・前後の行で追える（在庫・マスタの直接の書き込みと同じ）。
11. **書いた人の id は読める人みんなに見える**：店長・副店長と閲覧のみにも created_by・updated_by（uuid）が見える（RLS は列を制限できない）。名前（profiles）は読めない（can_see_profile）。お知らせと同じ。画面は店長・副店長に書いた人を出さない（後半）。
12. **締切の終わり**：DB は種類によって ends_at を止めない（計画にない）。締切に終わりの欄を出すかは後半の画面で決める（「確認したいこと」の 3）。
13. **id の書き換え**：直接の update で id（主キー）を変えることは止めない（ほかの表〔rules・groups など〕と同じ。events を参照する表はない）。変えるとほかの人の楽観ロックは 0 行（not_found）になり、監査の row_pk は新しい id になる。画面は id を送らない。

## 確認したいこと（ユーザーに）

1. 終日の CHECK と日付の範囲の CHECK（判断の 1・2）を足してよいか（計画より厳しくしたのは、計画の保存のしかたを崩す値と、表示できない値だけ）。
2. 年度の複製で予定と締切を写さない（判断の 8）でよいか（写すなら、1日目の差で日付をずらして写す案がある）。
3. 締切（deadline）に終わりの日時を入れられるままでよいか（判断の 12。止めるなら CHECK `kind = 'event' or ends_at is null` を足す）。
4. 本番への出し方（「後方互換と出し方」）：DB と画面を1つの PR で出すと、マージから migrate.yml までの間、/calendar と予定と締切の分が失敗を出す。DB だけを先に別の PR で出すか（T17 と同じ問い）。
