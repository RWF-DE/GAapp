決めたこと（新しい決定。notes/decisions.md は直さない。D-32）：

- **年度をまたぐ表の行は別の問い合わせで読む**（設計 3.12 は `or(year_id.eq.{年度},year_id.is.null)` の1つ）。場所・品目・距離の行は year_id がいつも null（tg_audit は行・団体から年度を引く。これらの表は年度も団体も持たない）ので、年度の表は `year_id = 年度`、年度をまたぐ表は `year_id is null` の2つの問い合わせにし、それぞれ 51 件を読んで at desc・id desc に合わせる（先頭 51 件どうしを合わせれば全体の先頭 51 件になる）。or の1つにすると索引の順で読めず、10 万行で 183〜202 ms かかった（3）。団体で絞るときは年度をまたぐ表の問い合わせを作らない（団体を持たない）。
- **続きは `at <= {at}` も付ける**。`or(at.lt.{at},and(at.eq.{at},id.lt.{id}))` だけだと索引の範囲に使われず、深いページほど先頭から読み飛ばす（1000 ページ目で 61 ms → 0.7 ms）。
- 2つの問い合わせを合わせる並びは at をマイクロ秒まで比べる（`atMicros`。Date はミリ秒で丸めるので、同じミリ秒の行の順が DB と変わる）。
- 年度をまたぐ表を選んでいないときは、年度のない行を出さない（設計の「場所・品目・距離を選んだときは year_id が null の行も含める」のとおり。「すべての表」は年度の行だけ）。
- 期間の入力は、URL の反映（router.replace）を待たずに続けて変えても前の変更を落とさないよう、最後に送った絞り込みから次を作る（E2E で始めと終わりの日付を続けて入れたときに始めが消えた）。
- 変更の列の列名は DB の列名のまま（設計の例「count：3 → 5」のとおり）。値だけを日本語・名前にする。
- 消えた団体の名前は、その団体の groups の記録（before・after の name）を、ページに出た団体のうち今の年度にないものだけ1回読んで引く。引けなければ「（消えた団体）」。

E2E（`e2e/t14-history.spec.ts`。シナリオの年度で閉じる。履歴の行は 2001 年の日時で audit_logs に直接入れ、cleanup の後に年度の id と入れた行の id で消す）：

### 3. 履歴の読み込みの速さ（audit_logs に 10 万行）

`notes/T14/history-perf.sql`（1つのトランザクションで年度を作り、その年度に 10 万行〔15 種の表・40 団体・利用者 4 種・120 日に散らす〕と年度のない場所・品目 200 行を入れ、管理者〔authenticated と JWT の sub〕として EXPLAIN ANALYZE し、最後に rollback）。共有の DB の audit_logs はもとから約 41.5 万行（640 年度）あり、合わせて約 51.6 万行。ロックを取って流した（2026-10-29）。

| 問い合わせ | 実行時間 | 使った索引 |
| --- | --- | --- |
| 年度だけ | 1.0 ms | audit_logs_year_at_idx |
| 年度と表（申請・提出） | 0.8〜1.2 ms | year_at（表は Filter） |
| 年度と珍しい表（ルール 20 行） | 2.6〜6.7 ms | audit_logs_table_at_idx |
| 年度と団体 | 0.7 ms | audit_logs_group_at_idx |
| 年度と期間（7 日） | 0.7 ms | year_at（at も Index Cond） |
| 年度と行のない期間 | 0.03 ms | year_at |
| 年度と表（在庫・場所）を `or(year_id.eq,year_id.is.null)` で（設計の形） | 183〜202 ms | BitmapOr → 2 万行に RLS の関数 → Sort |
| 同じ絞り込みを2つに分けた形（画面の今の形）：年度の在庫 ＋ 年度のない場所 | 0.8 ms ＋ 2.3 ms | year_at ＋ table_at |
| 年度とした人（1 割の人） | 1.4 ms | year_at（user は Filter） |
| 年度と珍しい人（5 行） | 25〜50 ms | Bitmap Heap Scan で年度の 10 万行を読む（user_id の索引がない） |
| 続き 20 ページ目（or だけ → `at <=` を足す） | 1.5 ms → 0.6 ms | year_at |
| 続き 1000 ページ目（or だけ → `at <=` を足す） | 61 ms → 0.7 ms | year_at |
| 未招待の人が絞り込みなしで読む（RLS で 0 行） | **4,132 ms** | 全行に has_role |

- 画面がふだん使う絞り込み（年度と表・年度と団体・期間）は索引で読めて 1〜7 ms。画面で直せた2つ（年度をまたぐ表の or・深いページ）は直した。
- RLS の関数は、ほかの条件で絞った後の行にだけ呼ばれる（Filter の順）。行ごとの呼び出しが重く出るのは、絞った後も行が多いとき（or の形の 2 万行で約 180 ms）と、絞り込みのない読み（未招待の人の 4.1 秒。foundation.spec の statement timeout の形）。DB への申し送りの案で測った数字は下。

### 4. DB への申し送り（DB は変えていない）

すでに分かっているもの（統合の前から）：

- 場所・団体の削除を DB で止める（T09）。
- update_requests_after_deadline の提出の記録の楽観ロック（T11）。
- 確定中のルールの変更を DB で止めるか（T12）。
- audit_logs の RLS が行ごとに関数を呼ぶので、行が多いと遅い（foundation.spec の未招待のテストの statement timeout）。

段 1 で測った数字と案（audit_logs の RLS）：

- 今：`case when year_id is null then table_name in (…) and private.is_admin_of_open_year() else private.has_role(year_id, 'admin') end`。has_role は行の year_id を引数に取るので initPlan にできず、残った行ごとに year_roles を引く。
- 案：admin の年度の集合を1回だけ作る形にする（SECURITY DEFINER・`search_path = ''` の `private.admin_year_ids() returns setof uuid`〔`select year_id from public.year_roles where user_id = (select auth.uid()) and role = 'admin'`〕と、`(select private.is_admin_of_open_year())`）。
  ```sql
  using (case when year_id is null
              then table_name in ('rooms', 'items', 'distance_overrides') and (select private.is_admin_of_open_year())
              else year_id in (select private.admin_year_ids()) end)
  ```
- 同じトランザクションで案のポリシーに置き換えて測った（rollback で戻した）：未招待の人の絞り込みなしの読み 4,132 ms → 123 ms、or の形の年度と在庫・場所 183〜202 ms → 58 ms、年度だけ 1.0 ms → 0.3 ms、年度と珍しい人 50 ms → 37 ms。
- 珍しい人の絞り込み（25〜50 ms）は今の行数なら困らない。`(year_id, user_id, at desc)` の索引を足せば索引で読めるが、書き込みのたびの費用が増えるので、行が増えて遅くなってからでよい。
- pgTAP の権限の棚卸し（has_*_privilege）に新しい関数を足すこと。
