**LAN で配る手順**（総務の PC。Mac・Linux・Windows〔Docker Desktop〕）：

> **先に読む注意（LAN に開くもの）**
>
> - `supabase start` は API の 54321 だけでなく、**Postgres の 54322**（ユーザー postgres・既定のパスワード `postgres`。RLS を通らずに全部の表を読み書きできる）、テスト用のメールの受け箱（Inbucket）の 54324、設定によって Studio の 54323 なども `0.0.0.0`（PC のすべての口）で待ち受ける（`docker ps` の PORTS の列で確かめられる）。

> - だから、**信頼できるネットワーク（総務の部屋の閉じた Wi-Fi・テザリングなど、知らない端末がつながらないもの）だけ**で行う。学校の共用の Wi-Fi・寮・イベント会場のネットワークでは行わない。
> - **ファイアウォールで 54321 と配る静的サーバーの port（下の 3100）以外を閉じる**（下の 4）。Linux の Docker は公開した port を ufw の規則より前で通すので、ufw では閉じられない。`DOCKER-USER` のチェーンで、LAN の口から入る 54321 以外の新しい接続を落とす：`sudo iptables -I DOCKER-USER -i <LAN の口〔wlan0 など〕> -p tcp -m conntrack --ctstate NEW ! --ctorigdstport 54321 -j DROP`（終わったら同じ引数で `-D` にして消す）。Mac・Windows の Docker Desktop も、Docker の受信を許可すると全部の port が開く。どの OS でも、**スマホか別の PC から `<IP>:54322` に届かないこと**を確かめてから始める（例：別の PC で `nc -vz <IP> 54322` が失敗する）。
> - **本番の DB・本番の鍵は使わない**（`supabase link` した本番や、本番の URL・キーで書き出さない）。ローカルの DB に入れるのは合成データ（`pnpm e2e:manual` の MANUAL- の年度）だけで、本物の名簿・メールアドレスは入れない。
> - **終わったらすぐ `supabase stop`** し、ファイアウォールの許可（4 で足した規則）を消し、静的サーバー（serve）も止める。

**指摘**（blocking）：`startEarlyLoad` がパスを問わず `startRecording` を呼び、`settleEarlyLoad` も先読みの表にないパス（entries が空なので removed=0・use=true）の記録を保存していた。そのため、ダッシュボード（/）・/allocation・/swaps で `loadSnapshot` が送る読み取り（`fetchYear` の版と、items・groups・stocks・requests・allocations など。立場の 5 件と合わせても `MAX_RECORDED`=24 に収まる）も覚えられ、次に開いたときに `<head>` の script が版とデータを同時に送っていた。サーバーでデータが版より先に読まれ、その間に版を上げる書き込み（ほかの admin の `save_allocation_rows` など）がコミットされると、新しい版 v+1 と古い行の組のスナップショットができ、その版で確定（`set_year_status` の `p_base_version`）・行の保存・机の交換が conflict にならずに通る。`snapshot.ts` の前提（版 v の後に読んだデータは v の時点かそれより新しい）と D-33、04 の「振り分けに関わる画面は今までどおり版を先に読む」に反する。

### /my の年度の行を毎回読み直す（2026-10-30、レビューの指摘 med）

**指摘**：`lib/data/screen-queries.ts` の loadMyData は、キャッシュに新しい年度の行（立場の読み込みで入れたもの。最大 30 秒前）があれば年度の行を読み直さず、その行の状態で振り分けの行を読むかを決め、画面に出す year もその行にしていた。確定・終了の後 30 秒以内に確定前へ戻されると、振り分けの行は RLS で 0 行なのに year は confirmed のままで「振り分けがない」と出る（T13 が避けた取り違え）。逆（確定前 → 確定）では、確定したのに「振り分け作業中」のままになる。main は /my を読むたびに年度の行を先に読み直していた。

**直したこと**：

- 年度の行は毎回 fetchYear で、団体・品目・場所・申請・提出・了承と並行に読み直す。画面に出す year と、振り分けの行を使うかは読み直した行で決める。
- キャッシュの年度の行は、振り分けの行を先に（並行に）読み始めるかの判断にだけ使う。キャッシュが確定・終了なら並行に読み始め、読み直した行が確定前ならその結果は捨てて null。キャッシュが確定前・ないなら読みに行かず、読み直した行が確定・終了ならその後で読む。往復の段は増えない（どの組み合わせも main 以下。キャッシュと読み直した行が同じなら 1 段）。Supabase への読み取りは /my で 1 本増える（年度の行。並行なので段は同じ）。
- 読み直した年度の行は seedYearRows（読み始めた時刻より新しいキャッシュは上書きしない）でキャッシュに入れ、古い行が次の判断に残らないようにした。
- 確定前と分かっていれば振り分けの行は読みに行かない（`e2e/t13-my.spec.ts` の「確定前は振り分けの行を読まない」はそのまま通る）。キャッシュが確定で読み直した行が確定前のときだけ、読んで捨てる（その結果は使わない）。04 の /my と共通レイアウト、設計（notes/T09a-design/ui-design.md）の 2.1 の表と 2.2、D-45 の記録をこの形に合わせた。
- /stock・/request も確かめた：画面のデータ（stock-master・部屋と年度の在庫・申請・提出）は年度の状態によらずに読み、年度の状態は書けるかの表示に使うだけ（書き込みは DB が状態を確かめる）。/stock の useRoomAllocated（管理者が振り分け中・確定中のときだけ読む）は年度の状態で読むかを決めるが、allocations の RLS は admin・staff には状態によらず全行を見せるので 0 行の取り違えは起きず、保存の前にも読み直している（fresh）。useYearRow のキャッシュ（30 秒）は main と同じ使い方なので、直すところはなかった。
