## 決めたこと

- **E005 は両方向**：isKeep と「運び元＝使用場所」の不一致を error にする（checkInvariants と同じ。allocate は常にそろえて返す）。03 の文言を直した。
- **W105 はまとめて1件**（団体数と先頭5件の名前。1団体のときだけ refs.groupId）。提出前は大半が未提出で、団体ごとに出すと一覧が埋まるため。03 に追記。
- **W103 の品目は実際に運ぶ品目 j**（不可椅子など）で数える。運び元は残す行も含めて数える。
- **I201 は使用不可の部屋の在庫を数えない**。部屋ごとの余りは正の分だけ。
- **E004 は行ごと**。理由（ルールなし／区分・屋内の不一致／了承しなかった／運び元の制限）をメッセージに入れ、refs.ruleCode に該当のルールを入れる。declined の置き換えは W102 ではなく E004 だけ。
- **W102 は団体ごとに当てはまるルール**（区分・屋内。substituteOptions と同じ判定）だけで、団体・申請品目・運ぶ品目の組ごとに1件。
- **W106 の「申請」**は fixed_request を外して buildDemand した値（読み替え後の合算）。
- **validate は入力が不正（知らない id、ルールの参照先がない）なら例外**。allocate が先に invalid_input で止めるので、画面は allocate の後に呼ぶ。
- **diagnose**：
  - 品目全体の不足は、需要のある団体の候補の品目の和集合の在庫（S′、運び元の制限は無視）と比べる。
  - 解き直しは常に full・previousRows なしで行う。
  - `allocate(input, solver, opts)` の `opts.disabledRuleCodes` は diagnose にも渡し、base と解き直しの両方で外したままにする。
  - 「解けた」は buildModel が ready（または需要なしの empty）で HiGHS が optimal のとき。
  - 組み合わせの cause は、品目全体の不足が空で、どのルールを1つ外しても解けず、かつ運び元の制限をすべて外すと解けるときだけ（制限があるかどうかではなく、効いているかどうかで決める）。details は制限の対象（団体・申請品目）ごとに1つ（制限が重なる場合は共通部分の場所）。制限をすべて外しても解けないときは組み合わせとは言わず、message が「代替を含めても在庫が足りません」（STOCK_SHORT_MESSAGE）、ruleCode が null の cause を返す。shortages は、制限をすべて外して数え直した前処理 7 の団体つきの不足。LP だけが Infeasible のときは shortages に入れず、代替先を共有する組の不足を cause の details に1件だけ入れる（最大流の最小カットで見つけた (団体・申請品目) の集まりについて、itemIds ＝申請品目と代替先、demand ＝組の需要の合計、supply ＝候補の品目の在庫の合計。groupId・roomIds なし）。そうして shortages の意味（groupId null は品目全体、それ以外は団体つき）を変えない。
  - cause の details：source_restrict は不足している対象だけ（なければ全部）、fixed_request は固定の数と候補の在庫、keep は残す数とその部屋の在庫。

## 結果（合成データ r8like）

- S05 が原因の入力（makeInfeasibleS05）：shortages に設営・机(木)・需要241・在庫235、causes に S05。診断の解き直し込みで allocate は 2 秒未満（テストで確認。手元で約 0.1 秒台）。
- allocate の結果は validate で error・W101・W107 が0件。checkInvariants と、壊した行（6通り）でもコードの集合が一致。
- R8 では未確認（fixtures/r8 がない）。fixtures/r8 が入れば validate-invariants.test.ts は自動で R8 にも流れる。
