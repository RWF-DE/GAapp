### 3. 画面のふるまい（設計どおりのところは省く）

- **/request**：`?group=` が自分の代表する団体にない id なら無視して最初の団体（その id の団体は読みにいかない）。団体・年度ごとに画面を作り直す（key）ので、印・入力は団体ごと。入力は団体ごとの下書き（`screen: 'request'`、target は団体 id）に置き、受付期間内のときだけ DraftNotice と UnsavedChangesGuard を出す。提出は「最新でない年度」の確認（useNotLatestYearConfirm）→ 0 でない品目の一覧の確認 → 提出の記録の読み直し（読み込んだ後にほかの代表者が提出していれば「{時刻} にほかの代表者が提出しています。上書きしますか」）→ requestFormSchema で確かめて submit_requests。成功したら「提出しました（10/5 18:01）」、下書きを消して読み直す。
- **DB が受付期間の外と判断したとき（端末の時計のずれ）**：submit_requests が invalid_state なら年度の行を読み直し、状態が申請受付中のままなら印を立てて読み取り専用にし、「締切を過ぎました（または受付の前です）。端末の時計がずれている可能性があります。変更は総務へ」と出す（提出のボタンを消し、入力欄を無効にする）。状態が変わっていれば、その状態の文言（「年度が「振り分け中」のため…」）と表示にする。Vitest（request-screen.test.tsx）と E2E の両方で確かめた。
- **/requests**：セルを入れると未保存（黄色）。「保存（N件）」で、締切前はセルごとに直接（行があれば updateWithLock、なければ insert）、締切後は理由のダイアログ → 団体ごとに update_requests_after_deadline。セルごとの成否を出す（「2 件を保存しました。1 件は保存できませんでした：…」）。区分で申請できない品目のセルは「—」、0 でない申請が残っていれば灰色の数と ※（title と読み上げに「長机(2人掛)として扱う」「申請できない品目（E006）」）と「0にする」。表の下に「—」と ※ の説明。部員は表だけ（入力欄・保存・代理入力なし）。確定中・終了は読み取り専用の帯。
- 絞り込み（区分・未提出だけ・備考ありだけ）は URL のクエリ（`router.forceReplace`。同じ画面なので未保存のセルはそのまま残り、確かめない）。
- 締切の表示：締切前は「締切 2026/10/05 23:59（あと3日）」、締切後・振り分け中以降・印があるときは「締切後（変更には理由が要ります）」。

### 4. 決めたこと（設計に書いていない細部。新しい決定はここに書く。D-32）

1. **「DB が受付期間の外と判断した」印の鍵**：設計は「年度の行を読み直して状態が変わったとき・画面を開き直したときに消す」。状態に加えて受付期間（request_open_at・request_close_at）も鍵に入れた（管理者が締切を延ばしたら、団体代表は画面を開き直さなくても提出できる）。印はコンポーネントの状態なので、画面を開き直すと消える。
2. **申請一覧の直接の保存は forbidden で止める**：最初の forbidden（RLS で 0 行・42501）で残りのセルを送らない（同じ直接の書き込みを繰り返さない）。conflict・not_found のセルは読み直した値に戻して印（青の枠）、それ以外の失敗（E006・入力・通信など）は入力を残して印（赤の枠）。
3. **締切後の団体ごとの保存は forbidden・state で止める**。conflict の団体は、2.5 のとおり変えたセルの値を残して印をつけ、表を読み直す（次の保存は新しい updated_at で送る）。理由が空（reason）なら理由のダイアログを開いたままにする。
4. **申請できない品目のセル**：管理者は 0 にすることだけができる（「0にする」）。pendingChanges は申請できない品目の 0 でない値を捨てる（DB のトリガーも E006 で止める）。
5. **合計の行**は、表示している行（区分・絞り込みの後）に未保存の値を当てた数。**未提出の団体の一覧**は区分の絞り込みの後（未提出だけ・備考ありだけの前）の団体で数える。
6. **代理入力**：締切前は submit_requests で表示した品目すべてを送る（申請と提出を1回で）。締切後は update_requests_after_deadline に、変えた品目だけ（行があれば updatedAt）と `p_submission: { submitted: true, note }` を送る（何も変えずに保存すると、提出済みにして備考を直すだけになる）。代理入力の締切前の提出が invalid_state で、年度が受付中のままなら、申請一覧と同じ印を立てて締切後の書き方に切り替える（シートは開いたまま、入力は残る）。
7. **「前年の数を入れる」**は、区分が休憩所で、今年の 0 でない申請がなく、年度に prev_year_id があるときだけ出す。previous_year_requests の団体名が今年の団体名と完全に同じ行を、今年の区分で申請できる品目にだけ当てる（ほかは 0）。前年に同じ名前の団体がなければ「前年度に「休憩所1」の申請がありません」。
8. **提出の直前の読み直しに失敗したとき**（通信など）は、確かめずに submit_requests を送る（送信の失敗として扱われる。submit_requests は同じ値なら何度送っても同じ。2.6）。
9. /request の団体名は groups.name（表示名ではない。団体代表がフォームで答える名前と同じにする）。

## 後の段への申し送り（段 2：CSV 取り込みと仕上げ）

- **入れる所**：「Googleフォームの回答を取り込む」のボタンは RequestsScreen（components/requests/requests-screen.tsx）の PageHeader の `actions` に置く。出す条件は `admin && mode !== 'readonly'`（confirmed・closed では出さない。設計 3.6）。ダイアログは components/requests/import-dialog.tsx、純粋関数とつなぎは lib/data/import.ts（依頼の範囲）。
- **保存の後**：`queryClient.invalidateQueries({ queryKey: queryKeys.yearPart(yearId, 'requests') })` で申請一覧を読み直す（RequestsBoard の reloadTables と同じキー）。団体ごとの失敗の文言は `messageFor(classifyError(e), { rpc: 'update_requests_after_deadline', names, groupId })`（conflict の item_id・invalid_input の submittedAt に団体名が付く）。
- **使える関数**：lib/data/requests.ts の `sortItems`・`isRequestable`・`buildRequestMatrix`（団体ごとの今の数と updated_at・提出日時・備考）。p_rows は「区分で申請できる品目と DB に行がある品目のすべて」（CSV にない品目は 0、行があれば updatedAt）、申請できない品目（読み替え先のないもの）は送らない（設計 5.1）。
- **E2E**：e2e/t11-import.spec.ts（設計 5.2。`extraGroups` で模擬店甲・乙・丙）。スクリーンショットは e2e/shots/T11.shots.ts に取り込みのダイアログを足す。シナリオの年度は最新の年度ではないが、申請一覧は「最新でない年度」の確認を出さない（/stock・/request・/my だけ。1.3.1）。
- **要件定義**：差分案 3-15（CSV取り込み）を 04 に当てる（当てる前に変更前の文と見比べる）。
- **仕上げ**：全体の `pnpm e2e` を1回流す。foundation.spec.ts の `READY` は T11 が足した（ほかの画面のチケットも同じ所を直すと衝突しうるので、マージのときに `READY` の集合をまとめる）。
