### 3. 画面のふるまい（設計どおりのところは省く）

- **/request**：`?group=` が自分の代表する団体にない id なら無視して最初の団体（その id の団体は読みにいかない）。団体・年度ごとに画面を作り直す（key）ので、印・入力は団体ごと。入力は団体ごとの下書き（`screen: 'request'`、target は団体 id）に置き、受付期間内のときだけ DraftNotice と UnsavedChangesGuard を出す。提出は「最新でない年度」の確認（useNotLatestYearConfirm）→ 0 でない品目の一覧の確認 → 提出の記録の読み直し（読み込んだ後にほかの代表者が提出していれば「{時刻} にほかの代表者が提出しています。上書きしますか」）→ requestFormSchema で確かめて submit_requests。成功したら「提出しました（10/5 18:01）」、下書きを消して読み直す。
- **DB が受付期間の外と判断したとき（端末の時計のずれ）**：submit_requests が invalid_state なら年度の行を読み直し、状態が申請受付中のままなら印を立てて読み取り専用にし、「締切を過ぎました（または受付の前です）。端末の時計がずれている可能性があります。変更は総務へ」と出す（提出のボタンを消し、入力欄を無効にする）。状態が変わっていれば、その状態の文言（「年度が「振り分け中」のため…」）と表示にする。Vitest（request-screen.test.tsx）と E2E の両方で確かめた。
- **/requests**：セルを入れると未保存（黄色）。「保存（N件）」で、締切前はセルごとに直接（行があれば updateWithLock、なければ insert）、締切後は理由のダイアログ → 団体ごとに update_requests_after_deadline。セルごとの成否を出す（「2 件を保存しました。1 件は保存できませんでした：…」）。区分で申請できない品目のセルは「—」、0 でない申請が残っていれば灰色の数と ※（title と読み上げに「長机(2人掛)として扱う」「申請できない品目（E006）」）と「0にする」。表の下に「—」と ※ の説明。部員は表だけ（入力欄・保存・代理入力なし）。確定中・終了は読み取り専用の帯。
- 絞り込み（区分・未提出だけ・備考ありだけ）は URL のクエリ（`router.forceReplace`。同じ画面なので未保存のセルはそのまま残り、確かめない）。
- 締切の表示：締切前は「締切 2026/10/05 23:59（あと3日）」、締切後・振り分け中以降・印があるときは「締切後（変更には理由が要ります）」。

### 4. 決めたこと（設計に書いていない細部。新しい決定はここに書く。D-32）

1. **「DB が受付期間の外と判断した」印の鍵**：設計は「年度の行を読み直して状態が変わったとき・画面を開き直したときに消す」。状態に加えて受付期間（request_open_at・request_close_at）も鍵に入れた（管理者が締切を延ばしたら、団体代表は画面を開き直さなくても提出できる）。印はコンポーネントの状態なので、画面を開き直すと消える。
2. **申請一覧の直接の保存は forbidden で止める**：最初の forbidden（RLS で 0 行・42501）で残りのセルを送らない（同じ直接の書き込みを繰り返さない）。conflict・not_found のセルは読み直した値に戻して印（青の枠）、それ以外の失敗（E006・入力・通信など）は入力を残して印（赤の枠）。楽観ロックの基準は決めたこと 19。
3. **締切後の団体ごとの保存は forbidden・state で止める**。conflict の団体は、2.5 のとおり変えたセルの値を残して印をつけ、表を読み直す（そのセルの基準を読み直した行に付け替えるので、次の保存は新しい updated_at で送る。印を見た上での保存なので黙った上書きではない。決めたこと 19）。理由が空（reason）なら理由のダイアログを開いたままにする。
4. **申請できない品目のセル**：管理者は 0 にすることだけができる（「0にする」）。pendingChanges は申請できない品目の 0 でない値を捨てる（DB のトリガーも E006 で止める）。
5. **合計の行**は、表示している行（区分・絞り込みの後）に未保存の値を当てた数。**未提出の団体の一覧**は区分の絞り込みの後（未提出だけ・備考ありだけの前）の団体で数える。
6. **代理入力**：締切前は submit_requests で表示した品目すべてを送る（申請と提出を1回で）。締切後は update_requests_after_deadline に、変えた品目だけ（行があれば updatedAt）と `p_submission: { submitted: true, note }` を送る（何も変えずに保存すると、提出済みにして備考を直すだけになる）。代理入力の締切前の提出が invalid_state で、年度が受付中のままなら、申請一覧と同じ印を立てて締切後の書き方に切り替える（シートは開いたまま、入力は残る）。
7. **「前年の数を入れる」**は、区分が休憩所で、今年の 0 でない申請がなく、年度に prev_year_id があるときだけ出す。previous_year_requests の団体名が今年の団体名と完全に同じ行を、今年の区分で申請できる品目にだけ当てる（ほかは 0）。前年に同じ名前の団体がなければ「前年度に「休憩所1」の申請がありません」。
8. **提出の直前の読み直しに失敗したとき**（通信など）は、確かめずに submit_requests を送る（送信の失敗として扱われる。submit_requests は同じ値なら何度送っても同じ。2.6）。
9. /request の団体名は groups.name（表示名ではない。団体代表がフォームで答える名前と同じにする）。

### 3. 画面のふるまい（設計 5.1 どおりのところは省く）

- **種類とファイル**：種類（模擬店・部門・企業）はボタンの radiogroup（既定は模擬店）。ファイルは `<input type="file" accept=".csv,text/csv">` を lib/csv-file.ts の readCsvFile（UTF-8 → Shift_JIS）で読む。読めなければ「文字コードが読めません…」、見出しが合わないなどは ImportFormatError の文言だけ（元の値を含まない）。種類を変えると同じ文字列を読み直し、手で選んだ対応と上書きの選び直しは消す。
- **プレビュー**：件数の行（回答・対応した・対応しない・取り込まない〔理由ごと〕・古い回答、読まなかった列の見出し）、対応しない行（行番号・フォームの団体名〔企業・空・メールだけの名前は「（なし）」〕・タイムスタンプ・数の要約・EntitySelect〔その区分の団体。「取り込まない（団体を選ぶ）」、選び直し・外すことができる〕とマスタ設定へのリンク）、古い回答（「模擬店甲：行4（…）を使い、行2（…）は使いません」）、取り込まない行（行番号と理由だけ）、団体ごとの結果の表（上書きのチェック・団体・フォームのタイムスタンプと行番号・今の提出日時〔Q2 で既定が「取り込まない」なら「アプリの提出の方が新しい」〕・品目ごとの CSV の数〔今の数と違うセルは色と「今 N」〕・備考の置き換え／消去・長机の読み替え・申請できない品目の印・「数は今と同じ」）。
- **保存**：理由の欄（既定「Googleフォームの回答の取り込み（模擬店・{ファイル名}）」、編集できる、必須・500 字）→「取り込む（K 団体）」→ 団体ごとに順に送る → 結果の一覧（団体ごとの成否。conflict は「取り込みの前に、ほかの人がこの団体の申請を変えました。読み直してからもう一度取り込んでください」、ほかは messageFor の文言）。1団体でも送ったら（成否によらず）申請一覧を読み直す（決めたこと 16）。送信中はダイアログを閉じられない。

### 4. 決めたこと（段 2。設計に書いていない細部。D-32）

10. **理由はダイアログの中の欄で入れる**（設計の「取り込む → 理由」を1画面にした）。T09a の ReasonDialog は初期値を渡せない（既定の理由を入れておけない）ので、T09a のファイルは変えず、同じ確かめ（reasonError）を使う欄をダイアログの末尾に置いた。
11. **備考は CSV の備考で置き換える**（設計 5.1 の `p_submission: { submittedAt, note }` のとおり。CSV に備考がなければ null を送り、今の備考は消える）。フォームの回答は申請の全体という扱い（CSV にない品目は 0）と合わせた。プレビューの「備考・印」の列に「今の備考を置き換えます」「今の備考を消します」と出す。→ 未決 1。
12. **p_rows**：区分で申請できる品目はすべて（CSV になければ 0）、申請できない品目で DB に行があるものは 0（企業以外の長机(3人掛) は読み替えた後なので 0 にする）。CSV に申請できない品目（読み替え先なし）の 0 でない数があれば、その品目は送らず（DB の行もそのまま）、団体の行に「申請できない品目のため取り込みません」と出す。行があれば updatedAt を付ける（読み込んだ後にほかの人が変えれば conflict）。
13. **Q2 の比べ方**：DB が未提出か、CSV のタイムスタンプが DB の提出日時より**厳密に**新しいときだけ既定で上書きする（同じ時刻は上書きしない）。→ 未決 2。
14. **対応しない行は、手で選んだ後も一覧に残す**（選び直し・外しができるように）。一覧は手で選ぶ前の resolveResponses の unmatched から作り、件数の行の「対応しない」は選んだ後の数。
15. **使う行の行番号**：resolveResponses は古い回答のない団体の行番号を返さないので、回答を1件ずつ resolveResponses に通して団体 → 行番号を引く（rowsByGroup。対応のしかたは importer と同じになる。回答は多くても数百件で速い）。
16. **保存は forbidden・state で止める**（申請一覧の締切後の保存と同じ。止めた団体は「送っていません」と出す）。conflict の団体は取り込みの文言（「読み直してからもう一度取り込んでください」）を出し、onError には渡さない。**1団体でも送ったら、成否によらず onImported で申請一覧を読み直す**（5.1 の「全部終わったら申請一覧を読み直す」。全団体が conflict・通信の失敗でも読み直すので、ファイルを選び直すと新しい updated_at・提出日時でプレビューと p_rows ができる。レビューの指摘で直した）。プレビューは結果の画面に切り替えるので、続けて取り込むときはファイルを選び直す。
17. **取り込みのボタン**は管理者で `mode !== 'readonly'`（preparing・requesting・allocating）のときだけ。「DB が締切後と判断した」印があっても出す（取り込みは締切の前後によらず update_requests_after_deadline）。
18. ダイアログには UnsavedChangesGuard を付けない（中身は閉じると消える決まり〔設計 5.1 の 6〕で、閉じるのは明示の操作だけ）。

### 4b. 決めたこと（レビューの指摘で足したもの）

19. **申請一覧の未保存のセルは、最初に編集したときの行（基準）を持つ**（PendingCell `{ value, baseCount, baseUpdatedAt }`。下書きにもこの形で置く）。保存の楽観ロック（updateWithLock・update_requests_after_deadline の updatedAt）には、保存のときの表の値ではなく基準の updated_at を送る（行がなかったセルは updatedAt なし＝DB は行があれば conflict）。前は表の今の updated_at を送っていたので、編集と保存の間に表を読み直すと（読み直す・代理入力・提出済みにする・取り込み・ほかのセルの conflict の読み直し）、ほかの人の変更を黙って上書きできた（2.3 に反する）。
20. **表が届くたびに未保存のセルを当て直す**（rebasePending。届いた表ごとに1回。読み直す・invalidate・書き込みの後の読み直しのどれでも）：基準から行が変わったセル（updated_at が違う・行ができた・消えた）は読み直した値に戻して（未保存から外して）印（青の枠）をつけ、「N 件のセルは、ほかの人が先に変えたので読み直した値に戻しました」と出す（3.6 の「conflict のセルは読み直した値に戻して印」と同じ扱い）。DB の数と同じになったセルは黙って外す（自分の保存が届いていた・同じ数になった）。**下書きを戻すとき**も今の表と比べて同じように当て直す（下書きは 24 時間まで残る）。形の違う下書きの値（基準のない古い形）は捨てる。
21. **保存中はセルを読み取り専用にする**（RequestsTable の busy。入力欄は readOnly、代理入力・提出済みにする・0にする・取り込みのボタンは押せない。列は隠さない）。保存の結果は、押したときの写しではなく最新の未保存のセルに当てる（送った値のままのセルだけを外す。送った後に値が変わっていれば基準を保存した行に付け替えて残す）。保存中に届いた表は当て直さず、保存の後に読み直した表でまとめて当て直す（自分の保存で updated_at が進んだセルを、ほかの人の変更と取り違えないため）。

### 10. フォローアップの修正（2026-10-29）：取り込みが提出の記録の変更を黙って上書きする

指摘：saveImport が p_submission（submittedAt・note）を送るが、楽観ロックは p_rows の行の updatedAt にしかかからない。プレビューの後に団体代表が数を変えずに出し直した（備考だけの変更を含む。submit_requests は数が同じ行を更新しないので requests の updated_at は変わらない）・ほかの管理者が「提出済みにする」を押した場合に conflict にならず、新しい提出日時が CSV の古いタイムスタンプに戻り、備考も CSV のもので上書きされていた（2.3・Q2 に反する）。

直したこと：ImportPlan に `dbSubmission`（プレビューを作ったときの提出の記録）を足した。saveImport は団体ごとに送る直前に fetchSubmission で読み直し、`submissionChanged`（記録ができた・消えた、updated_at・submitted_at・備考のどれかが違う。時刻の書き方の違いは同じとみなす）なら送らずに `conflict`（reason `submission_changed`）で返す。ダイアログは今までの conflict の文言（「取り込みの前に、ほかの人がこの団体の申請を変えました。読み直してからもう一度取り込んでください」）を出し、結果があれば申請一覧を読み直すので、取り込み直すと Q2 の既定が新しい提出日時で決め直される。読み直しの失敗は送る失敗と同じ扱い（forbidden・state なら残りを送らずに止める）。04 の「CSV取り込み」に書き足した。

**決めたこと 26.** DB の側の確かめ（update_requests_after_deadline の p_submission に期待する updated_at を渡して DB が conflict を返す）は入れていない（このチケットでは supabase/ を変えない）。読み直しから RPC までの短い間にほかの人が提出の記録を変えた場合は、まだ上書きしうる。確実に防ぐなら DB のチケットで p_submission に `expectedUpdatedAt` を足し、saveImport から dbSubmission.updated_at を送る。

### 11. フォローアップの修正 3（2026-10-29）：通信の失敗の後の代理入力・「分からない」の範囲・結果の文

a. **代理入力の保存が途切れたとき（設計 2.6）**：前は network・unknown を onError に渡して文言を出すだけで、送り直す前に読み直していなかった。直したこと：proxy-sheet.tsx は、応答が届かなかった失敗（下の b の isUnknownOutcome）なら onError に渡さず、団体の申請と提出の記録を読み直して（fetchGroupRequestState）、`proxySavedAfterUnknown`（lib/data/requests.ts）で突き合わせる。submit_requests も update_requests_after_deadline も提出の記録を必ず書き直す（request_submissions の updated_at が進む）ので、それを届いた印にし、送った品目の数・備考（締切後は備考を送ったときだけ）が自分の入れたもので、提出済みなら「通信が途切れましたが、{団体}の申請は保存されていました」と出してシートを閉じる。締切後は、送った品目の行の updated_at が送った値から進んだことも確かめる。どちらの RPC も全部か何もないかなので、一部だけを保存済みにはしない。保存されていなければ入力を残して「保存されていませんでした（通信できませんでした）。もう一度押してください」。読み直しもできなければ「保存できたか確かめられません。通信が戻ったら『確かめる』を押してください」と出し、「確かめる」を出して、確かめるまで提出を押せなくする（申請一覧のセルの保存と同じ考え方）。締切前の比べる基準は、送る直前に読み直した記録（checkAndSend の latest）の updated_at。
