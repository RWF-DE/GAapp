## 画面の作り（要点）

### /stock（在庫入力。スマホ）
- room がないとき：保管場所（is_storage）を並び順（sort_order → 名前 → id）で、建物ごとの見出し（建物がなければ場所の種類「屋外」など）。名前・建物と階・別名で絞る入力欄（components/common の matchesEntity）。各行に「数えた（10/5 18:01・名前）」か「まだ」と使用不可の印。行は AppLink で `/stock?room=<id>`。
- room があるとき：場所名・建物と階、使用不可なら「今年は使用不可」と理由のメモ（「数えることはできます」）、「前回の入力：日時（名前）」（その部屋の stocks の counted_at が最も新しい行。名前を読めなければ「名前を表示できません」）、品目ごとの行（品目名・前年の数・＋－と数字〔ボタンと欄は 44px〕）、画面の下に固定した「保存」。
- 保存の流れ（StockInput の save）：zod で数を確かめる → 下書きを書き切る → 最新でない年度なら確かめる（useNotLatestYearConfirm）→（管理者で振り分け中・確定中）その部屋の振り分けの合計を読み直し、少なくなる品目があれば振り分け中は確かめ・確定中は止める → その部屋の stocks を読み直し、読み込んだときの行と updated_at を比べる → 違えばダイアログ（上書きする・読み直す・やめる）→ 部屋の全品目を1回の upsert（`onConflict: year_id,room_id,item_id`、送るのは year_id・room_id・item_id・count だけ）→ toast「保存しました」と「次の部屋へ（名前）」。
- 書けるか：`stockAccess(status, role)`（RLS の can_write_stocks と同じ）。部員は振り分け中に「振り分けが始まったので、在庫は総務管理者だけが直せます」、確定・終了は ReadOnlyNotice の既定の文言。
- エラー：ErrorBanner（部屋・品目の名前つき。確定中の守りの invalid_state は「確定中は、在庫超過や…（E2E倉庫Aの机(木)）」）。forbidden・state は年度の行を読み直して立場も読み直す（読み取り専用に切り替わる）。401 はセッションを1回更新して upsert を1回だけ送り直す。network・deadlock は「もう一度」（保存の流れを最初から。読み直しの確かめを通る）。

### /stocks（在庫一覧。PC）
- 保管場所 × 品目の表（`buildStockMatrix`）。セルは「12（+2）」、行と列の合計、合計は「使用不可を除く」と「全部」の2行。使用不可の部屋は灰色と印。数えていない部屋は「まだ」。部屋の名前から在庫入力へ。
- 表の上に「まだ数えていない場所（n／m。使用不可を除く）」（W104 と同じ）。PageHeader に最終読み込みと「読み直す」、「QR を印刷」。
- 表は DataTable を使わず、見出しと1列目を sticky にした table にした（列が品目で動的、合計の行を tfoot に置くため）。入れ物の中だけ横にスクロールする。

### /stocks/qr（QR の印刷）
- 保管場所すべて（既定）か `?rooms=<id>,<id>`（形の違う id は無視）。チェックで選び直せる。「印刷」で window.print()。
- カード：場所名（大）・建物と階・QR（uqr の renderSVG、border 2、誤り訂正 M。dangerouslySetInnerHTML に入れるのは uqr の SVG だけ）・「在庫入力（電波祭 総務）」・URL の文字・「スマホのカメラで読み、Safari か Chrome で開いてください（LINE などのアプリの中で開くと Google でログインできません）」。A4（`@page { size: A4; margin: 10mm }`）に 2列×4段、8枚ごとに改ページ。
- URL は `stockUrl(roomId, location.origin, BASE_PATH)` → `${origin}${basePath}/stock/?room=<id>`（年度を入れない。D-31）。origin は useSyncExternalStore でブラウザでだけ読む（プリレンダーの間は空でカードを出さない）。

## 決めたこと（新しい決定。D-32 により notes/decisions.md には書かない）

1. **振り分けの合計は allocations をその部屋で数える**（設計 2.1 の表は v_remaining と書くが、v_remaining は使用不可の部屋と在庫の行のない品目を含まない。DB の確定中の守り tg_stocks_guard は使用可否によらず allocations を数えるので、同じ条件にした）。管理者が振り分け中・確定中のときだけ読み、品目の行に「振り分け n台」を出す。保存の直前にも読み直す。
2. **ほかの人の保存の見分け方**：画面を開いたとき（と自分の保存・読み直しの後）の部屋の行を持ち、保存の直前に読み直した行と品目ごとに updated_at（受け取った文字列のまま）を比べる。行が増えた・消えたものも「変わった」とする。ダイアログの名前と時刻は、変わった行のうち counted_at が最も新しい行。「上書きする」は読み直した行を元にして自分の数で送り、「読み直す」は相手の数を入力にして下書きを消す。
3. **room の値が形の違う・保管場所の一覧にない**ときは「この場所は見つかりません」と一覧へのリンク（設計 3.3 の「形が違う」も含める）。room がない・空なら場所の一覧。
4. **「次の部屋へ」**：並び順で今の部屋より後の、まだ数えていない保管場所（W104 と同じく使用不可を除く）。後になければ前から探す。なければ「まだ数えていない保管場所はありません」。
5. **前年との差**：今年と前年の両方の行があるセルだけ出す（前年の行がなければ数だけ）。合計の前年は、**今年数えた部屋だけ**を足す（前年の行のない部屋は 0。数えていない部屋は今年の合計に入らないので、前年の合計からも除く。数えた部屋が1つもなければ合計の差は出さない。表の上に注を出す。軽い指摘 c で直した）。数えていない部屋は「まだ」。数えた部屋で行のない品目（品目を後から足した場合）は「—」。前年度がない年度は差を出さない（説明の文を出す）。
6. **下書き**：値は `{ counts, base }`（base は入力の元にした部屋の行の updated_at。品目の id → updated_at。zod で確かめ、壊れている・base がなければ捨てる）。読み込んだ数と違うときだけ、書ける年度でだけ DraftNotice を出す。入力が読み込んだ数に戻ったら下書きを消す。**戻した下書きを保存するときは、下書きの base（下書きを作ったときの行）と保存の直前に読み直した行を比べる**（レビューの指摘で直した。前は戻した時点の DB と比べていたので、QR を読みに離れている間にほかの人が保存すると、触っていない品目も確かめなしに古い数で上書きされた）。違えば 2. と同じダイアログ（上書きする・読み直す・やめる）。戻した後にさらに入力しても下書きの base は下書きを作ったときのまま。自分の保存・上書き・読み直しの後は、その行が元になる。画面の「前回の入力」と「保存していない変更があります」は、今の DB の行を元にしたまま。
7. **品目の行は全品目**（申請できない品目〔不可机など〕も。保存が部屋の全品目を書くため。04「部屋の全品目（0 を含む）」）。
8. **QR の印刷は年度によらない**（保管場所は年度をまたぐ表。その年度の使用不可の部屋も出す。PageHeader に年度を出さない）。
9. **数えた人の名前**は profiles を `.in('user_id', ids)` で読む。RLS で読めない人（シナリオで postgres が入れた行の counted_by が null の場合を含む）は、「前回の入力」と場所の一覧では「名前を表示できません」（設計 3.3 の文言）、ほかの人の保存のダイアログと知らせでは文の形にして「ほかの人が 日時 に保存しました（名前は表示できません）」（表の見出しは「ほかの人」）。
10. **前年の数**は previous_year_stocks を `.range()` で分けて読む（RPC の結果も max_rows 1000 で切れうるため。年度ごとに1回）。
11. **401 の扱い**：upsert の送信で 401 なら、セッションの更新を1回試し、更新できたら同じ upsert を1回だけ送り直す（同じ値で何度送っても同じ。設計 2.6）。保存の前の読み直し（振り分けの合計・部屋の行）で 401 なら、セッションの更新を1回試し、通ればその読み直しを1回だけやり直して保存を続ける（軽い指摘 g。前は何も出さずに「保存」へ戻っていた）。更新できなければ onAuthError が signOut して /login へ移る（下書きは残る）。
12. **保存のボタン**は書けるときはいつでも押せる（同じ数でも数え直した記録を残すため。F1-5）。送っている間と確かめている間は押せない（「保存中…」「確かめています…」）。
13. **ほかの人の保存のダイアログのフォーカス**（レビューの修正）：「やめる」を AlertDialogCancel にして、開いたときに Radix がそこへフォーカスを移すようにした（Radix の AlertDialogContent は既定のフォーカスを止めて cancel だけにフォーカスするため、普通の Button だけだとフォーカスが body に残っていた）。閉じたら（やめる・Esc・読み直す）「保存」へ戻す。上書きして送信中で「保存」が押せないときは、送り終わってから戻す。T09a の ConfirmDialog と同じ形。

14. **読み直し（設計 2.6）**：部屋の行のクエリが新しい行を返したら（ErrorBanner の「読み直す」、キャッシュから開いた後の裏の読み直し、conflict・not_found の後の invalidate、自分の保存の後の invalidate）、未保存の入力がなければその行で入力と元の行を作り直す。入力があれば入力も元の行も変えず、元の行（下書きを戻したなら下書きの base）と比べてほかの人が保存していれば「○○さんが 日時 にこの部屋の数を保存しました。入力はそのまま残しています…」と「ほかの人の数を読み直す」を出す。元の行を変えないので、保存の前の確かめでダイアログ（上書きする・読み直す・やめる）が出る。入力を元に戻したら（未保存でなくなったら）、知らせを消して読み直した行で作り直す。「前回の入力」は入力を残しているときも今の DB の行で出す。
15. **応答が届かなかった保存**（設計 2.6「読み直して、値が自分の入れたものなら『保存されていました』」）：送った数を覚えておき（成功したら消す）、「もう一度」（保存の流れを最初から）で読み直した行がほかの人の保存に見えても、部屋の全品目の数が送った数と同じで、変わった行の数えた人がすべて自分なら（`isOwnSave`）、ダイアログを出さずに「保存されていました（hh:mm）」で終える（送り直さない）。その後に入力を変えていたら、読み直した行を元にしてその数で送る（確かめない）。→ 21. で変えた（送らずに知らせ、もう一度「保存」を押してもらう）。
16. **前年の数を読めないとき**：品目の行の「前年 …」を出さず、「前年の数を読み込めませんでした（理由）」と「前年の数を読み直す」を出す（前年がない「前年 —」と見分ける）。在庫一覧は前から ErrorState（「もう一度」）。
17. **下書きの書き出し**：500 ms の遅れと画面を外れるとき（unmount）に加え、`pagehide` と `visibilitychange`（hidden）でもすぐ書き出す（次の QR の URL を開く・スマホで裏に回る・タブを閉じる）。
18. **E2E の待ち方**：在庫入力の外側に `data-testid="stock-input"` と `data-fetching`（部屋の行・前年・名前・振り分けの合計のどれかを読んでいる間 "true"）を置き、`waitInput` は値に加えて "false" まで待つ。ほかの人の保存を SQL で入れる前に裏の読み込みが終わっていることを確かめる（読み直しで作り直す形にしたので、裏の読み込みが SQL の後に終わるとダイアログが出ない、というタイミングへの依存をなくした）。
19. **確かめる読み直しも通信できないとき**（設計 2.6「読み直しも通信できないときは…」。後の段の軽い指摘 a）：応答の届かなかった送信（送った数が残っている）があり、保存の前の読み直し（振り分けの合計・部屋の行）が network・unknown で失敗したら、ErrorBanner の代わりに「保存できたか確かめられません。通信が戻ったら「確かめる」を押してください」（`data-testid="stock-unconfirmed"`）を出し、入力を残して「保存」を押せなくする（入力の＋－は使える）。「確かめる」は部屋の行だけを読み直し（最新でない年度の確かめは出さない。読むだけなので）、自分の保存が入っていれば（15. と同じ `isOwnSave`）「保存されていました」で終える。その後に入力を変えていたら、読み直した行を元にして「前に送った数は保存されていました。その後に変えた数はまだ保存していません」と知らせ、保存は押せるようにする。入っていなければ「前に送った数は保存されていませんでした。もう一度「保存」を押してください」と知らせて送り直せる状態に戻す（ほかの人の保存が入っていれば、14. の読み直しの知らせが出て、保存のときにダイアログで選べる）。→ 文言とほかの人の保存があるときの分岐は 21. で変えた（ほかの人の保存があれば「保存されていませんでした」と言い切らず、ダイアログに回す）。「確かめる」の読み直しも通信できなければ、知らせを残したまま（toast で「まだ通信できません」）。応答が届いた失敗（conflict・state・forbidden など）では送った数を消す（何も保存されていないので、その後の通信の失敗を「確かめられません」にしない）。設計の文の『確かめる』は、画面では「確かめる」にした（入れ子の括弧は設計の文の中だけのため）。
20. **自分の保存が入ったかを見る元**（後の段の指摘）：送った数と一緒に、送る直前に読んだ部屋の行の updated_at（保存の前の読み直しの行。上書きならダイアログの行）を残し、「もう一度」「確かめる」ではそれと読み直した行を比べて `isOwnSave` を見る（入力の元〔base・下書きの base〕とは比べない）。確かめるまでの間に、通信が戻ったときの読み直し（TanStack Query の refetchOnReconnect）や「ほかの人の数を読み直す」で入力の元が自分の保存の入った行に変わることがあり、元と比べると変化がなく「保存されていませんでした」と事実と逆に知らせて送り直させていたため。ほかの人の保存のダイアログは、自分の保存で片づかなかったときだけ、これまでどおり入力の元と比べて出す。→ 未確定の間は、ほかの人の保存も送る直前の行と比べて見る（21.）。

21. **未確定の保存の決まり**（設計 2.6「通信の失敗の後の書き込み」をこの画面で1つにそろえた。後の段の指摘）：送った upsert の応答が届かず（network・unknown）、保存されたか分からない間を「未確定」とする（送った数と送る直前に読んだ行を `pending` に残す。応答の届いた失敗・保存できた・下の片づけで消す）。
    - (1) 未確定の間は、入力と入力の元を勝手に置き換えない。裏の読み直し（通信が戻ったときの refetchOnReconnect・ErrorBanner の「読み直す」・invalidate の後）でも、入力を変えていなくても置き換えない（14. の「未保存の入力がなければ作り直す」を未確定の間は止める）。
    - (2) どの読み直し（「確かめる」・「保存」「もう一度」の前・裏の読み直し）でも、まず `settleSent` で、送った値が入ったかを送る直前に読んだ行と比べて決める（20.）。入っていて、その後に入力を変えていなければ「保存されていました」で終える。入っていて、その後に入力を変えていれば「前に送った値は保存されていました。その後に変えた値はまだ保存していません」と知らせ、読み直した行を入力の元にして保存を押せる状態に戻す（送らない。「保存」「もう一度」で読み直したときも送らない）。
    - (3) 入っておらず、ほかの人の保存もなければ（送る直前の行から何も変わっていない）、「確かめる」と裏の読み直しでは「前に送った値は保存されていませんでした。もう一度「保存」を押してください」と知らせて送り直せる状態に戻す。「保存」「もう一度」の前の読み直しでは、押したのが送り直しなので、そのまま送る（設計の振り分けの「保存されたか分からないとき」の (2)「同じ変更をそのまま送り直してよい」と同じ）。
    - (4) ほかの人の保存があって、自分の保存か決められない（`isOwnSave` が偽）ときは「保存されていませんでした」と言い切らない。「確かめる」と「保存」「もう一度」ではほかの人の保存のダイアログ（上書きする・読み直す・やめる）を出す。裏の読み直しでは「ほかの人が保存しました」の知らせを出す（入力を変えていなくても出す）。どちらも入力は置き換えず、未確定のままにする（やめても、次の「保存」でもう一度選ばせる）。上書きすると送り直し、読み直す（ダイアログ・知らせのどちらでも）とほかの人の数を入力にして未確定を片づける。
    - (5) 読み直しも通信できなければ「保存できたか確かめられません。通信が戻ったら「確かめる」を押してください」を残したまま、送り直しを押せない（19.）。「確かめる」の読み直しも通信できなければ「まだ通信できません…」の toast を出してそのまま。
    - 裏の読み直しは、TanStack Query の部屋の行のクエリの更新（QueryCache の subscribe の success）を見て決める。送信が失敗した時点でキャッシュにあった行（送る前か送っている間に読んだもの）は使わず、それより後に届いた行だけで決める（`dataUpdateCount` で見分ける）。送る直前と、応答の届かなかった失敗の時点で、まだ届いていない部屋の行の読み込み（直前の保存・確かめる・rebased の後の invalidate、ErrorBanner の「読み直す」など）は `cancelQueries` で捨てる（届く行は送る前か送っている間に読んだものなので、送った値が入っていても「保存されていませんでした」と決めてしまうため）。保存・確かめるの流れの途中と、ほかの人の保存のダイアログを開いている間は、その流れ・選択が決めるので見送る。
    - 開き直したとき：送った値と送る直前に読んだ行（`sent`）は、送るときに下書きにも置く（送っている間と未確定の間。保存できた・応答の届いた失敗・決まったら消す）。画面を離れて（カメラで次の QR を読むなど）開き直したら、下書きの `sent` から未確定に戻し、**下書きの数（送った値と、その後に変えた値）をそのまま入力にする**（離れる前の入力に戻す。「戻す」の知らせは出さない。未確定の間に、戻していない下書きは残らない）。開いた後に最初に届いた部屋の行で (2)〜(4) と同じく決める（開いたときにキャッシュの行しかなければ読み直す）。どの読み直し（裏の読み直し・「保存」・「確かめる」）でも、今の入力＝画面の数で決める（入力がまだないときは、描画で作るのと同じ `openingCounts`）。入っていて入力が送った値なら「保存されていました」（下書きを消す）、違えば「前に送った値は保存されていました…」と知らせて読み直した行を元にする（知らせのとおり「保存」を押すと、ほかの人の保存のダイアログを出さずに後で変えた値を送る）。入っておらずほかの人の保存もなければ「保存されていませんでした」と知らせ、知らせのとおり「保存」を押すと画面の数（送ろうとした値）を送る。ほかの人の保存があれば言い切らずに知らせ、未確定のまま（「保存」でダイアログ。上書きすると画面の数を送る）。決まった後の下書きは、画面の数で書き直す（`sent` を外し、元を読み直した行にする。DB の数と同じときだけ消す）。前は下書きを戻すまで入力が DB の数のままで、知らせのとおり「保存」を押すと DB の数を送って下書きを消し、送ろうとした値が失われていた。
    - 送っている間に離れたとき：離れても送信（upsert）は続く。送っている書き込みはモジュールの `sendsInFlight`（下書きのキー → 終わると解決する Promise）に置き、開き直した画面は、それが終わるまで送信中（「保存中…」、入力も保存も押せない）として待ち、裏の読み直しでは決めない。終わったら、それまでに読んだ行・読んでいる行を使わず（`cancelQueries` と `dataUpdateCount`）、読み直した行で (2)〜(4) と同じく決める（届いていれば「保存されていました」）。離れた画面は、送信の結果で知らせ・下書き・キャッシュ・ダイアログを変えない（開き直した画面と同じキーの下書きを消して、自分の保存を「ほかの人の保存」に出すことをしない）。届いたときに下書きの `sent` がまだこの送信のものなら、下書きを消す（開き直さなかったときに、次に開いて「保存されていました」と出さないため）。失敗のときは何もしない（開き直した画面か、次に開いたときに読み直して決める）。
    - 流れの途中：「保存」の流れ（最新でない年度の確かめ・在庫超過の確かめを開いている間を含む）・「確かめる」・「上書きする」の間は、裏の読み直しで決めない（流れの中で読み直して決める）。前は最新でない年度の確かめを開いている間に裏の読み直しで「保存されていました」と決め、続けると流れの古い元の行と比べて自分の保存を「ほかの人が先に保存しています」（自分の名前）に出し、上書きで同じ値を二重に送っていた。phase は描画の後にしか変わらないので、すぐ変わる ref（`flow`）で見る。流れの間に届いて見送った行があり、流れの後も未確定なら、読み直して決める。

## T09a への申し送り

申し送った3件は、どれも T09a の f7bf2f4 で解決し、T10 はそれを取り込んだ（上の「仕上げの後の軽い指摘」の「T09a の取り込み」と「CountStepper」）。T09a に残っている申し送りはない。記録のために、申し送った内容と、どう解決したかを残す。

- （解決）**e2e/foundation.spec.ts の雛形の行**：T10 は当初、TICKET の型を `Record<string, string | null>` にして T10 の3ページを null にし、expectPlaceholder に null の分岐を足していた（T09・T11〜T13 も同じ行を直すとマージで衝突するので、T09a の側で先に形を入れてほしいと申し送った）。→ T09a の f7bf2f4 で foundation.spec.ts が雛形かどうかを見ない形（ALL_PAGES と expectOpens）になり、TICKET と expectPlaceholder の T10 の行は要らなくなった。取り込みのときの衝突は T09a の側を採って片づけた。
- （解決）**e2e/shots/T09a.shots.ts が T10 の雛形を前提にしていた**（「T09a 読み込み中」が /stocks/ の「この画面は準備中です（T10）」を待ち、「T09a 雛形のページ（スマホ）」が /stock/ の雛形を撮っていたので、T10 のマージの後は `pnpm e2e:shots --grep T09a` が落ちるはずだった）。→ T09a の f7bf2f4 で雛形を前提にしない形になった。
- （解決）**CountStepper のボタンが 36px**（size="icon"）で、設計 3.3 の「ボタンは 44px 以上」に足りず、在庫入力では className の `[&_button]:size-11 [&_input]:h-11` で大きくしていた（申請〔T11〕も同じなら size の引数を足すとよいと申し送った）。→ T09a の f7bf2f4 で `size="lg"`（ボタンと欄が 44px）ができ、在庫入力は className をやめて `size="lg"` にした。
- 共通基盤の不具合で先に進めなくなったことはなかった。

## T14 への申し送り

- **通しの流れの 3（部員が 390px で1部屋を同じ数のまま数え直す）**：`/stock/?room=<1-1 の id>` を開き、`getByRole('button', { name: '保存', exact: true })` を押す。シナリオの年度（2001 年）は seed の部員にとって最新でないので「最新でない年度（…）に保存します。よろしいですか」が出る → 「この年度に保存する」。保存の後は `data-testid="stock-saved"` と `last-counted`（「前回の入力：日時（テスト部員）」）。数えた人と日時が変わったことは stocks の counted_by・counted_at で見る（e2e/t10-stock.spec.ts の1件目に例）。同じ数なら「保存していない変更があります」は出ないが、保存は押せる。
- **basePath のスモーク**：/GAapp/stocks/qr/ の `data-testid="qr-url"` の文字が `http://localhost:3101/GAapp/stock/?room=` で始まること（stockUrl は lib/env.ts の BASE_PATH を使う）。
- **最初に読む JS**：/stock/ は gzip 322.7 KB（基準 394.8 KB）。uqr は /stocks/qr/ でだけ読む。
- **受け入れ（手で確かめる。設計 7.6）**：A4 に実際に印刷して、カードの大きさ（66mm 高）と QR を iOS・Android のカメラで読めること（とアプリの中のブラウザの案内）を確かめる。この環境では印刷と実機の読み取りは試していない（emulateMedia print の見た目だけ）。

## DB について

- DB の不具合・足りない RPC は見つからなかった。stocks の upsert（RLS の insert・update）、確定中の守り（tg_stocks_guard の invalid_state・E001）、previous_year_stocks、profiles の読み取りで足りた。
- 気づいたこと：createScenario が入れる stocks の行は postgres で入れるので counted_by が null（画面は「名前を表示できません」）。テストでは「前回の入力」の名前を、保存した後の名前で確かめた。
