## 確かめたこと（実際の Supabase で）

- `supabase db reset`：0001〜0006 と seed が通った。
- `supabase test db`：9 ファイル 4072 件、すべて ok（001 140・002 148・010 16・011 3438・012 35・020 76・021 65・022 61・023 93）。
- `pnpm gen:types` → `pnpm check:types` が一致。`pnpm lint`・`pnpm typecheck`・`pnpm test`（15 件）・`pnpm check:emails` が通る。
- PostgREST（kong 経由、publishable キーとローカルの JWT）で：
  - 自分の年度の years だけが返り、ロールのない人は `[]`。anon は表も RPC も 401（42501）。
  - RPC のエラーは HTTP 400 で `{"code":"P0001","message":"forbidden","details":""}`、conflict の details は `{"allocation_version": 0}` の JSON 文字列。jsonb の中の uuid でない値は invalid_input（22P02 は返らない）。ただし RPC のトップレベルの型つきの引数（uuid・enum・date・integer）は PostgREST が関数の前に変換するので、形が違うと 22P02・22007 などがそのまま返る（レビューの指摘。04 のエラーの説明に書いた）。
  - private の関数は `/rpc/has_role` で見つからず（PGRST202）、`Content-Profile: private` は PGRST106（公開していないスキーマ）。
  - previous_year_stocks は GET でも呼べる（STABLE）。
  - where のない DELETE は safeupdate で 400（21000）。
  - pg_graphql は無効（graphql/v1 は「extension is not enabled」）。
- 同時実行（設計 9.6 の (1)〜(3)。psql を2つ開いて、片方のトランザクションを pg_sleep で止めた）：
  - (1) 同じ版で save_auto_allocations を2つ：後の方が先の方のコミットまで待ち、その後 conflict（details に新しい版）。
  - (2) requesting の年度で update_year の途中（コミット前）に、部員が在庫を insert：待たされない（50ms）。在庫の update は守りのトリガーが年度の行を取るので、update_year のコミットまで待つ（想定どおり）。設計の「save_auto_allocations の途中に部員が在庫を insert」は、save_auto_allocations が allocating でしか動かず、allocating では部員は在庫を書けないので、update_year で試した。
  - (3) set_year_status(confirmed) の途中に、管理者が在庫を振り分けより少なくする update：確定のコミットまで待ち、その後 invalid_state（detail の code が E001）。
  - (4)〜(6) は T02 で確かめた（notes/T02.md）。

## 設計からの変更点

1. **抜け (e)**：使われていない `private.year_role` と `private.is_request_open` を消した。判定関数は 14 個 → 12 個（ポリシーが呼ぶものだけ）。010 の set_eq も 12 個。
2. **抜け (f)**：update_requests_after_deadline の p_submission は `{ submitted: true, note }` だけを受け付ける（後で submittedAt を足した。下の「レビュー（low）の修正」）。`submitted: false`（未提出に戻す）と知らないキーは invalid_input。未提出に戻すと D-07 で需要が変わるため（D-19）。04 の表に書いた。ロジック側の申し送り（取り込みの提出日時 submittedAt）は、この形に `submittedAt` を足せば入る（今は知らないキーとして invalid_input になる）。
3. **抜け (g)**：save_auto_allocations・set_consent に、形の誤り（クラス 22）と CHECK 違反（23514）を invalid_input に直す例外ブロックを足した。submit_requests・update_requests_after_deadline・check_delivery にも同じものを足した（どの RPC からも生の 23514 が返らない）。save_auto_allocations は数の上限（10000）を先に確かめる。set_consent の上限は、置き換えの合計が 10000 を超える行を作って確かめた。
4. **抜け (a)**：ポリシーの with check は更新後の行しか見ないので「year_id が変わらない」は書けない。T02 のトリガー guard_rules が止める（D-15）。011 で「両方の年度の admin でも、ルールを closed の年度・開いている別の年度へ移せない（invalid_input）」を確かめた。ポリシーの横にコメントで書いた。
5. **抜け (b)**：auth.users のトリガー・profiles の自動作成・フック・supabase_auth_admin の execute の検査は T03 のテストに入れていない。010 は「supabase_auth_admin が実行できる public・private の関数はない」を確かめる（T04 でフックだけの集合に変える）。招待の受け入れは、トリガーなしで動く invite と accept_my_invitations で確かめた（未確認のアカウントには付かない → 確認後に accept_my_invitations で付く）。
6. **抜け (c)**：T02 が足した fixture（staff・viewer が G4 の代表、rep が Y2 の viewer、staff あての使用済みの招待）で、year_roles(own) の rep、invitations(own) の staff、group_members(own) の staff・viewer が本当に行を返すことを確かめた。あわせて profiles(rep) の admin2（Y2 の admin から Y2 の viewer の rep が見える）と、requests(G4) の insert（staff・viewer が団体代表として書ける）のセルを足した。
7. **抜け (d)**：T02 のトリガーで直っている。012 で「逆順で入れると入れ替わる」「正順で同じ組を入れると重複」を authenticated で確かめた。
8. **抜け (h)**：04 のダッシュボードに、確定ボタンの版の渡し方を書いた（画面は T09・T13）。
9. **update_year の年度名**：設計の update_year は SET に `label = case … else label end` を常に入れていた。実際に試すと、値が同じでも SET に一意の列があると行のロックが「キーの更新」の強さになり、その年度を参照する行の insert（外部キーの FOR KEY SHARE。部員の在庫入力など）が update_year のコミットまで待たされた（1.5 秒止めたら 1.5 秒待った）。allocating では、外部キーの確認を済ませた在庫の insert と update_year が互いを待つデッドロックの元にもなる。年度名は変えるときだけ別の文で書くようにし、同じ確認で待たされない（50ms）ことを確かめた。set_year_status・版の増分（status・allocation_version だけを変える）は、この問題がないことも確かめた。
10. **revoke_invitation**：設計は招待の行を `for update` でロックしてからロールを確かめていた。ロールのない人にも行ロックを取らせてしまうので、ロールを確かめてからロックするようにした。見つからなければ forbidden（招待の年度が引けないので assert_role が止める。有無を漏らさない。021 で確かめる）。ロールを確かめた後に別の人が消していたときだけ not_found になる。
11. 権限表の期待値（設計の 122 行・732 セル）を、全6状態に広げた（既定の `*` と状態ごとの上書き）。設計で状態を1つしか試していなかったセル（rooms の closed、stocks の delete の confirmed、request_submissions の締切後など）も全状態で確かめる。

## セキュリティの観点での見直し（自分で）

- すべての RPC は SECURITY DEFINER・`search_path = ''`、execute は authenticated だけ（010）。最初にロールを確かめ、対象が見つからないときも forbidden にして有無を漏らさない（存在しない年度・団体・招待・受け渡しで確かめた）。ロールのない人に年度・招待の行ロックを取らせない（lock_year、revoke_invitation）。
- RPC の書き込みは RLS を通らないので、年度・団体の一致を RPC の中で確かめている（save_auto_allocations と save_allocation_rows の団体の年度、invite の団体の年度、save_allocation_rows の update・delete は p_year_id の行だけ）。
- private の判定関数は呼んだ人についてだけ答える。authenticated から直接呼べるが、PostgREST からは private が公開されていない（PGRST106）。答えは「自分にロールがあるか」「年度の状態」程度で、他人の情報は返さない。
- 残るもの（low、仕様どおり）：
  - invite の返り値 applied で、admin はそのメールの確認済みアカウントがあるかを知れる（招待の画面に必要。admin だけ）。
  - set_role は admin が uuid を知っている任意のユーザーにロールを付けられる（admin の画面は年度のメンバーの profiles しか見えないので、uuid を知る手段は限られる）。
  - update_year は request_open_at が request_close_at より後でも受け付ける（団体代表が書けない期間ができるだけ。画面で止める。T09）。
- 監査：invitations と profiles は個人情報を写さないので記録しない（D-11）。RPC の detail にメールは入れていない（invite は id だけを返す）。

## レビュー（low）の修正とロジック設計からの申し送り（2026-10-29）

1. **closed の例外**：02（設計上の決めごと・権限表の下）、D-17、04 の表を実装に合わせた。closed でもできるのは、ルールの memo、check_delivery、ロールを外す（remove_role）、団体代表を外す（remove_group_member）、未使用の招待の取り消し（revoke_invitation。年度の状態を見ない）。021 に「closed の年度の招待も取り消せる」を足した。
2. **set_role の分割**：外す操作を remove_role(p_year_id, p_user_id, p_reason) に分けた（生成した型で p_role が必須のため。null を書けない）。set_role は role が null なら invalid_input、closed では invalid_state。remove_role は closed でもでき、最後の admin は invalid_state（last_admin）、ロールがなければ not_found。010（RPC 17 個）・021・shared の型のテスト・04・D-17・SPEC を直した。
3. **update_year の1日目**：1日目を変えるとき、prev_year_id の年度より後で、この年度を prev_year_id に持つ年度より前でなければ invalid_input（field: festival_start）。create_year_from の「最新の年度」の判定（それを複製元にした年度も、1日目が同じか後の年度もない）を崩して、どの年度からも次の年度を作れなくなるのを防ぐ。020 に7件（同じ日・前・後、複製元の側の同じ日・後・前、変えた後も複製先から次の年度を作れる）。2人の admin が複製元と複製先の1日目を同時に変える競合は止めていない（関係する年度の行をロックするとデッドロックの元になる。どちらも admin の操作で、ほぼ起きない）。
4. **revoke_invitation**：上の 10 の説明を実装とテストに合わせた（forbidden）。
5. **守りのトリガーと RLS**：BEFORE ROW トリガーは with check より先に動くので、tg_room_years_guard（insert・update）、tg_stocks_guard・tg_groups_before_write（update・delete）が、拒否される書き込みでも年度の行をロックしていた。0004 で3つを置き換え、最初に `private.rls_applies()`（role の設定が anon・authenticated。postgres・service_role・テストの act_as は RLS を通らないので今までどおり守る）とポリシーと同じ条件（can_admin・can_write_stocks）を確かめ、書けなければロックせずに new（delete は old）を返す。RLS の判定は変えていない。update・delete はポリシーの using で行が先に絞られるのでもともと届かないが、同じ形にそろえた。RPC（SECURITY DEFINER）の中でも role は authenticated のままなので同じ条件を見る（今これらの表に書く RPC は create_year_from の room_years だけで、呼んだ人は新しい年度の admin）。012 で、lock_year_guard を呼び出しを数える関数に差し替え（数はシーケンス。副トランザクションの取り消しで消えない）、viewer・staff・団体代表・未招待の room_years の insert が今までどおり 42501、staff の update が0行で、ロックが0回、admin の書き込みでは守りが効く（invalid_state）ことを確かめた。置き換える前のトリガーではロックの検査が落ちることも確かめた。
6. **check_immutable**：private.tg_immutable_columns を SECURITY DEFINER にした（search_path = '' は T02 から）。authenticated の書き込みでも private.fail を呼べ、42501 でなく invalid_input になる。012 で staff の在庫・admin の団体の年度の変更が invalid_input になることを確かめた（011 は 42501 を denied に数えるので別に確かめた）。
