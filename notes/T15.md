# T15 作業記録（ロールの見直し：総務部門長・副部門長、店長・副店長、3つの段、兼任の禁止。DB）

ブランチ feat/T15-roles-db（origin/main 762e99a から）。T15 は DB だけを変える（0011〜0013 と pgTAP、それに伴う最小の型・テスト・エラーの対応表の直し）。今の画面（T14 までの版）は、本番にマイグレーションを流す前も後もそのまま動く。画面（ロールの表示名、段ごとのナビゲーションと設定、店長・副店長の表示と切り替え、兼任のエラーの出し方）は T15b、総務アプリの土台は T16。

この記録の最初の版（2026-10-31）は、SQL を書く前に設計を固めたもの。次の段の 0011〜0013 と pgTAP は「SQL の約束」に合わせて書く。合わないところが見つかったら、先に 02・04 とこの記録を直してから実装する。

## 目的とユーザーの決定（2026-10-31）

アプリを総務部門のアプリにする（T16 から）。その前に、ロールを DB で見直す。ユーザーの決定は次のとおり（D-48・D-49）。

1. **ロール**（app_role。年度ごとのまま。year_roles の主キーは (year_id, user_id) で、1人に年度ごと1つ）。列挙の並びは admin, head, deputy_head, staff, viewer。

   | 表示名 | 値 | |
   | --- | --- | --- |
   | 管理者 | admin | 今のまま |
   | 総務部門長 | head | 新しい |
   | 総務副部門長 | deputy_head | 新しい。権限は head と同じ |
   | 総務部門員 | staff | 今のまま |
   | 閲覧のみ | viewer | 今のまま |

2. **団体代表の立場**：新しい列挙 group_role（manager 店長、deputy_manager 副店長）。権限は同じで、表示名だけが違う。人数の上限はない。group_members.role は not null・既定 'manager'（今の団体代表は店長になる）。invitations.group_role は group_id があるときだけ持つ（CHECK）。
3. **3つの段**：管理者だけ／部門長以上（LEAD＝admin・head・deputy_head）／総務（SOUMU＝LEAD と staff）。どの判定がどの段かは次の「権限の段」の表。
4. **兼任の禁止**（年度ごと）：staff・head・deputy_head を year_roles に持つ人は、同じ年度の団体の group_members に入れない。admin と viewer は店長・副店長を兼ねられる。違う年度ならよい。トリガーで止め、invite は早めにエラーにし、招待の受け入れは重なる招待を飛ばす（例外を出さない）。0012 は、既に違反しているデータがあれば止まる。
5. **RPC の中の段**：部門長・副部門長が扱えるのは、staff のロールと団体代表（店長・副店長）だけ（招待・付ける・外す・取り消す）。管理者の招待を上書きさせない。
6. **エラー**：新しいコード role_overlap（P0001）。画面の種類は conflict、文言は「総務の部門員・部門長・副部門長は、同じ年度の団体の店長・副店長を兼ねられません（管理者と閲覧のみは兼ねられます）」。
7. **マイグレーション**：0011（列挙に値を足すだけ）・0012（group_role と兼任の禁止）・0013（段）。
8. **後方互換と出す順**：今の画面のまま動く（足した引数は既定値つき、引数名は変えない）。この DB の PR をマージ → ユーザーが migrate.yml を流す → T15b（画面）。

## SQL の約束（次の段はこれに合わせて書く）

### ロールの配列

- LEAD（部門長以上）：`'{admin,head,deputy_head}'`
- SOUMU（総務）：`'{admin,head,deputy_head,staff}'`
- 部門のロール（兼任できない）：`('head','deputy_head','staff')`

### 列挙型・列・CHECK

```sql
-- 0011_app_role_lead.sql（この2行だけ）
alter type public.app_role add value 'deputy_head' after 'admin';
alter type public.app_role add value 'head' after 'admin';
-- 結果の並び：admin, head, deputy_head, staff, viewer

-- 0012_group_roles_overlap.sql（最初のロックと違反の確かめは下の「兼任の禁止」）
create type public.group_role as enum ('manager', 'deputy_manager');
alter table public.group_members add column role public.group_role not null default 'manager';   -- 今の行は店長
alter table public.invitations add column group_role public.group_role;
update public.invitations set group_role = 'manager' where group_id is not null;               -- 今の団体の招待は店長
alter table public.invitations add constraint invitations_group_role_check
  check ((group_id is null) = (group_role is null));
```

- `alter type … add value` で足した値は、同じトランザクションの中では使えない（unsafe use of new value）。CLI（`supabase db reset`・`supabase db push`）はファイルごとに1トランザクションで流すので、新しい値を使うのは 0012 から（0012 の関数の本体と DO ブロック、0013 のポリシーと RPC のロールの配列）。
- group_members.role の追加は既定値つきの not null（PG 11 から表を書き直さない）。行の update ではないので、監査のトリガーは動かない。
- invitations の未使用の一意の索引（invitations_pending_group_key は (year_id, email, group_id)）は変えない。同じ団体に立場違いの未使用の招待を2つは作れず、招待し直すと立場が変わる。

### 兼任の禁止（0012）

補助の関数（任意の人について答えるので、誰にも execute を与えない。PUBLIC から外し、010 の判定関数の一覧に入れない。トリガー・RPC〔SECURITY DEFINER〕の中からだけ呼ぶ）：

```sql
-- 同じ年度・同じ人の「ロール」と「団体代表」の書き込みを順にする（トランザクションの終わりまで持つ）
create function private.lock_year_member(p_year_id uuid, p_user_id uuid)
returns void language sql set search_path = '' as $$
  select pg_advisory_xact_lock(hashtext('gaapp.year_member'), hashtext(p_year_id::text || '/' || p_user_id::text))
$$;

-- その年度で部門のロール（head・deputy_head・staff）を持つか
create function private.year_member_has_department_role(p_year_id uuid, p_user_id uuid)
returns boolean language sql security definer set search_path = '' as $$
  select exists (select 1 from public.year_roles yr
                 where yr.year_id = p_year_id and yr.user_id = p_user_id and yr.role in ('head', 'deputy_head', 'staff'))
$$;

-- その年度の団体の代表（店長・副店長）か
create function private.year_member_in_group(p_year_id uuid, p_user_id uuid)
returns boolean language sql security definer set search_path = '' as $$
  select exists (select 1 from public.group_members gm join public.groups g on g.id = gm.group_id
                 where g.year_id = p_year_id and gm.user_id = p_user_id)
$$;
```

- 3つとも VOLATILE（既定のまま。STABLE にしない）。ロックを待った後で、待っている間に確定した行を読むため（READ COMMITTED では、VOLATILE の関数の中の問い合わせごとに新しいスナップショットになる）。呼ぶ側も、ロックを取る文と確かめる文を分ける（同じ文の中で取って読まない）。

トリガー（名前は両方の表で `check_role_overlap`。BEFORE ROW のトリガーは名前の順に動くので、check_immutable の後、set_timestamps の前）：

```sql
create function private.tg_year_roles_check_overlap()
returns trigger language plpgsql security definer set search_path = '' as $$
begin
  perform private.lock_year_member(new.year_id, new.user_id);
  if new.role in ('head', 'deputy_head', 'staff') and private.year_member_in_group(new.year_id, new.user_id) then
    perform private.fail('role_overlap', jsonb_build_object('year_id', new.year_id, 'user_id', new.user_id));
  end if;
  return new;
end $$;
create trigger check_role_overlap before insert or update of role, user_id on public.year_roles
  for each row execute function private.tg_year_roles_check_overlap();

create function private.tg_group_members_check_overlap()
returns trigger language plpgsql security definer set search_path = '' as $$
declare v_year_id uuid := (select g.year_id from public.groups g where g.id = new.group_id);
begin
  if v_year_id is null then return new; end if;   -- 団体がなければ外部キーのエラー（23503）に任せる
  perform private.lock_year_member(v_year_id, new.user_id);
  if private.year_member_has_department_role(v_year_id, new.user_id) then
    perform private.fail('role_overlap', jsonb_build_object('year_id', v_year_id, 'user_id', new.user_id));
  end if;
  return new;
end $$;
create trigger check_role_overlap before insert or update of user_id, group_id on public.group_members
  for each row execute function private.tg_group_members_check_overlap();
```

- ロックの鍵：`pg_advisory_xact_lock(hashtext('gaapp.year_member'), hashtext(year_id::text || '/' || user_id::text))`（int4 の2つの鍵。pg_locks には locktype = 'advisory'、classid と objid に符号なしの数、objsubid = 2 で出る）。年度・人の組が違えば待たない。ハッシュが偶然ぶつかっても、余分に待つだけ。
- 年度の行はロックしない（lock_year_guard・lock_year も、for share・for update・for no key update も書かない）。在庫の保存・submit_requests の lock_year_guard（for share）とぶつかり、GoTrue のログインのトランザクション（on_auth_user_confirmed → 受け入れ）を長い振り分けの保存の後ろで待たせ、年度をまたいでデッドロックし得るため。year_roles・group_members の insert の外部キーの確かめ（years・groups の for key share）は、lock_year の for no key update とぶつからない。
- 違反は `role_overlap`（P0001。message は 'role_overlap'、detail は `{"year_id": …, "user_id": …}`。メールは入れない）。
- 店長⇄副店長（group_members の role だけの update）ではトリガーは動かない（update of の列に role を入れない）。year_roles の update of role は、staff → viewer のような向きでもロックを取って確かめる（向きで分けない）。
- set_role の `insert … on conflict do update` では、BEFORE INSERT と BEFORE UPDATE の両方で動く（どちらも同じ結果。ロックは同じトランザクションで重ねて取れる）。
- groups.year_id・group_members.group_id・year_roles.year_id は check_immutable で変えられないので、行の付け替えで重なりを作る道はない。

0012 の最初（型・列・関数・トリガーより前）：

```sql
lock table public.year_roles, public.group_members in share row exclusive mode;
do $$
begin
  if exists (select 1 from public.year_roles yr
             join public.group_members gm on gm.user_id = yr.user_id
             join public.groups g on g.id = gm.group_id and g.year_id = yr.year_id
             where yr.role in ('head', 'deputy_head', 'staff')) then
    raise exception 'role_overlap: 同じ年度で部員（staff）のロールと団体代表を兼ねている人がいます。README の「5. 本番 DB への適用」の問い合わせで探して直してから、もう一度 migrate.yml を流してください';
  end if;
end $$;
```

- 表を先にロックするのは、確かめてからトリガーを作るまでの間に、受け入れ（ログイン）などが重なる行を入れないようにするため（トリガーができるまでは止めるものがない）。ロックは 0012 のトランザクションの終わりまでで、その間（1秒もかからない）のログインは待つだけ。
- 止まったときは 0012 の変更は何も残らない（0011 は先に確定して残るが、害はない。流し直すと 0012 から続く）。

5. 同じ年度・同じメールに未使用のロールの招待があり、admin でなく role を渡していて、その招待のロールが staff 以外なら forbidden（head・deputy_head に、管理者・部門長・副部門長・閲覧のみの招待を上書きさせない。今の `on conflict … do update set role` の抜け道をふさぐ）

### 招待の受け入れ（apply_invitations。0013 で置き換え）

引数・返り値・SECURITY DEFINER・search_path・権限は今のまま（create or replace）。

```sql
for inv in
  select i.id, i.year_id, i.role, i.group_id, i.group_role
  from public.invitations i join public.years y on y.id = i.year_id
  where i.email = lower(btrim(p_email)) and i.used_at is null and y.status <> 'closed'
  order by i.created_at, (i.role is null), i.id      -- 同じ時刻（同じトランザクション）ならロールの招待を先に
  for update of i
loop
  perform private.lock_year_member(inv.year_id, p_user_id);
  if inv.role is not null then
    if inv.role in ('head', 'deputy_head', 'staff') and private.year_member_in_group(inv.year_id, p_user_id) then
      continue;                                        -- 兼任になる：使用済みにしない・数えない
    end if;
    insert into public.year_roles (year_id, user_id, role) values (inv.year_id, p_user_id, inv.role)
    on conflict (year_id, user_id) do nothing;
    if not found and not exists (select 1 from public.year_roles yr
      where yr.year_id = inv.year_id and yr.user_id = p_user_id and yr.role = inv.role) then
      continue;                                        -- 別のロールを持つ（0009 のまま）
    end if;
  else
    if private.year_member_has_department_role(inv.year_id, p_user_id) then
      continue;                                        -- 兼任になる
    end if;
    insert into public.group_members (group_id, user_id, role) values (inv.group_id, p_user_id, inv.group_role)
    on conflict (group_id, user_id) do nothing;
    if not found and not exists (select 1 from public.group_members gm
      where gm.group_id = inv.group_id and gm.user_id = p_user_id and gm.role = inv.group_role) then
      continue;                                        -- その団体に別の立場でいる（0009 と同じ扱い）
    end if;
  end if;
  update public.invitations set used_at = now() where id = inv.id;
  v_n := v_n + 1;
end loop;
```

- 例外を出さない。on_auth_user_confirmed・on_auth_identity_created は GoTrue のトランザクションの中で動き、例外はログインの失敗（「Database error …」）になる。先に同じロックの下で、トリガーと同じ関数で確かめるので、insert のトリガーは role_overlap を出さない（insert … on conflict do nothing でも BEFORE INSERT のトリガーは動くので、確かめは insert の前に置く）。
- 1回の呼び出しの中でも順に効く：同じ年度の staff の招待を先に付けたら、その後の団体の招待は飛ばす（同じトランザクションの行は見える）。
- 呼ばれる所：accept_invitations_of（0007。on_auth_user_confirmed・on_auth_identity_created）、accept_my_invitations、invite。

### 014 で確かめること（兼任の禁止。postgres のまま直接書く）

- 両方の向き：staff → 同じ年度の団体代表の insert は role_overlap。団体代表 → 同じ年度の staff・head・deputy_head の insert は role_overlap。detail が `{"year_id": …, "user_id": …}` そのもの（メールなし）。
- update の道：year_roles の viewer → staff（閲覧のみの店長。「viewer→staff」）、year_roles の user_id を店長に付け替える、group_members の user_id を staff に付け替える、はどれも role_overlap。staff → viewer にした後なら団体代表に入れる。
- 兼ねてよいもの：admin と店長、viewer と副店長（同じ年度）。違う年度なら staff と店長も、どちらの順でも入る。
- 店長⇄副店長（role だけの update）は通り、トリガーが動かない（pg_trigger の列でも確かめる）。
- 団体がない group_members の insert は 23503（role_overlap にしない）。
- ロックの鍵：year_roles に1行入れた後、このトランザクションが pg_locks に locktype = 'advisory'、classid = hashtext('gaapp.year_member')、objid = その年度と人の hashtext（int4 を符号なしの oid に直して比べる）、objsubid = 2 のロックを持つ。
- 書き方の決まり：トリガー関数2つと lock_year_member の本体（pg_get_functiondef）に、for share・for update・for no key update・lock_year がない（年度の行をロックしない）。兼任の補助3つは VOLATILE で、authenticated・anon が実行できない。

### 024 で確かめること（RPC の段。authenticated で）

全部の RPC を head・deputy（と staff・viewer・rep・outsider・admin2）で呼び、「権限の段」の表のとおりに forbidden か通るかを確かめる。そのうえで：

- invite（head・deputy）：staff の招待と団体の招待（店長・副店長）はできる。admin・head・deputy_head・viewer の招待は forbidden。未使用の admin（と viewer）の招待のあるメールに staff を招待すると forbidden で、その招待は admin のまま（管理者の招待を上書きできない）。未使用の staff の招待は招待し直せる。group_role だけを渡すと invalid_input（field: group_role）。
- set_role（head・deputy）：ロールのない人と staff の人に staff を付けられる。viewer・admin・head の人に付けるのは forbidden。staff 以外を付けるのは forbidden。
- remove_role（head・deputy）：staff は外せる（その人あての未使用のロールの招待も消える）。viewer・admin・deputy_head の人は forbidden。ロールのない人は not_found（forbidden より先）。
- revoke_invitation（head・deputy）：staff の招待と団体の招待は取り消せる。admin・viewer の招待は forbidden で、消えていない。見つからない招待も forbidden。
- set_group_member_role：head・deputy・admin は店長⇄副店長を切り替えられ、監査に残る。staff・viewer・rep・admin2 は forbidden。団体がなければ forbidden、団体代表でなければ not_found、group_role が null なら invalid_input、closed は invalid_state。
- remove_group_member：head は外せる（closed でも）。
- 読み取り：head・deputy は Y1 の year_roles・group_members の全行、staff と団体の招待（viewer の招待は見えない）、Y1 の履歴（年度のない行は見えない）を読める。

### 受け入れで確かめること（030 と 024）

- apply は例外を出さず、飛ばした招待は未使用のまま：Google の経路（未確認で insert → 同じトランザクションで確認済みに update）で、同じ年度の未使用の staff の招待と団体の招待を持つ人がログインしても失敗せず、staff だけが付き、団体の招待は未使用で、件数に数えない。先に店長になっている人の未使用の staff の招待、先に staff の人の未使用の団体の招待、副店長の人への同じ団体の店長の招待も、同じく未使用のまま。次の accept_my_invitations も 0 件。
- 違う年度の招待は両方付く（Y1 の staff と Y2 の団体）。admin・viewer のロールの招待と団体の招待は両方付く。

### 同時実行（psql を2つ開き、片方のトランザクションを止めて確かめる。T03 と同じやり方。結果をこの記録に書く）

1. A：begin; year_roles に (Y, U, staff) を入れて止める。B：同じ Y の団体に U を入れる → B は待ち、A の commit の後に role_overlap。
2. 1 の逆の順（A が group_members に入れ、B が year_roles の staff の insert と、viewer → staff の update）→ B は待ち、A の commit の後に role_overlap。
3. A が (Y1, U)、B が (Y2, U) を入れる → B は待たない（鍵が違う）。
4. A が `select … from public.years where id = Y for no key update`（長い振り分けの保存の代わり）を持ったまま、B が auth.users の email_confirmed_at を update して（初回ログイン）Y の招待を受け入れる → B は待たない。A が `for share`（在庫の保存の代わり）のときも同じ（トリガーは年度の行をロックせず、外部キーの for key share はどちらともぶつからない）。
5. A：begin; invite(Y, X, 'staff') をして止める。B：invite(Y, X, 団体) → B は年度の行で待ち、A の commit の後に role_overlap（pending_invitation）。
6. A：受け入れの途中（ロックを持つ）。B：set_role(Y, U, 'staff') → B は待ち、A の結果に合わせて role_overlap か成功。

## 判断したこと（ユーザーの決定にないもの）
