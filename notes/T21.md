| save_lending_assignments(year_id, changes) | 部門長以上 | changes＝[{ groupId, itemId, count, updatedAt }]（1000 件まで）を1回で保存する（全部か何も）。行ごとに updated_at の楽観ロック（ミリ秒まで）。行がないのに updatedAt がある、または行があるのに null なら conflict（detail は団体と備品）。終了の年度・確定中は invalid_state。在庫を超えても保存はできる（確定で止める）。理由「テント等の割り当て」を置く（→ 判断したことの 5：count が null なら行を消す） |
| set_lending_confirmed(year_id, confirmed, reason) | 部門長以上 | 確定は、受付の締切を過ぎた（または振り分け中以降）・在庫超過がない・申請があるのに割り当てがない組がない、のときだけ。違えば invalid_state（detail の reason は before_deadline・over_stock・unassigned と、備品の id）。解除は理由が要る（reason_required）。同じ状態への変更と、終了の年度は invalid_state |

エラーは今のコードだけを使い、forbidden → invalid_state → invalid_input → conflict の順に返す。新しいコードは足さない（lib/errors.ts は文言を足すだけ）。

#### 2.6 トリガー・ロック

- **申請できる区分**：lending_requests で数が1以上なのに、団体の区分が備品の requestable_categories にないと invalid_input（field: lending_item_id、reason: not_requestable）。他の表を見る CHECK は使わない。
- **確定中の在庫の守り**：確定中は、在庫をその備品の割り当て合計より少なくできない（invalid_state）。申請・割り当て・記録のある備品は消せない（restrict）。
- **set_actor**：updated_by に auth.uid() を入れる（クライアントの値は使わない。seed・SQL Editor では入れた値のまま。D-10）。関数は表ごとの名前にする（T18 と同じ）。
- **ロック**：
  - 確定・解除・割り当ての保存・在庫の守りは、年度ごとの勧告的ロック（排他）で順に処理する。
  - years の行はロックしない（机椅子の版・確定の RPC とぶつけないため）。
  - 申請と記録はロックしない。
- **机椅子との関係**：版は増やさない。机椅子の確定中の守りも付けない。年度の複製（create_year_from）は写さない（画面の「前年度から読み込む」で写す）。

#### 2.7 番号・型

- `0018_lending.sql`（リードの割り当て。T19 の 0016・T20 の 0017 と並行に作る。計画のときは「0016〔目安〕、T19・T20 が先にマージしたら付け直す」だった）。今の表・関数・ポリシーは変えない。
- 積み直した後に `pnpm gen:types` と `pnpm check:types` を流す。lib/rpc/payloads.ts に、3つの RPC の zod を足す。

4. 確定後：店長がタブで割り当てを見る。閲覧のみが /lending を読む（申請の列なし）。部門員は割り当てを直せない
5. 部門員（スマホ）が渡した・返った・破損を記録する。2つのセッションの保存がぶつかる場合も確かめる
6. ダッシュボード：2日目の年度で、総務と店長に未返却、部門長に在庫超過と確定の要対応が出る
7. 確定を解除（理由）→ 直す → 確定する
8. 終了した年度は3画面とも読むだけ

あわせて：
- 今の E2E のナビの期待値に「テント等の貸し出し」を足す（foundation・auth・roles・t15b・t16・t17・t18）。
- t11（申請）の E2E がそのまま通ることを確かめる。

**スクリーンショット**（e2e/shots/T21.shots.ts → notes/T21/）
- /lending（PC）：確定前・在庫超過・確定中・部門員・閲覧のみ。備品と確定のダイアログ。

### 7. 速さ

- スマホの画面は 4G で 2 秒以内にする。/request（店長）・/lending/records（部員）・/（店長）を `pnpm e2e:perf` で計る。
- /request：
  - 机・椅子のタブの読み込みに足すのは、タブを出すかを決める備品の読み取り1本だけ（並行に読む）。

```sql
-- 列挙型は足さない（申請できる区分は group_category）

-- 貸し出す備品（年度ごと）
create table public.lending_items (
  id uuid primary key default gen_random_uuid(),
  year_id uuid not null references public.years on delete cascade,
  name text not null,
  unit text not null default '個',
  stock integer not null,
  requestable_categories public.group_category[] not null default '{stall,department}',
  sort_order integer not null default 0,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  -- 名前・単位は前後の空白（notices の題名と同じ 25 文字）のない形（画面は zod の trim を通してから送る。判断したことの 2）
  constraint lending_items_name_check check (name <> ''
    and name = btrim(name, E'\t\n\u000b\f\r \u00a0\u1680\u2000\u2001\u2002\u2003\u2004\u2005\u2006\u2007\u2008\u2009\u200a\u2028\u2029\u202f\u205f\u3000\ufeff')
    and length(name) <= 100),
  constraint lending_items_unit_check check (unit <> ''
    and unit = btrim(unit, E'\t\n\u000b\f\r \u00a0\u1680\u2000\u2001\u2002\u2003\u2004\u2005\u2006\u2007\u2008\u2009\u200a\u2028\u2029\u202f\u205f\u3000\ufeff')
    and length(unit) <= 10),
  constraint lending_items_stock_check check (stock between 0 and 10000),
  constraint lending_items_categories_check check (cardinality(requestable_categories) <= 4),
  constraint lending_items_year_id_name_key unique (year_id, name),
  constraint lending_items_id_year_id_key unique (id, year_id)      -- 子の3表の複合外部キーの参照先
);

-- テント等の申請（団体×備品。数だけ。備考はない）
create table public.lending_requests (
  group_id uuid not null,
  lending_item_id uuid not null,
  year_id uuid not null references public.years on delete cascade, -- 判断したことの 1
  count integer not null,
  updated_by uuid references auth.users on delete set null,        -- DB が入れる（set_actor）
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),

  constraint lending_requests_group_fkey foreign key (group_id, year_id)
    references public.groups (id, year_id) on delete cascade,

    references public.lending_items (id, year_id) on delete restrict
);
create index lending_requests_year_id_idx on public.lending_requests (year_id);
create index lending_requests_item_idx on public.lending_requests (lending_item_id, year_id);

-- 割り当て（団体に貸す数。0 は「貸さない」と決めたこと。行がなければ未入力）
create table public.lending_assignments (
  group_id uuid not null,
  lending_item_id uuid not null,
  year_id uuid not null references public.years on delete cascade,

  updated_by uuid references auth.users on delete set null,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  primary key (group_id, lending_item_id),

  lending_item_id uuid not null,
  year_id uuid not null references public.years on delete cascade,
  lent_count integer not null default 0,
  returned_count integer not null default 0,

create table public.lending_years (
  year_id uuid primary key references public.years on delete cascade,
  confirmed_at timestamptz,
  confirmed_by uuid references auth.users on delete set null,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),

alter table public.lending_items enable row level security;   -- 5表とも
```

- 外部キーの on delete：年度・団体へは cascade（年度や団体を消すと、その下の行も消える）、備品へは restrict（申請・割り当て・記録のある備品は消せない。直接の削除は 23503 で、画面は「ほかのデータから使われているので削除できません」の代わりに「申請・割り当て・記録のある備品は削除できません」と出す）、記録のための人（updated_by・confirmed_by）は set null。
- 子の3表（申請・割り当て・記録）は year_id → years（cascade）も持つ（判断したことの 1）。
- 申請・割り当て・記録の year_id は、画面・RPC が団体の年度を入れて送る（複合外部キーが、団体と備品が行と同じ年度であることを保証する。違えば 23503）。

### ロック

- 補助 `private.lock_lending_year(p_year_id uuid) returns void`：`pg_advisory_xact_lock(hashtext('gaapp.lending'), hashtext(p_year_id::text))`（年度ごとの排他。VOLATILE。authenticated には execute を与えない。DEFINER の RPC とトリガーの中からだけ呼ぶ）。

- デッドロックにならないこと：RPC は勧告的ロック → 割り当て・確定の行の順に取り、備品の行は外部キーの確かめの FOR KEY SHARE だけ（在庫の更新の FOR NO KEY UPDATE とはぶつからない）。guard_stock は備品の行 → 勧告的ロックの順だが、勧告的ロックを持つ RPC は備品の行を待たないので、輪にならない。
  - （→ 0018 で変えた）名前も書き直す備品の編集（FOR UPDATE。unique (year_id, name) の列を書く）は外部キーの確かめの FOR KEY SHARE ともぶつかる。その編集が guard_stock で勧告的ロックを待つ間に、割り当ての insert の外部キーの確かめが備品の行を待つとデッドロックになる（2つのセッションで再現した）。そこで save_lending_assignments は、勧告的ロックの前にその年度の備品の行を FOR KEY SHARE で取る（順は「備品の行 → 勧告的ロック → 割り当て・確定の行」にそろう。2つのセッションで解消を確かめた）。set_lending_confirmed は備品の行を読むだけで、待たない。

### RPC（SECURITY DEFINER・`search_path = ''`。execute は authenticated だけ）

**save_lending_assignments(p_year_id uuid, p_changes jsonb) returns jsonb**

- p_changes：1〜1000 件の配列。1件は `{ "groupId": uuid, "itemId": uuid, "count": 0〜10000 の整数 | null, "updatedAt": 日時の文字列 | null }`（4つのキーを見る。ほかのキーは見ない）。count が null なら行を消す（未入力に戻す。判断したことの 5）。
- エラーの順（029 はこの順で確かめる）：
  1. forbidden：その年度の部門長以上でない（年度がない・p_year_id が null も）。勧告的ロックの前に確かめ、取った後にもう一度確かめる
  2. invalid_state：年度が終了（detail `{status: 'closed'}`）→ 割り当ての確定中（detail `{reason: 'confirmed'}`）
  3. invalid_input：p_changes が配列でない・0 件・1000 件を超える（`{field: 'changes'}`）→ 要素の形が違う（`{field: 'changes', reason: 'shape'}`）→ 同じ団体・備品が2回（`{field: 'changes', reason: 'duplicate'}`）→ その年度にない団体（`{field: 'groupId', reason: 'not_in_year', group_id}`）→ その年度にない備品（`{field: 'itemId', reason: 'not_in_year', lending_item_id}`）
  4. conflict：changes の順に行を `for update` で読み、行があるのに updatedAt が null、行がないのに updatedAt がある、updatedAt が行の updated_at とミリ秒までで違う（`date_trunc('milliseconds', …)`）のどれか（detail `{group_id, lending_item_id}`。最初の1つ）
  5. 理由「テント等の割り当て」を置き（`private.set_reason`）、changes の順に書く：count が数なら insert か update（同じ数でも書く。updated_at が進む）、null なら delete（行がなく updatedAt も null なら何もしない）
- 全部か何も（どこかで止まれば全体を取り消す）。在庫を超えても保存できる（確定で止める）。区分で申請できない団体（企業・休憩所など）にも入れられる。
- 例外の読み替え：関数の中の 22xxx（jsonb の中の uuid・日時の形）と CHECK 違反は invalid_input（`{field: 'changes'}`）、外部キーの違反（確かめた後に団体・備品が消えた）は invalid_input（`{field: 'changes', reason: 'not_in_year'}`）。生の SQLSTATE を返さない（D-19）。
- 返り値：changes の順の配列 `[{ "groupId", "itemId", "count", "updatedAt" }]`（消した行・何もしなかった行は count と updatedAt が null。updatedAt は行の updated_at の文字列）。画面は返った updatedAt を次の保存の版にする。

**set_lending_confirmed(p_year_id uuid, p_confirmed boolean, p_reason text default null) returns public.lending_years**

- エラーの順：
  1. forbidden：その年度の部門長以上でない（年度がない・p_year_id が null も）。勧告的ロックの前と後に確かめる
  2. invalid_state：年度が終了（`{status: 'closed'}`）
  3. invalid_input：p_confirmed が null（`{field: 'confirmed'}`）
  4. invalid_state：今と同じ状態（`{reason: 'unchanged', confirmed: 今の状態}`。確定中の確定・確定前の解除）
  5. 解除だけ：理由が空なら reason_required、500 字を超えれば invalid_input（`{field: 'reason'}`。`private.set_reason(p_reason, true)`）
  6. 確定だけ：締切の前（`{reason: 'before_deadline'}`）→ 在庫超過（`{reason: 'over_stock', lending_item_ids}`）→ 未入力（`{reason: 'unassigned', lending_item_ids}`）
  7. 書く：確定は lending_years の行を作るか直して confirmed_at = now()・confirmed_by = auth.uid()、理由は「テント等の割り当ての確定」（p_reason は使わない。判断したことの 10）。解除は confirmed_at・confirmed_by を null にし、理由は p_reason
- 締切の後：年度が受付中で request_close_at が null でなく now() 以降、または振り分け中・確定（判断したことの 6。準備中は締切の日時によらず前）。
- 在庫超過：備品ごとの割り当て合計 > 在庫（未入力の組は数えない。判断したことの 7）。未入力：申請の数が1以上なのに、その団体・備品の割り当ての行がない組。lending_item_ids は該当する備品の id を備品の並び（sort_order → name → id）で。
- 返り値：lending_years の行（解除の後は confirmed_at が null）。

**previous_year_lending_items(p_year_id uuid) returns table (name text, unit text, stock integer, requestable_categories public.group_category[], sort_order integer)**

- `language plpgsql stable`。最初に `private.assert_role(p_year_id, '{admin,head,deputy_head}')`（でなければ forbidden）。年度の prev_year_id の備品を sort_order → name → id の順に返す（前年度がなければ 0 行）。年度の状態によらず読める（previous_year_stocks・previous_year_requests と同じ）。書き込みはしない。

## 判断したこと（計画にないもの・計画の読み方）

1. **子の3表に years への外部キー**（申請・割り当て・記録の year_id → years、cascade）：計画の外部キーは、団体へ cascade、備品へ restrict。年度を消すと、years からの連鎖（団体の削除と備品の削除）は after トリガーで順に処理され、その順はトリガーの名前（OID）で決まる。備品の削除が先に動くと、restrict の確かめが、団体からの連鎖で消える前の申請を見て止まりうる（OID の桁が変わると名前の順が入れ替わる）。子の表が years からも直接 cascade で消えれば、restrict の確かめ（連鎖の次の回に動く）より先に必ず消えるので、年度の削除が順によらず通る（pgTAP・E2E のシナリオの年度の片付けで年度を消す）。団体の削除と備品の削除の意味は計画のまま。
2. **名前・単位の CHECK**：計画の「名前は空白だけ不可で 100 字まで」を、events の題名と同じ形（前後に 25 文字の空白がない・空でない）にした。unique (year_id, name) が「テント」と「テント 」を別の名前にしないため。画面は zod の trim を通してから送る（予定と締切と同じく、DB では除かない）。単位も同じ形で 10 字まで。
3. **ビュー v_lending_totals を作らない**：計画では目安だった。ダッシュボードのカードの「申請 9 団体・割り当て 9 団体」「渡した 8／9 団体」は団体ごとの数が要り、備品ごとの合計のビューでは足りない。机椅子（counts.ts）と同じく、軽い読み取り（確定の行・備品・申請〔1以上〕・割り当て・記録の要る列）と、/lending と同じ数え方の関数（lib/modules/lending/counts.ts）にする。ダッシュボードと /lending で数が食い違わない（D-52 の理由）。001・010・030 のビューの分はなくなる。
4. **確定の印**：lending_years の行は消さず、解除は confirmed_at と confirmed_by を null にする（計画の「行がなければ確定前」に、「confirmed_at が null なら確定前」を足した）。履歴では、確定と解除が同じ行の「変更」（確定した日時 → なし。理由つき）として並ぶ。
5. **割り当ての count に null**：計画の changes の形（{ groupId, itemId, count, updatedAt }）で、count が null なら行を消す（未入力に戻す）。間違って入れたセルを空に戻すため。応答が届かずに送り直すと、行がないのに updatedAt がある conflict になり、読み直すと入力と同じ（行がない）なので「保存されていました」とする（(B1)）。
6. **確定の「締切の後」**：年度が受付中で締切（request_close_at）を過ぎた、または振り分け中・確定。準備中は、締切の日時を過ぎていても前とする（受付を始めていないので、団体の申請がまだない）。終了は 2 の invalid_state。机椅子の「締切後」（受付中の締切後と振り分け中以降）と同じ読み方。
7. **在庫超過の2つの見方**：DB の確定の確かめ（over_stock）と /lending の「在庫を超えています（確定できません）」は、割り当て合計 > 在庫（未入力は unassigned で別に止める）。ダッシュボードの「直していない在庫超過」とカードの「在庫を超える備品 N」は、割り当て合計＋未入力の組の申請の合計 > 在庫（計画の「割り当て合計が在庫を超える、または未入力が残っていて申請合計が在庫を超える」を、未入力を申請どおりに入れたときの合計で読んだ。未入力が残っていても、申請どおりに入れて在庫に収まるなら出さない）。/lending の「申請が在庫を超えています」は申請合計 > 在庫のまま。
8. **申請できる区分の確かめの前に RLS の段**：check_requestable は、書けない人（RLS の insert・update のポリシーで拒まれる人）には区分を確かめずに new を返す（拒否を RLS に任せる。02 の「トリガーは最初に、書いている人がその表に書けるかを確かめる」と同じ。011 のセルが 42501 になり、書けない人に備品の区分を漏らさない）。
9. **申請と記録を消さない**：計画の表の権限のとおり、delete を与えない。0 にして残す（申請の「すべて 0」は「テント等を借りない」申請として残る）。団体・年度の削除の連鎖では消える。
10. **確定の理由**：確定の理由は決まった文「テント等の割り当ての確定」（計画の 5）。p_reason は解除のときだけ使う（確定のときに渡しても使わない）。
11. **書いた人の id が見える**：店長・副店長と閲覧のみにも、読める行の updated_by・confirmed_by（uuid）が見える（RLS は列を隠せない）。名前（profiles）は読めない（can_see_profile）。画面は店長・副店長と閲覧のみに書いた人を出さない（お知らせ・締切と予定と同じ）。
12. **終了の年度の要対応**：終了の年度では、テント等の要対応を作らない（書けないので、押しても何もできない）。カードは出す。
13. **前年度から読み込む**：画面はその年度の備品が 0 件のときだけ出す（計画の 3.3）。前年度の備品を、画面が作った id で1回の insert（配列）で入れる（同じ名前は unique で止まる）。
14. **年度の複製で写さない**：計画の 2.6 のとおり、create_year_from は変えない。020 で、複製元に備品・申請・割り当て・記録・確定があっても、複製した年度に写らないことを確かめる（T18A-1 と同じ）。
15. **店長・副店長のダッシュボードの読み取り**：割り当てと記録を、備品の名前・単位・並びを埋め込んで（`lending_items(name, unit, sort_order)`。複合外部キーの関係）2本だけ読む。確定の行は読まない（割り当ては確定後にしか返らないので、行があれば確定後。割り当ての要対応は行があるときだけ作る）。
16. **受け渡し・返却の一覧に出す団体**：既定は、割り当て（1以上）か記録のある団体。探す欄に入れたときは、その年度の全部の団体から探す（割り当てのない団体に渡したときも記録できる）。
17. **履歴の列の名前**：計画の「表と列の名前を足す」のとおり、テント等の5表だけ、変わった列の名前を日本語にする（ほかの表は今のまま列名。lib/labels.ts に表ごとの列の名前を足し、無ければ列名のまま）（→ 実装では lib/data/history.ts に置いた。「画面の実装の記録」の決めたこと 2）。申請できる区分は区分の表示名、備品の id は備品の名前、confirmed_by は表示名で出す。
18. **申請できる区分の CHECK**：4 個まで（区分は4つ。大きな配列を入れさせない。D-09）。重複と null の要素は止めない（区分の判定〔`= any`〕で害がない。画面は送らない）。
19. **確定の印の CHECK**：confirmed_by は confirmed_at があるときだけ（lending_years_confirmed_check）。
20. **「未返却」を出すのは2日目から**：計画は受け渡し・返却の状態のチップで「未返却（2日目から）」とし、それより前の同じ状態を「貸し出し中」としている。これに合わせて、カードの「未返却 K 団体」（計画の 4 の「渡した 8／9 団体・未返却 5 団体」）と、申請のタブの注意の色の「未返却：テント 1 張」も2日目（1日目の翌日の 0 時、Asia/Tokyo）から出す（前日・1日目に貸し出し中の団体を「未返却」と数えて、総務と店長・副店長を驚かせない）。2日目の前のカードの3行目は「渡した N／M 団体」だけ。要対応（計画の 4）は計画のまま2日目から。01 の用語集の「未返却」にも書いた。
21. **申請のタブの確定後の割り当て**：計画の「確定後は「割り当て：テント 1 張（申請 2）」」を、申請が1以上か割り当ての行がある備品ごとに出す、と読んだ（割り当て 0 の備品も「割り当て：テント 0 張（申請 2）」と出し、申請した団体に「貸さない」と決まったことが分かるようにする。確定の後に締切を延ばして申請が増え、割り当ての行がない備品は「未定」）。記録（渡した・返った）は確定の前でも出す（記録は確定の前でも書け〔確かめたいことの 9〕、店長・副店長は自団体の記録を RLS で読めるので、2日目からの「返してください」の要対応の行き先で数が見えるようにする）。
22. **割り当ての入力のエラーの文言**：save_lending_assignments の invalid_input の field は changes・groupId・itemId。lib/labels.ts の FIELD_LABELS では changes が「振り分けの変更」なので、lib/errors.ts は RPC の名前（ctx.rpc）で分けて「入力の形が違います（テント等の割り当て）」と出す（not_in_year は読み直す文言。下の 12）。

### 9. 書き込みと通信の失敗

- 備品：登録はダイアログを開いたときに作った id で insert し、行を返させる（送り直しは 23505。id の行を読み直して入力と同じなら「「{名前}」は登録されていました」、違えば〔同じ名前の別の行と 23505〕「同じ名前の備品がすでにあります」）。編集は updated_at の文字列のままの条件の update（updateWithLock）、削除は deleteChecked。0 行・応答なしは (B1)（settleLockedWrite）。削除の 23503 は「申請・割り当て・記録のある備品は削除できません」。在庫の守り（invalid_state の reason confirmed）は「割り当ての確定中は、在庫を割り当ての合計（{N}）より少なくできません」。
- 割り当て：save_lending_assignments。conflict はその行（団体・備品）を読み直し、入力と同じなら「保存されていました」、違えば読み直した値を出して入力を残す（もう一度の保存は読み直した updatedAt で送る）。応答が届かなければ、送った変更の行を読み直して全部が入力と同じなら保存されていたとし、そうでなければ入力を残して「保存できたか分かりません。もう一度「保存（N件）」を押すと、確かめてから送ります」（(B1)。送り直しても行が二重にならない）。
- 確定・解除：set_lending_confirmed。応答が届かなければ確定の行を読み直して、頼んだ状態になっていれば成功と同じに扱う。invalid_state の unchanged は読み直して今の状態を出す。before_deadline・over_stock・unassigned は読み直して押せない理由を出し直す。
- 申請・記録：(A)（上の 5・6）。
- 直接の update・delete は `.select()` で返った行を確かめ、0 行を成功にしない。

### 決めたこと（約束にないもの・約束から変えたもの）

1. **割り当ての未保存の変更は、セルごとに「入力を始めたときの版」を持つ**（約束の 4・9）：save_lending_assignments の updatedAt には、裏で読み直した行ではなく、入力を始めたときの行の updated_at を送る（読み直しで版を進めると、ほかの人の変更を黙って上書きする。締切と予定の「一覧の読み直しでは入力の元の版を進めない」と同じ）。conflict で送った組を読み直したときだけ、読み直した版に進めて入力を残す（次の保存はこの入力で上書きする）。応答が届かなかったときは、送った組を読み直して入力と同じなら「保存されていました」、送った版から行が変わっていれば conflict と同じ、変わっていなければ「保存できたか分かりません。もう一度「保存（N件）」を押すと…」。
2. **履歴の列の名前は lib/data/history.ts に置いた**（約束は lib/labels.ts）：lib/labels.ts は lib/errors.ts 経由でどのページの最初に読む JS にも入る（ビルドのチャンクで、列の名前の表が /login にも入っていた）。履歴だけが使う表なので、T18 の lib/datetime-weekday.ts と同じ理由で分けた。表の名前（AUDIT_TABLE_LABELS）は約束のまま lib/labels.ts。
