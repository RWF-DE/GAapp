## 背景と目的

電波祭の総務部門の仕事を、1つの Web アプリ（総務アプリ。画面の名前は「電波祭 総務」）にまとめる。仕事は「機能」ごとに足していく。最初の機能は「机椅子」で、机椅子の振り分けを在庫入力から当日の運搬確認まで扱い、総務の手作業とレビューの往復をなくす。机椅子は R9（2027年）の電波祭で本番運用することを目標とする。トップはダッシュボードで、機能ごとのカード・要対応の一覧・締切と予定を、立場ごとに出す（T17 から、総務には総務内のお知らせ、閲覧のみ・団体代表にはお知らせの新着も。D-51・D-53）。後から足す機能は「スコープ」の表のとおり。

机椅子の仕事で、R8 で手間がかかった原因は次のとおり。

- 申請フォームが自由記入を許し、備考での読み替え（長机(3人)→キャスター机3×2）や在庫外の物（制作工房の机）を人が解釈していた
- 在庫の数え直し、使用不可の部屋（第一セミナー）、残す机の扱いが後から判明し、そのたびに表を作り直した
- 「不可机は模擬店のみ」「設営は1・2年の教室から」などのルールが口頭で決まり、文書に残っていない
- Excelの数式が前年のまま残り、在庫超過や申請との差を目で確認していた（外部レビュー4回）
- 振り分け表と配布スケジュールを別々に手で作り、片方の変更がもう片方に反映されなかった

机椅子の機能で実現すること：

1. 申請と在庫を決まった形式で集める
2. ルールに沿って振り分けを自動で作り、在庫超過・申請との差を自動で検出する
3. 振り分けから配布スケジュールと当日の運搬リストを自動で作る
4. 毎年のデータとルールを引き継げるようにする

アプリ全体で実現すること：総務の仕事の入口を1つにし（ダッシュボードと、機能の見出しごとのナビゲーション）、年度・ロール・団体代表をどの機能でも同じものにする（T16。D-51・D-52）。

## 利用者とロール

ロールは年度ごとに付け、アプリ全体（どの機能の画面も）で同じロールを使う。編集できるのは総務だけで、団体代表は自分の団体の申請と振り分け結果だけを見る。招待されていない人は、学校のアカウントでログインしても何も見られない。

| ロール | できること | 主な端末 |
| --- | --- | --- |
| 管理者（admin） | アプリの設定（場所・品目・距離・団体のマスタ、年度の作成と終了、年度名と1日目）、年度データの書き出し、管理者・総務部門長・総務副部門長・閲覧のみの招待と、ロールの変更。下の部門長以上の操作もすべてできる | PC |
| 総務部門長（head）・総務副部門長（deputy_head） | 業務の決定（受付の開始・締切・確定と確定の解除、受付期間、ルール、振り分けの実行と手直し、了承の記録、締切後の申請の修正、今年の使用、時間枠と受け渡し、履歴）、総務部門員と団体代表（店長・副店長）の招待・招待の取り消し・外すことと、店長⇄副店長の切り替え。副部門長の権限は部門長と同じ | PC |
| 総務部門員（staff） | 在庫の入力（数え）、振り分けなどの閲覧、当日の運搬・返却のチェック | スマホ |
| 団体代表（店長・副店長） | 自団体の申請の提出と締切前の修正、キャスター机交換への回答、自団体の振り分けと受け取り時刻の確認。店長と副店長の権限は同じ | スマホ |
| 閲覧のみ（viewer：他部門・教員） | 確定後の振り分け表とスケジュールの閲覧 | PC・スマホ |

権限は3つの段に分ける：管理者だけ、部門長以上（管理者・部門長・副部門長）、総務（部門長以上と部門員）。表と DB 関数ごとの段は[データ設計](02_data.md)の「権限とRLS」にある（D-48）。管理者と閲覧のみは、同じ年度の団体代表（店長・副店長）を兼ねられる。部門長・副部門長・部門員は、同じ年度の団体代表を兼ねられない（兼任の禁止。違う年度なら兼ねてよい。D-49）。R8 の団体は55（模擬店39・部門11・企業3・休憩所2）。企業ブースと休憩所にはアカウントを渡さず、総務（部門長以上）が代わりに申請を入力する（企業のメールアドレスをアプリに保存しないため）。

ここから下のフェーズは机椅子のもの。フェーズ1だけで R8 の作業の大部分がなくなる。R9 ではフェーズ1と2を本番で使い、3は余裕があれば作る。

**フェーズ1：振り分け（必須）**

- 年度の作成と前年度の複製、場所・品目・団体のマスタ、招待
- 保管場所ごとの在庫入力（使用不可の部屋の設定を含む）
- 団体による申請の提出（Googleフォームの置き換え）と、フォーム回答の取り込み
- ルールの設定と、ルールに沿った自動振り分け（確定後の変更に使う最小変更モードを含む）
- 振り分けの手動修正、固定、変更履歴
- 検証（在庫超過・申請との差・ルール違反など）
- キャスター机交換の依頼と了承の記録
- R8 と同じ様式の Excel 出力（品目別シート＋団体別集計）、交換依頼一覧、年度データの書き出し

**フェーズ2：配布と当日（R9 で使う）**

- 時間枠の設定と、配布スケジュールの自動作成（机等・テント・重し・三方幕）
- 班ごとの運搬リストと、スマホでの「運搬済み」チェック。印刷用の運搬リスト
- 本部向けの進捗画面
- 返却（元の部屋に戻したか）のチェック

**フェーズ3：余裕があれば**

- レイアウト図の上で使用場所を選ぶ
- 備品の種類を増やす（ホワイトボード、延長コード、制作工房の机など）

**対象外**

- 模擬店そのものの申請受付（出店の受け付けなど。机椅子は備品の数と受け渡しに関わる部分だけを扱う。テントなどの貸し出しは T21 の機能で扱う）
- 総務以外の部門の業務管理
- ネイティブアプリ（PWA で対応する）
- サーバー側の処理（計算とファイル作成はブラウザ、データと権限は Supabase）

## 振り分けロジック

机椅子の振り分けは「申請をすべて満たし、キャスター机などへの置き換えを最小にし、その中で運ぶ距離を最小にする」輸送問題として、部門長以上（管理者・総務部門長・総務副部門長）のブラウザで解く。R8 規模なら一瞬で解け、同じ入力なら同じ結果になる。式・ルールの扱い・解けないときの診断は[振り分けと検証](03_allocation.md)、ルールの一覧は[用語と業務ルール](01_rules.md)にある。

R8 で決めたことのうち、ルールとして入るもの：

- 不可机は模擬店だけ、不可椅子は休憩所と模擬店だけに使う。どちらも距離が最優先で、同じ距離なら不可椅子は休憩所に先に回す
- 長机(3人掛)は企業の希望だけ聞く。他の団体の申請は長机(2人掛)に読み替える
- 設営の机(木)241台は 1・2年の教室から出す
- 机(木)が足りないときは、屋内の模擬店をキャスター机に置き換える（団体の了承が要る）
- 団体の使用場所にある備品は、その団体が残して使う
- 予備の台数は持たない

## データモデル

Supabase（PostgreSQL）に、年度・場所・品目・在庫・団体・申請・ルール・振り分け・了承・招待・履歴などの表を置く。今の表は机椅子の機能のもので、年度・ロール・団体代表・招待はアプリ全体の立場（ナビゲーション・ダッシュボード）にも使う（T16 は表を足さない）。ほかの機能の表は、その機能のチケットが足す。列の定義、権限（RLS）、DB 関数は[データ設計](02_data.md)にある。二重管理を避けるため、この文書には表の一覧を置かない。

## 非機能要件と技術構成

費用0円で運用でき、すべてのアカウントが個人ではなく組織の持ち物になる構成にする。アプリにはサーバーを置かず、計算とファイル作成はブラウザ、データと権限は Supabase に集める。

| 層 | 採用 | 理由 |
| --- | --- | --- |
| フロント | Next.js（App Router、output: 'export'）＋TypeScript、Tailwind CSS、shadcn/ui、TanStack Table・TanStack Query、PWA（フェーズ1はホーム画面に追加できるマニフェストとアイコンだけで、ホーム画面からはブラウザで開く。standalone は実機で Google のログインを確かめてから。Service Worker はオフラインの運搬リストが要るフェーズ2で検討。D-38） | スマホでインストール不要。静的なファイルだけで動く |
| 配信 | GitHub Pages（組織の公開リポジトリ） | 無料。GitHub の組織だけで完結し、引き継ぐアカウントが増えない |
| DB・認証 | Supabase 無料プラン（Postgres、Auth、Realtime）、組織で所有、東京リージョン | 権限を RLS と DB 関数に集められる |
| 振り分け | highs-js（WebAssembly）を Web Worker で実行 | 輸送問題を部門長以上のブラウザで解く |
| Excel 出力 | ExcelJS（ブラウザ） | R8 の様式（数式付き）を再現 |
| テスト | Vitest、pgTAP、Playwright | R8 のデータをテストに使う（D-40：R8 の元データは使わず、R8 と合計が同じ合成データで代用する） |

Vercel Hobby を使わない理由：GitHub の組織の非公開リポジトリからはデプロイできず、プロジェクトが1人の個人アカウントの持ち物になるため。Vercel Pro＋GitHub Team は人数分の月額費用がかかる。

**権限とセキュリティ**

- ログインは学校の Google アカウントに限る（ドメイン制限）。招待されていない人は何も見られない
- 全テーブルに RLS。理由が要る書き込みと、まとめて変える書き込みは DB 関数で行い、関数の中で権限を確かめる
- アプリが使う鍵は publishable キーだけ。secret（旧 service_role）キーはアプリで使わない（旧形式の anon・service_role キーは 2026年末までに廃止予定）
- 企業のメールアドレスなど外部の個人情報は保存しない。フォーム回答の取り込みでもメールアドレスは捨てる

**性能と可用性**

- 画面はスマホの 4G でも 2 秒以内に開く
- 振り分けの計算（allocate の呼び出しから結果まで）は R8 規模でブラウザ 2 秒以内。highs の wasm（gzip で約 1.2 MB）の初回の読み込みは含めず、振り分け画面を開いたときに読み込み中と表示する（T00 の実測：計算は 0.1〜0.3 秒、wasm の読み込みは Fast 4G 相当で約 1.3 秒、Slow 4G 相当で約 6 秒）
- 当日に通信が切れた場合に備え、運搬リストは印刷できるようにする（フェーズ2）

**保守と引き継ぎ**

- GitHub と Supabase は組織で所有し、オーナーを常に2人以上にする。卒業する人は、後輩をオーナーに追加してから抜ける
- Supabase の無料プランは自動バックアップがない。年度末に管理者がアプリから年度データ（JSON と Excel）を書き出し、総務の共有ドライブに保存する。開発者は `supabase db dump` でも保存する（公開リポジトリには置かない）
- Supabase の無料プランは、1週間ほど使われないと一時停止する。停止から1年以内なら管理画面から再開できるので、毎年7月の年度作成の前に再開する
- README に「7月の再開と年度の始め方」「ルールの変え方」「年度末の書き出し」「障害時の対応」を書く
- DB の変更は Supabase のマイグレーションファイルで管理する
