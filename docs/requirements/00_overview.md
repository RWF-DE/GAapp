最終更新：2026-10-28（Claude Docs の要件定義書から書き出したもの。以後はこのリポジトリの docs/requirements を正とする）

この文書は全体像。実装に必要な詳細は次のファイルにある：[用語と業務ルール](01_rules.md) ／ [データ設計](02_data.md) ／ [振り分けと検証](03_allocation.md) ／ [画面とAPI](04_screens_api.md) ／ [開発の進め方](05_development.md)。食い違ったときは詳細のファイルを正とする。

## 背景と目的

電波祭の机椅子振り分けを、在庫入力から当日の運搬確認まで1つのWebアプリで扱い、総務の手作業とレビューの往復をなくす。R9（2027年）の電波祭で本番運用することを目標とする。

R8で手間がかかった原因は次のとおり。

- 申請フォームが自由記入を許し、備考での読み替え（長机(3人)→キャスター机3×2）や在庫外の物（制作工房の机）を人が解釈していた
- 在庫の数え直し、使用不可の部屋（第一セミナー）、残す机の扱いが後から判明し、そのたびに表を作り直した
- 「不可机は模擬店のみ」「設営は1・2年の教室から」などのルールが口頭で決まり、文書に残っていない
- Excelの数式が前年のまま残り、在庫超過や申請との差を目で確認していた（外部レビュー4回）
- 振り分け表と配布スケジュールを別々に手で作り、片方の変更がもう片方に反映されなかった

このアプリで実現すること：

1. 申請と在庫を決まった形式で集める
2. ルールに沿って振り分けを自動で作り、在庫超過・申請との差を自動で検出する
3. 振り分けから配布スケジュールと当日の運搬リストを自動で作る
4. 毎年のデータとルールを引き継げるようにする

## 利用者とロール

ロールは年度ごとに付ける。編集できるのは総務だけで、団体代表は自分の団体の申請と振り分け結果だけを見る。招待されていない人は、学校のアカウントでログインしても何も見られない。

| ロール | できること | 主な端末 |
| --- | --- | --- |
| 総務管理者（admin） | 年度・場所・品目・団体・ルールの設定、振り分けの実行と確定、招待、出力 | PC |
| 総務部員（staff） | 在庫の入力（数え）、振り分けの閲覧、当日の運搬チェック | スマホ |
| 団体代表 | 自団体の申請の提出と締切前の修正、キャスター机交換への回答、自団体の振り分けと受け取り時刻の確認 | スマホ |
| 閲覧のみ（viewer：他部門・教員） | 確定後の振り分け表とスケジュールの閲覧 | PC・スマホ |

1人が複数の立場を持てる（総務部員で、クラスの団体代表も兼ねるなど）。R8 の団体は55（模擬店39・部門11・企業3・休憩所2）。企業ブースと休憩所にはアカウントを渡さず、総務が代わりに申請を入力する（企業のメールアドレスをアプリに保存しないため）。

## スコープ

フェーズ1だけで R8 の作業の大部分がなくなる。R9 ではフェーズ1と2を本番で使い、3は余裕があれば作る。

**フェーズ1：振り分け（必須）**

- 年度の作成と前年度の複製、場所・品目・団体のマスタ、招待
- 保管場所ごとの在庫入力（使用不可の部屋の設定を含む）
- 団体による申請の提出（Googleフォームの置き換え）と、フォーム回答の取り込み
- ルールの設定と、ルールに沿った自動振り分け（確定後の変更に使う最小変更モードを含む）
- 振り分けの手動修正、固定、変更履歴
- 検証（在庫超過・申請との差・ルール違反など）
- キャスター机交換の依頼と了承の記録
- R8 と同じ様式の Excel 出力（品目別シート＋団体別集計）、交換依頼一覧、年度データの書き出し

**フェーズ2：配布と当日（R9 で使う）**

- 時間枠の設定と、配布スケジュールの自動作成（机等・テント・重し・三方幕）
- 班ごとの運搬リストと、スマホでの「運搬済み」チェック。印刷用の運搬リスト
- 本部向けの進捗画面
- 返却（元の部屋に戻したか）のチェック

**フェーズ3：余裕があれば**

- レイアウト図の上で使用場所を選ぶ
- 備品の種類を増やす（ホワイトボード、延長コード、制作工房の机など）

**対象外**

- テントや模擬店そのものの申請受付（備品の数と受け渡しに関わる部分だけを扱う）
- 総務以外の部門の業務管理
- ネイティブアプリ（PWA で対応する）
- サーバー側の処理（計算とファイル作成はブラウザ、データと権限は Supabase）

## 機能要件

各機能は R8 で発生した作業をそのまま置き換える形で定義する。ID の F1〜 はフェーズ1、F2〜 はフェーズ2。詳細は各ファイルにある。

| ID | 機能 | 要件 | ロール |
| --- | --- | --- | --- |
| F1-1 | 年度 | 年度ごとに全データを分ける。作成時に前年度の団体・ルール・使用不可の設定を複製する。状態（準備中〜終了）を持つ | 管理者 |
| F1-2 | 場所マスタ | 建物・階・種類（部屋・体育館・屋外）・保管場所か・追加コストを持つ。「この年は使用不可」を場所単位で設定できる | 管理者 |
| F1-3 | 品目マスタ | 9品目。申請できる区分とフォームでの表記を持つ。長机(3人掛)は企業のみ、不可机・不可椅子は申請不可 | 管理者 |
| F1-4 | 団体マスタ | 区分（模擬店・部門・企業・休憩所）、飲食かどうか、使用場所、別名（「展示部門(2-2)」＝「2年2組（カジノ）」など） | 管理者 |
| F1-5 | 在庫入力 | 保管場所ごとに品目の数をスマホで入力する。誰がいつ数えたかを残す | 部員 |
| F1-6 | 申請 | 品目ごとの数と、団体ごとに1つの備考（数には影響しない）。締切後は総務だけが理由つきで修正できる | 団体 |
| F1-7 | フォーム回答の取り込み | Googleフォームの回答（3種類）を取り込む。メールアドレスは捨てる | 管理者 |
| F1-8 | ルール | 代替・運び元の制限・固定の申請・残すを設定する。年度をまたいで引き継ぐ | 管理者 |
| F1-9 | 自動振り分け | 在庫・申請・ルールから、ブラウザで数秒以内に作る。固定・手動の行は変えない。確定後の変更には最小変更モードを使う。同じ入力なら同じ結果 | 管理者 |
| F1-10 | 手動修正 | 行の追加・変更・削除・固定。変更履歴を残す | 管理者 |
| F1-11 | 検証 | 在庫超過、申請との差、ルール違反、使用不可の部屋からの運び出しなどを一覧で出す。error があると確定できない | 管理者 |
| F1-12 | キャスター机交換 | 置き換えた団体への依頼と了承の記録。了承した置き換えは固定し、拒否した団体は置き換えから外す | 管理者・団体 |
| F1-13 | 出力 | R8 と同じ様式の Excel（品目別シート＋団体別集計）、交換依頼一覧、年度データ（JSON）。色を付けず、備考は特記事項のみ | 管理者 |
| F1-14 | 団体への公開 | 確定後、各団体が自団体の振り分け（運び元・数）を見られる | 団体 |
| F2-1 | 時間枠 | 前々日・前日の時間枠（15分単位など）を作り、団体や部門の受け渡し（机等・テント・重し・三方幕）を割り当てる | 管理者 |
| F2-2 | スケジュール自動作成 | 振り分けと時間枠から「屋外」「屋内」「部門・企業」「時間別」を作る。テントの30分後に机、のような順序を守る | 管理者 |
| F2-3 | 運搬チェック | 班ごとのリストをスマホで開き、「運搬済み」「問題あり」を押す。印刷用のリストも出せる | 部員 |
| F2-4 | 進捗画面 | 本部が時間枠ごとの進み具合と問題の報告をリアルタイムで見る | 管理者 |
| F2-5 | 返却 | 祭の後、元の部屋に戻したかを同じ画面でチェックする | 部員 |

## 振り分けロジック

振り分けは「申請をすべて満たし、キャスター机などへの置き換えを最小にし、その中で運ぶ距離を最小にする」輸送問題として、管理者のブラウザで解く。R8 規模なら一瞬で解け、同じ入力なら同じ結果になる。式・ルールの扱い・解けないときの診断は[振り分けと検証](03_allocation.md)、ルールの一覧は[用語と業務ルール](01_rules.md)にある。

R8 で決めたことのうち、ルールとして入るもの：

- 不可机は模擬店だけ、不可椅子は休憩所と模擬店だけに使う。どちらも距離が最優先で、同じ距離なら不可椅子は休憩所に先に回す
- 長机(3人掛)は企業の希望だけ聞く。他の団体の申請は長机(2人掛)に読み替える
- 設営の机(木)241台は 1・2年の教室から出す
- 机(木)が足りないときは、屋内の模擬店をキャスター机に置き換える（団体の了承が要る）
- 団体の使用場所にある備品は、その団体が残して使う
- 予備の台数は持たない

## データモデル

Supabase（PostgreSQL）に、年度・場所・品目・在庫・団体・申請・ルール・振り分け・了承・招待・履歴などの表を置く。列の定義、権限（RLS）、DB 関数は[データ設計](02_data.md)にある。二重管理を避けるため、この文書には表の一覧を置かない。

## 非機能要件と技術構成

費用0円で運用でき、すべてのアカウントが個人ではなく組織の持ち物になる構成にする。アプリにはサーバーを置かず、計算とファイル作成はブラウザ、データと権限は Supabase に集める。

| 層 | 採用 | 理由 |
| --- | --- | --- |
| フロント | Next.js（App Router、output: 'export'）＋TypeScript、Tailwind CSS、shadcn/ui、PWA | スマホでインストール不要。静的なファイルだけで動く |
| 配信 | GitHub Pages（組織の公開リポジトリ） | 無料。GitHub の組織だけで完結し、引き継ぐアカウントが増えない |
| DB・認証 | Supabase 無料プラン（Postgres、Auth、Realtime）、組織で所有、東京リージョン | 権限を RLS と DB 関数に集められる |
| 振り分け | highs-js（WebAssembly）を Web Worker で実行 | 輸送問題を管理者のブラウザで解く |
| Excel 出力 | ExcelJS（ブラウザ） | R8 の様式（数式付き）を再現 |
| テスト | Vitest、pgTAP、Playwright | R8 のデータをテストに使う |

Vercel Hobby を使わない理由：GitHub の組織の非公開リポジトリからはデプロイできず、プロジェクトが1人の個人アカウントの持ち物になるため。Vercel Pro＋GitHub Team は人数分の月額費用がかかる。

**権限とセキュリティ**

- ログインは学校の Google アカウントに限る（ドメイン制限）。招待されていない人は何も見られない
- 全テーブルに RLS。理由が要る書き込みと、まとめて変える書き込みは DB 関数で行い、関数の中で権限を確かめる
- アプリが使う鍵は publishable キーだけ。secret（旧 service_role）キーはアプリで使わない（旧形式の anon・service_role キーは 2026年末までに廃止予定）
- 企業のメールアドレスなど外部の個人情報は保存しない。フォーム回答の取り込みでもメールアドレスは捨てる

**性能と可用性**

- 画面はスマホの 4G でも 2 秒以内に開く
- 振り分けの計算は R8 規模でブラウザ 2 秒以内
- 当日に通信が切れた場合に備え、運搬リストは印刷できるようにする（フェーズ2）

**保守と引き継ぎ**

- GitHub と Supabase は組織で所有し、オーナーを常に2人以上にする。卒業する人は、後輩をオーナーに追加してから抜ける
- Supabase の無料プランは自動バックアップがない。年度末に管理者がアプリから年度データ（JSON と Excel）を書き出し、総務の共有ドライブに保存する。開発者は `supabase db dump` でも保存する（公開リポジトリには置かない）
- Supabase の無料プランは、1週間ほど使われないと一時停止する。停止から1年以内なら管理画面から再開できるので、毎年7月の年度作成の前に再開する
- README に「7月の再開と年度の始め方」「ルールの変え方」「年度末の書き出し」「障害時の対応」を書く
- DB の変更は Supabase のマイグレーションファイルで管理する

## 開発スケジュールとマイルストーン

フェーズ1を2027年4月までに作り、R8 のデータで検証してから R9 で使うかを決める。最初に highs-js をブラウザで動かして計算時間を確かめる（T00）。申請受付は R8 と同じく8月中旬からの想定。判断ポイントの基準は[開発の進め方](05_development.md)の受け入れ基準。

| 期間 | 段階 | 内容 |
| --- | --- | --- |
| 2026年11月〜2027年1月 | 要件確定・設計 | 未決事項を解決、DB・画面設計、highs-js の計算時間を確認（T00） |
| 2027年2月〜4月 | フェーズ1を実装 | マスタ・在庫・申請・ルール・自動振り分け・検証・Excel出力 |
| 2027年5月〜6月 | R8のデータで検証 | R8の申請を流し、手で作った振り分け表と比べる。総務内で試しに使う |
| （判断ポイント） | 本番で使うか判断 | 受け入れ基準（[05_development.md](05_development.md)）をすべて満たすか。不合格ならR9もExcelで運用 |
| 2027年7月 | 在庫数え・団体登録 | 部員がスマホで部屋ごとの在庫を入力。使用不可の部屋をここで確定 |
| 2027年8月〜9月 | 申請受付とフェーズ2の実装 | 団体がアプリで申請。並行してスケジュールと運搬チェックを作る |
| 2027年10月 | 振り分け確定・R9電波祭で本番運用 | 当日はスマホで運搬チェック。終わったらルールと課題を振り返る |

判断ポイントで不合格なら、R9はExcelで運用しつつ、在庫入力と申請受付だけアプリで行う。日付は案で、未決事項が片付いた時点で見直す。

## 未決事項

- [ ] 学校の Google Workspace で、1〜3年生（18歳未満の指定がある人）が外部アプリにログインできるか（情報担当に確認。だめなら団体の申請はすべて総務が代理入力する）。教員と学生は同じドメイン（D-04）で、ドメインの値はまだ受け取っていない（フックの定数は仮の値）
- [ ] Google Cloud の OAuth クライアントを学校の Workspace の中に作れるか（同意画面を Internal にできるか）、誰の持ち物にするか（K-11。手順は README）
- [ ] 学生会・教員に、外部サービス（GitHub Pages・Supabase）の利用とコードの公開を認めてもらえるか
- [ ] GitHub と Supabase の組織のオーナーを誰にするか（2人以上）
- [ ] 引き継ぐ後輩（開発メンバー）は誰か
- [ ] 団体の申請をこのアプリに一本化するか。他部門の Googleフォームとの切り分け
- [ ] 建物・階のデータと、距離コストの値（R8 のデータで結果を見て決める）
- [ ] 校内に分散して使う団体（美化など）の運び先をどう表すか
