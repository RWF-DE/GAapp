# 振り分けと検証

## 入力と出力

振り分けは DB に触れない純粋関数 `allocate(input, solver): AllocateResult` として `packages/allocator` に置き、管理者のブラウザの Web Worker で実行する。solver は highs-js のインスタンスで、呼ぶ側が読み込んで渡す（Worker の中で1回だけ読み込んで使い回す。Node のテストでは `loadHighs()` で作る）。allocator は highs を import しない。画面は DB から入力を組み立てて呼び、結果を RPC `save_auto_allocations` で保存する。型と zod スキーマは `packages/shared` に置く。R8 の fixtures（fixtures/r8）と、R8 と合計が同じ合成データ（fixtures/synthetic/r8like）で単体テストする。

```ts
type Item = { id: string; code: string; name: string;
              requestableCategories: GroupCategory[]; sortOrder: number };
type Room = { id: string; name: string; kind: 'room' | 'gym' | 'outdoor' | 'other';
              building: string | null; floor: number | null;
              extraCost: number;              // 0〜20 の整数
              isStorage: boolean; usable: boolean; sortOrder: number };
type Group = { id: string; name: string; displayName: string | null;
               category: 'stall' | 'department' | 'company' | 'rest_area';
               locationRoomId: string | null; sortOrder: number;
               submittedAt: string | null };   // 未提出は null（D-07・W105）

type YearData = {                     // validate と exporter もこれを受け取る
  items: Item[]; rooms: Room[]; groups: Group[];
  stocks: { roomId: string; itemId: string; count: number }[];     // 数えた場所の行（0 も渡す）
  requests: { groupId: string; itemId: string; count: number }[];  // 前処理の前の申請
  rules: Rule[];                      // enabled のものだけ。zod で検証した params を持つ
  consents: { groupId: string; fromItemId: string; toItemId: string;
              status: 'not_asked' | 'asked' | 'accepted' | 'declined';
              count: number | null }[];   // 依頼したときの置き換え台数（W102 で使う。DB 設計の P-01）
  distanceOverrides: { buildingA: string; buildingB: string; cost: number }[];   // cost は 0〜20 の整数
};

type AllocateInput = YearData & {
  mode: 'full' | 'minimal_change';
  fixedRows: StoredAllocationRow[];   // pinned = true または origin = 'manual' の行
  previousRows: AllocationRow[];      // minimal_change のとき、前回の自動行（残すの行を含む）。full では []
};

type AllocationRow = {
  sourceRoomId: string; groupId: string;
  itemId: string;                     // 実際に運ぶ品目
  requestedItemId: string;            // 申請した品目（前処理1の読み替えの後）
  count: number; isKeep: boolean;
};
type StoredAllocationRow = AllocationRow & {
  id: string; origin: 'auto' | 'manual'; pinned: boolean; note: string | null };

type AllocateResult =
  | { ok: true; rows: AllocationRow[]; objective: number; elapsedMs: number; stats: AllocateStats }
  | { ok: false; reason: 'invalid_input' | 'precheck' | 'infeasible' | 'solver_error';
      message: string; inputErrors: InputError[]; issues: Issue[];
      shortages: Shortage[]; causes: Cause[]; elapsedMs: number;
      stats?: Partial<AllocateStats> };   // 途中まで分かった記録（変数の数など）

type InputError = { path: string; message: string; ruleCode?: string };
type Shortage = { requestedItemId: string; groupId: string | null;  // null は品目全体
                  demand: number; supply: number };
type Cause = { ruleCode: string | null; message: string;
               details: { groupId?: string; itemIds?: string[]; roomIds?: string[];
                          demand?: number; supply?: number }[] };
```

（AllocateStats は変数・制約の数、重み、時間、需要から除いた申請の行の数（excludedRequests）などの記録。形は packages/shared に書く。）

- 入力の配列の並び順は結果に影響しない。allocate の中で、品目・場所・団体を sort_order → 名前 → id（文字列は UTF-16 のコード単位で比べ、localeCompare は使わない）、ルールを code の順に並べ直し、在庫・申請・了承・固定行・前回の行は並べ直した順に引いて使う。並び順が変わると、同じ点数の解の中で別の解が選ばれうるため
- 保存は RPC `save_auto_allocations(year_id, rows, mode)`。1トランザクションで `origin = 'auto' AND NOT pinned` の行だけを消して rows を入れ、保存後に在庫超過がないかを DB の中でも確かめる（超過していれば全体を取り消す）。ブラウザの計算結果をそのまま信用しない
- 手で直した行（origin = manual）と固定した行（pinned）は消さず、すべて fixedRows として渡す。了承済みのキャスター机交換は、了承を記録した時点でその行を pinned にする
- rows には固定行を含めない。残す（S08）の行は含める（保存のしかたは上の箇条書き）。x と x̂ は（運び元・団体・申請品目・品目）ごとに足して1行にする。is_keep は、運び元が団体の使用場所と同じ行に付ける。画面で検証するときは、固定行と rows を合わせて validate に渡す
- ok: false の reason：invalid_input（入力の形や参照先が不正。inputErrors）、precheck（前処理で止めるもの。固定行と残すの行で在庫を超える E001、残すのルールの部屋が使用不可の E002・使用場所でない E005 を issues に入れ、該当の行やルールを refs で示す）、infeasible（解けない。shortages と causes）、solver_error（HiGHS が Optimal 以外の状態を返した、値が整数でない、など。message に状態を入れる）
- allocate は、自分が作る行（計算した行と残すの行）に error が出ないようにする。人が決めた固定行の error（使用不可の部屋から E002、is_keep の不整合 E005、ルール違反 E004）と、申請できない品目の申請（E006。需要から除いて計算する）では止めず、validate が error として示す。error がある間は確定できない

## 定式化

振り分けは輸送問題（線形計画）として解く。0/1 変数を使わないので R8 規模なら一瞬で解け、単体法で解けば整数の解が得られる。ソルバーは highs-js（HiGHS の WebAssembly 版）。以前の案にあった「運び元の数」の 0/1 変数は、最適解の証明に時間がかかり結果が毎回変わるため使わない（運び元が分かれすぎたときは W103 で知らせる）。

**前処理**

0. 入力を zod スキーマで検証し、id とルールの参照先（団体・場所・品目のコード）があること、fixed_request と keep の品目が対象の団体の区分で申請できる品目であること、ルールが重なっていないこと（同じ団体・品目の fixed_request、同じ団体・部屋・品目の keep、同じ代替で区分が重なる substitute）、keep の部屋が同じ団体・品目の source_restrict の場所に入っていること（入っていないと残すの行がルール違反（E004）になる）を確かめる。だめなら invalid_input（関わるルールをそれぞれ示す。ルールの画面も保存の前に同じ確認をする）
1. 申請を団体・品目ごとに合計する。団体の区分で申請できない品目のうち、長机(3人掛)は長机(2人掛)に1対1で読み替える（S03・D-05。品目マスタの申請できる区分で判定。DB に長机(3人掛)のまま残っていてよい）。それ以外の申請できない品目の申請は、需要から除いて計算を続ける（止めない）。検証の E006 がその申請を示し、直すまで確定できない
2. fixed_request（S06）は、対象の団体が未提出（submitted_at が null）のときだけ、その数を需要にする（申請の数は使わない）。提出済みなら 0 を含めて申請の数を使い、違えば W106 で知らせる（D-07）。1・2 の結果を需要 D とする。E003・W101 と、画面の「団体別」の申請数は、この D と比べる
3. keep（S08）の行をルールから作る（is_keep。保存は origin = auto・pinned = false で、自動実行のたびにルールから作り直す。D-06）。固定行と同じように、需要と在庫から先に差し引き（4）、結果の rows にも含める。管理者が固定した keep の行など、同じ団体・部屋・品目の固定行（fixedRows に入る）があれば、固定分を超える分だけを作る（同じ団体・部屋・品目の keep が2つあるものは前処理 0 で止めているので、固定分を引くのは1回だけ）。申請より多くても作る（多い分は W101）。部屋が団体の使用場所でなければ E005、使用不可なら E002 で止め、ルールを示す
4. 固定行と 3 の残すの行を差し引く。固定行の申請品目にも 1 と同じ読み替えを当ててから引く（企業以外の長机(3人掛)の手動の行が、長机(2人掛)の需要から引かれるように）。需要 D'(g,i) = max(0, D(g,i) − 固定分)、在庫 S'(r,j) = S(r,j) − 固定分。固定分が申請を超えても止めない（W101）。在庫を超えたら E001 で止め、該当の行を示す（使用不可の部屋でも同じ）。固定行の運び元が使用不可（E002）・ルール違反（E004）・is_keep の不整合（E005）では止めず、検証で示す
5. 使用不可の部屋は S' = 0
6. 最小変更モードでは、前回の自動行（申請品目は 1 と同じ読み替えの後）を（運び元・団体・申請品目・品目）ごとに合計し、3 の残すの行の数を引いたものを x̂ の上限にする
7. 変数を作った後、変数が1つもない需要、または変数の運び元の S' の合計が D' に足りない需要があれば、LP を作らずに shortages（団体つき）を返す。変数のない需要の行を LP から落とすと、HiGHS はその分を0のまま Optimal を返すため。この場合も「解けないときの扱い」の診断を行う

**変数**

- x(r,g,i,j)：保管場所 r から団体 g へ、申請品目 i の分として品目 j を運ぶ数（0 以上）。j = i のほか、代替ルールが許す j だけ変数を作る。S'(r,j) が 0 の場所（使用不可の部屋を含む）には作らない
- 代替ルールが j を許すのは、団体の区分が categories に入り、indoorOnly なら使用場所の rooms.kind が room で、needsConsent なら了承が declined でないとき。同じ j に当てはまるルールが2つ以上あれば cost の小さいもの、cost が同じなら code が先のものを使う
- 運び元の制限（S05）の対象の団体・申請品目は、指定した場所の変数だけを作る。代替先の品目にも同じ制限がかかる。制限が2つ以上あれば共通部分
- 最小変更モードでは、x を作った組み合わせのうち、前回の数（前処理 6）が正のものに、上限＝前回の数の別の変数 x̂ を作る。x を作らない組み合わせ（使用不可の部屋、了承を拒否した団体への置き換え、制限で外れた運び元など）には作らない（K-14）
- 変数は 団体 → 申請品目 → 品目の候補（j = i、次に品目の並び順）→ 場所 の順に作り、x̂ は対応する x の直後に置く

**目的関数**

```latex
\min \sum \big( W\, c_{\mathrm{sub}}(g,i,j) + A\, d(r,g) + e(r,g) - B\, p(g,i,j) \big)\, x(r,g,i,j) \; + \sum \big( W\, c_{\mathrm{sub}} + A\, d + e - B\, p - \mu \big)\, \hat{x}(r,g,i,j)
```

求めるのは、次の順の辞書式の最小である：①代替の重さの合計 → ②（最小変更モードのとき）前回と同じ台数の最大 → ③距離の合計 → ④休憩所への不可椅子の台数の最大 → ⑤運び出す台数（同じ距離なら残す方）。係数はすべて整数にし、上の段の差が1でもあれば下の段の合計では覆せない値にする（P-02 を、休憩所の数や解の形に依らず成り立つ形にしたもの）。

- c_sub：代替の重さ（ルールの cost。0〜10 の整数）。j = i なら 0。S01・S02（不可机・不可椅子）は 0（普通の机・椅子と同じ扱い）。S04（企業の長机3→2）は 1。S07（キャスター机）は 3
- d(r,g)：距離コスト（次の節。整数）
- e(r,g)：運び元が団体の使用場所でなければ 1、使用場所なら 0。距離が同じ解の中で、自室の備品を外へ出して運び込む形を避け、残す方を選ぶ
- p(g,i,j)：preferCategory つきの代替で、団体の区分が preferCategory なら 1（S02 の休憩所への不可椅子）。それ以外は 0
- K＝LP の需要の制約の数、P＝そのうち p = 1 の変数を含む制約の数、d_max＝作った変数の d の最大（1 未満なら 1）として
  - B = K + 1、A = B·P + K + 1、U = A·d_max + B + 1
  - μ = K·U + 1（最小変更モード。全体の実行では x̂ を作らないので 0）
  - W = K·(U + μ) + 1
- 上の値で足りる理由：2つの解の差は、二部グラフの単純な閉路と、在庫の点どうしを結ぶ単純な道に分けられる。どれも需要の点を高々 K 個通り、1点あたりの差は e・p・前回の台数が ±1、d が ±d_max に収まるので、閉路1つでの下の段の差の合計は、上の段の1単位より必ず小さい
- μ は、前回の1台を守ることを、どれだけ距離を縮めることよりも優先する値にした。1台ぶんの値（d_max + 1）では、前回の1台を手放してほかの何台かの距離を縮める解が選ばれうる（T06 の設計で、小さな入力の総当たりで確認）。これにより次が成り立つ（D-08）：部屋 M を使用不可にしたとき、M から受け取っていた団体・申請品目の失った分を、前回のほかの行を変えずに、その団体がルール上使える場所の余りから、代替の重さの合計を増やさずに補えるなら、前回の M 以外の行は減らず、増えるのは M から受け取っていた団体・申請品目の行だけ（失った分を、その団体がすでに受け取っている場所から補うと、その行の数が増える）で、M と無関係な行は変わらない
- 品目全体に余りがあっても、上の条件を満たすとは限らない。運び元の制限（S05）・代替の区分・了承の拒否で、M から受け取っていた団体の使える場所が限られると、代替を増やさないために無関係な団体の行を押し出す解が選ばれる（代替の重さが前回の維持より先なので、これも正しい最適解である）。例：設営が S05 で {M, R2} からしか受け取れず、R2 の机を団体 A も使っていたとき、M を使用不可にすると、設営は R2 の机を受け取り、A は別の部屋から受け取る形に変わる
- R8 規模（T00 のダミー：K = 170、P = 2、d_max = 7）では、全体の実行で W = 639,711、最小変更モードで μ = 639,711・W = 109,390,581。係数の最大は約 3.3×10⁸ で、HiGHS は整数の解を返し、時間も変わらない（1回 40 ms 前後）。係数の最大 × 需要の合計が 2⁵³ を超えるときはエラーにする。係数が大きくても辞書式の最小が返ることは、段ごとに LP を解く検算と比べるテストで確かめる

**制約**

```latex
\sum_{g,i} \big( x(r,g,i,j) + \hat{x}(r,g,i,j) \big) \le S'(r,j) \quad \forall r,j
```

```latex
\sum_{r,j} \big( x(r,g,i,j) + \hat{x}(r,g,i,j) \big) = D'(g,i) \quad \forall g,i
```

```latex
0 \le \hat{x}(r,g,i,j) \le \text{前回の数}
```

これは「保管場所×品目」から「団体×申請品目」への二部グラフ上の輸送問題なので、制約行列は完全単模である（変数の上限と、x̂ のような列の複製を足しても変わらない。目的関数の係数は制約行列に関係しない）。右辺と上限はすべて整数なので、HiGHS の単体法（`solver: 'simplex'`）で解けば、最適解は整数で返る。念のため、各値を四捨五入して差が 1e-6 を超えたらエラーにする。

**決定性**

- 入力の並び順に依らないよう、allocate の中で並べ直す（「入力と出力」）。変数の順は「変数」のとおり。在庫の制約は 場所 → 品目、需要の制約は 団体 → 品目 の順に書く。LP には整数だけを書き、折り返さない（数万字の行も読める）
- highs-js は 1.15.4 を package.json に exact で固定し（packages/allocator の devDependencies と apps/web の dependencies）、オプションを `{ solver: 'simplex', random_seed: 0, time_limit: 30, output_flag: false }` に固定する。時間で打ち切らないので、同じ入力なら同じ解になる
- 解は `Status` が `'Optimal'` のときだけ使う。`'Infeasible'` と `'Primal infeasible or unbounded'` は解けない（infeasible）、それ以外（`'Time limit reached'`、`'Unbounded'`、`'Unknown'` など）は solver_error として返す。途中の解は使わない
- LP 形式の変数名に UUID は使えない（`-` や数字始まりは不可）ので、`x123` のような連番にして対応表を持つ（x̂ も同じ通し番号）
- highs の読み込み（`loadHighs`）に渡すオプションのオブジェクトは、呼ぶたびに新しく作る（highs.js が書き換えるので、使い回すと2回目が TypeError になる）。読み込んだインスタンスは使い回してよい（solve は呼ぶたびに新しい内部のソルバーを作る）
- highs-js を上げるときは、R8 と合成データの回帰テストで rows が変わらないか確かめる

**ルールの params と扱い**

| kind | params の例 | 扱い |
| --- | --- | --- |
| substitute | `{"from":"desk","to":"desk_ng","categories":["stall"],"cost":0}` | 条件を満たす団体にだけ j ≠ i の変数を作り、c_sub = cost（S01） |
| substitute | `{"from":"chair","to":"chair_ng","categories":["rest_area","stall"],"cost":0,"preferCategory":"rest_area"}` | preferCategory の団体への代替の変数は p = 1（S02） |
| substitute | `{"from":"long_desk_3","to":"long_desk_2","categories":["company"],"cost":1}` | 企業の長机(3人掛)が足りないとき（S04） |
| substitute | `{"from":"desk","to":"caster_desk","categories":["stall"],"indoorOnly":true,"cost":3,"needsConsent":true}` | 使用場所の rooms.kind が room の団体だけ。了承が declined の団体には変数を作らない（S07） |
| source_restrict | `{"group":"<設営の id>","items":["desk"],"rooms":["<1-1 の id>","…"]}` | 対象の団体・申請品目は、指定した場所以外の変数を作らない。代替先の品目も同じ（S05） |
| fixed_request | `{"group":"<設営の id>","item":"desk","count":241}` | 前処理 2。対象の団体が未提出のときだけ（S06・D-07） |
| keep | `{"group":"<学科展示の id>","room":"<第一多目的室の id>","items":{"desk":12,"chair":4}}` | 前処理 3。自動実行のたびに残すの行を作る（S08・D-06） |

params は packages/shared の zod スキーマ（余計なキーを許さない strictObject）で検証してから保存する。cost は 0〜10 の整数（整数でないと目的関数の段の分け方が崩れる）、indoorOnly・needsConsent の既定は false、preferCategory は categories のどれか。団体と場所は画面で名前から選び、id で保存する。品目は年度をまたいでも変わらないコードで持つ。allocate も実行の最初に同じスキーマで検証し、参照先の団体・場所・品目がなければ invalid_input を返す。

is_keep は、運び元 r が団体の使用場所と同じ行に付ける（残すのルールの行に限らない。DB も保存のときに同じ規則で決め直す）。そのとき d(r,g) = 0・e = 0 なので、自室の備品は自然にその団体が残して使い、距離が同じなら残す方が選ばれる。それでも自室から同じ品目を外へ出しつつ運び込む結果になったら W107 で知らせる。

## 距離コスト

d(r,g) は保管場所 r と団体 g の使用場所 L の位置関係で決める段階値（整数）。正確な距離は測らない。値は R8 のデータで結果を見て調整する（[概要](00_overview.md) の未決事項）。上から順に、最初に当てはまるものを使う。階が null の部屋（体育館など）は1階として扱う。

| 順 | 位置関係 | d |
| --- | --- | --- |
| 1 | 使用場所がない団体（校内分散の美化など）へ | 4 ＋ 追加コスト |
| 2 | 同じ部屋（残す） | 0（追加コストは足さない） |
| 3 | 屋外の使用場所へ（運び元が屋外か1階以下なら） | 3 ＋ 追加コスト |
| 3 | 屋外の使用場所へ（運び元が2階以上なら） | 5 ＋ 追加コスト |
| 4 | 屋外の保管場所から、建物の使用場所へ（使用場所が1階以下なら 3、2階以上なら 5） | 3 か 5 ＋ 追加コスト |
| 5 | 同じ建物・同じ階 | 1 ＋ 追加コスト |
| 5 | 同じ建物・別の階 | 2 ＋ 追加コスト |
| 6 | 別の建物（体育館を含む。建物が null の部屋を含む） | 4（上書きがあればその値）＋ 追加コスト |

- 追加コストは運び元の rooms.extra_cost（0〜20 の整数）。運び出しにくい部屋（R8 で「4号棟より遠い」とされた CI5 など）に設定する。運び元が使用場所と同じとき（2）は足さない（足すと、追加コストのある部屋を使う団体が、自室の在庫より他所を選びうる）
- 建物どうしの距離が表と合わないときは distance_overrides（建物A、建物B、コスト。コストは 0〜20 の整数）で上書きする。上書きは 6 の「別の建物」の 4 だけを置き換え、建物の組の向きは問わない（DB は建物A < 建物B で保存する）。同じ建物（5）と屋外（3・4）には効かない
- 追加コストと上書きのコストを整数・0 以上・20 以下にするのは、目的関数の段の分け方（整数の差が1以上）を保ち、係数を大きくしすぎないため。範囲外なら allocate は invalid_input を返す
- 体育館は rooms.kind = gym、building に建物名を入れた1つの建物として扱う
- 屋内・屋外は rooms.kind で判断する（outdoor なら屋外、それ以外は建物の中）
- 上書きがなければ、この表は三角不等式（d(r,h) ≤ d(r,L) ＋ d(L,h)）を満たす（種類・建物・階・追加コストの全組み合わせで確認）。上書きで崩れることがあるので、W107 は「入れ替えても距離の合計が増えない」ときだけ出す（検証コード一覧）
- d_max（W と μ の計算に使う）は、作った変数の d の最大

## 解けないときの扱い

解けないときは振り分けを書き換えず、「何が何台足りないか」と「どのルールが原因か」を返す。輸送問題なので、解き直しは1回あたり数十ミリ秒で済む。allocate（T06）が見つけて返すものと、diagnose（T07）が調べるものは次のとおり。

| 場面 | reason | 返すもの |
| --- | --- | --- |
| 入力の形・参照先が不正 | invalid_input | inputErrors |
| 前処理で止めるもの（固定行・残すが在庫を超える E001、残すのルールの部屋が使用不可の E002・使用場所でない E005） | precheck | issues（該当の行・ルール） |
| 前処理 7 の、候補が足りない需要 | infeasible | shortages（団体つき）と diagnose の結果 |
| HiGHS が `Infeasible`・`Primal infeasible or unbounded` | infeasible | diagnose の結果 |
| HiGHS がそれ以外の状態、値が整数でない、結果の自己検算が合わない | solver_error | message |

diagnose は次の順に調べる。最小変更モードの入力でも、全体の実行として調べる（x̂ は上限つきの複製なので、解けるかどうかに関係しない）。

1. 申請品目ごとに、需要の合計 ΣD' と、その品目に使える在庫の合計 ΣS'（代替先の品目を含む。固定分は前処理で引き済みなので、もう一度引かない）を比べ、需要の方が多い品目を shortages（団体は null）に入れる（例：「机(木)が12台足りません」）。代替先の品目が複数の申請品目で共有される場合や、運び元の制限がある場合もあるので、ここで空でも解けないことはある
2. 1 の結果にかかわらず（品目全体の不足があっても、前処理 7 で団体ごとの不足が見つかって LP を作らなかった場合も）、設定ルールを1つずつ外して解き直し、解けるようになったルールを causes に入れる。解き直しでは、外したルールで前処理 1〜7 からやり直し、前処理で止まらず、前処理 7 の不足も出ず、HiGHS が Optimal を返したときに「解けた」とする。代替ルールは外すと選択肢が減るだけで解けるようにはならないので対象外で、運び元の制限（source_restrict）、残す（keep）、固定の申請（fixed_request。K-26）を試す。品目全体の不足があっても試すのは、固定の申請と残すは品目全体の需要と在庫を変えるので、外すと不足が消えることがあるため。causes には、そのルールが関わる需要と在庫を添える（運び元の制限なら、対象の団体・品目の需要と、指定した場所の在庫合計）
3. どれを1つ外しても解けず、1 の品目全体の不足もないときは、運び元の制限の対象ごとに「需要」と「その場所の在庫合計」を並べ、「複数の条件の組み合わせが原因」と表示する。品目全体の不足があってどのルールでも解けないときは、在庫そのものが足りない（1 の表示で示す）
4. 返す shortages は、1 の品目全体の不足と、前処理 7 の団体ごとの不足を合わせたもの

例：S05 の部屋（1-1〜2-3）の机(木)の合計が 235 台で、設営の需要が 241 台のときは、前処理 7 で団体ごとの不足（設営・机(木)・需要241・在庫235）として止まる。机は全体では足りるので 1 は空で、2 で S05 を外すと解けるので、causes に S05 が入る。

画面では「設営の机(木)：需要241、1-1〜2-3 の在庫合計235」のように表示し、ルールを変えるか、申請や固定行を直すかは管理者が決める。固定行が在庫を超えている場合は、前処理の段階で E001 として該当の行を示す。固定行の運び元が使用不可になった場合（了承済みのキャスター机交換の部屋を使用不可にしたときなど）は、計算は止めずに、検証の E002 が該当の行を示す（直すまで確定できない）。

## 検証コード一覧

検証は `packages/allocator` の `validate(data, rows): Issue[]` で行い、自動実行後と手動修正のたびに画面で呼ぶ。data は allocate の入力と同じ年度のデータ（YearData。AllocateInput をそのまま渡してよい）、rows はその年度の全行（固定・手動・自動・残す）。error が1件でもあると「確定」ボタンを押せない。warning は確認した上で確定できる。E001・E002・E005 は、確定の RPC の中で DB 側でも確かめる。

| コード | 重さ | 条件 | 表示例 |
| --- | --- | --- | --- |
| E001 | error | 保管場所・品目ごとの振り分け合計 > 在庫 | HI3 の机(木) が 2 台在庫超過 |
| E002 | error | 使用不可の部屋からの振り分けがある | 第一セミナーは今年使えません |
| E003 | error | 団体・申請品目ごとの振り分け合計（代替を含む） < 需要（前処理1・2を当てた後の申請。D-05・D-07） | 野球部の長机(2人掛) が 2 台不足 |
| E004 | error | ルール違反（代替の区分、運び元の制限、了承しなかった団体への置き換え）。行の申請品目が、団体の区分で申請できない品目（企業以外の長机(3人掛)は長机(2人掛)と読み替えてから判定） | 設営に不可机が割り当てられています（S01） |
| E005 | error | 残すの行で、運び元が団体の使用場所と違う | 「残す」は使用場所の部屋だけです |
| E006 | error | 申請できない区分の申請がある（企業以外の長机(3人掛)は前処理1で読み替えるので除く。D-05）。自動振り分けはこの申請を除いて計算する | 剣道部(飲食)は不可机を申請できません |
| W101 | warning | 振り分け合計 > 需要（前処理1・2を当てた後の申請） | 剣道部(飲食)の机(木) が申請より 2 台多い |
| W102 | warning | キャスター机への置き換えがあり、了承がまだ | 2年2組：机(木)24 → キャスター机（了承待ち） |
| W103 | warning | 1団体・1品目の運び元が4か所以上 | SE技術の机(木) が 4 か所に分かれています |
| W104 | warning | 保管場所（is_storage）のうち、今年の在庫がひとつも数えられていない場所がある（使用不可の部屋は除く） | MER の在庫がまだ数えられていません |
| W105 | warning | 申請が未提出の団体がある（submitted_at が null） | 3団体が未提出 |
| W106 | warning | 提出済みの団体で、fixed_request と申請の数が違う（未提出なら fixed_request の数を使うので出さない。D-07） | 設営：固定241、申請230 |
| W107 | warning | 団体 g の使用場所 L から品目 j が外（使用場所が L でない団体 h）へ出ているのに、g が L 以外の場所 r から同じ j を受け取っている。ただし、次の両方を満たす組み合わせがあるときだけ出す：(1) 入れ替え（g が L の j を使い、h が r の j を使う）がルール（代替の区分・了承・運び元の制限・使用不可）の上でできる、(2) 入れ替えても距離の合計が増えない（d(r,h) ≤ d(r,g) ＋ d(L,h)）。同じ部屋を使う別の団体へ渡す分は「外へ出ている」に数えない。この定義では、全体の実行の結果には出ない（出るのは最小変更モードで前回の行を保った場合と、手で決めた行） | CI3 の椅子(木)が外へ出ているのに、料理同好会が他の部屋から椅子(木)を受け取っています |
| I201 | info | 品目ごとの余り | 不可机 余り6（1-1：4、2-3：2） |

Issue の形：`{ code: 'E001' | … | 'I201'; severity: 'error' | 'warning' | 'info'; message: string; refs: { roomId?: string; groupId?: string; itemId?: string; requestedItemId?: string; ruleCode?: string; rowIds?: string[] } }`。画面では refs で該当行に飛べるようにする（rowIds は DB から読んだ行の id。保存前の行にはない）。並びは error → warning → info、次にコード、次に場所・団体・品目の並び。

検証は、行の申請品目にも前処理1と同じ読み替え（企業以外の長机(3人掛) → 長机(2人掛)）を当ててから比べる。W102 は DB 設計の差分 3-3 の条件（了承の記録がない、または了承した台数 count より今の置き換え台数が多い）で、了承が要る代替ルール（needsConsent）の行を団体ごとに足して比べる。

## Excel出力仕様

R8 の「R8 椅子机振り分け(部門員共有用).xlsx」と同じ様式で、ブラウザで作って出す。受け取った人が Excel で直しても合計が合うよう、合計・余り・警告は数式で書く。ExcelJS は数式を計算しないので、数式と一緒にアプリで計算した結果の値も書き、ブックに fullCalcOnLoad を設定する（プレビューで空欄にならないように）。色は付けない。

**ファイル名**：`{年度}_椅子机振り分け_部門員共有用.xlsx`

**シート構成**（この順）

1. 机(木)（机と不可机を2列で）
2. 椅子(木)（椅子と不可椅子を2列で）
3. キャスター机
4. 椅子(青)
5. 長机(3人掛)
6. 長机(2人掛)
7. 教卓
8. 団体別集計

**品目シート（1列のもの）**

| 列 | 見出し | 中身 |
| --- | --- | --- |
| A | 運び元 | 部屋のブロックの先頭行だけに部屋名 |
| B | 運び先 | 使用場所。残すは「残す」、使用不可は「残す」＋C列「使用不可」 |
| C | 使用用途 | 団体名（集計シートのSUMIFのキー） |
| D | 個数 | 数 |
| E | 備考 | 特記事項のみ（「キャスター机に交換」など）。行の備考（allocations.note）があればそれを書く。なければ、了承が要る代替（needsConsent。R8 は S07）の行に「{品目名}に交換」を自動で書く。計の行では警告式 |
| F | 在庫(R○数え) | 計の行だけに在庫数 |

各品目シートに出す保管場所は、その品目の在庫が1以上の場所と、その品目の振り分けがある場所。並びは rooms.sort_order。場所ごとのブロックは、振り分け行 → 余り行 → 計行の順。振り分けが無い場所も余り行と計行を出し、その場合は余り行の A 列に場所名を入れる。使用不可の場所は「運び先＝残す、使用用途＝使用不可」の1行に在庫の全数を入れる。例（簡略化したもので、R8 の実際の行とは違う。行17〜18が振り分け、行19が余り、行20が計）：

```csv
行,A,B,C,D,E,F
17,第二セミナー,外13,ハンドボール部,3,,
18,,外14,野球部,2,,
19,,余り,,=F20-SUM(D17:D18),,
20,,,(計),=SUM(D17:D19),"=IF(D19<0,""在庫超過"",IF(D20=F20,"""",""要確認""))",21
```

**品目シート（2列のもの：机(木)・椅子(木)）**

D＝机（椅子）、E＝不可机（不可椅子）、F＝備考（1列のシートの E 列と同じ中身。1行にまとめた2つの行に備考があれば「、」でつなぐ）、G・H＝在庫。同じ（運び元・運び先・団体）の机(木)の行と不可机の行は1行にまとめ、D と E に並べる（椅子も同じ）。余りは `=G{計}-SUM(D…)` と `=H{計}-SUM(E…)`、警告は `=IF(OR(D{余}<0,E{余}<0),"在庫超過",IF(AND(D{計}=G{計},E{計}=H{計}),"","要確認"))`。

**団体別集計**

- 列：区分、団体、机(木)、不可机、椅子(木)、不可椅子、キャスター机、椅子(青)、長机(3人掛)、長机(2人掛)、教卓、机計(木＋不可)
- 各セル：`=SUMIF('シート'!$C:$C,$B{行},'シート'!$D:$D)`（不可は E 列）。SUMIF の条件は、`*` `?` `~` をワイルドカード、先頭の `=` `<` `>` を比較演算子として読み、英字の大文字・小文字を区別しない。また集計の4行は C 列の「(計)」「使用不可」をキーにする。そのため団体名に、半角の `*` `?` `~` を含むもの、先頭が半角の `=` `<` `>` のもの、「(計)」「使用不可」「余り」「残す」と同じもの、同じ年度の他の団体と大文字・小文字（と全角・半角）だけが違うものは使えない（団体の登録と取り込みで止め、出力でも見つけたらファイルを作らない。K-21）
- 最後に4行：使用数 計（SUM）、在庫（`SUMIF(…,"(計)",在庫列)`）、使用不可（残す）（`SUMIF(…,"使用不可",…)`）、余り（在庫 − 使用数 − 使用不可）
- 団体の並び：模擬店 → 部門 → 企業 → 休憩所、区分の中は申請順（提出日時の順。未提出の団体は最後。同じ日時・未提出の中は sort_order → 名前 → id。K-27）。CSV で取り込んだ団体の提出日時は、フォームのタイムスタンプ（[画面とAPI](04_screens_api.md) の「CSV取り込み」）

**その他の出力**

- キャスター机交換依頼一覧：了承が要る代替（needsConsent。R8 は S07 の机(木)→キャスター机）だけを団体ごとにまとめた表（団体・企画名・場所・台数・了承状況）。不可机や長机の代替は入れない
- 年度データ（JSON）：場所・品目・団体・在庫・申請・ルール・振り分け・了承をまとめて書き出す。年度末のバックアップに使う（メールアドレスは含めない）
- フェーズ2で配布スケジュール（屋外・屋内・部門・企業・その他・時間別）

**確認方法**：出力したファイルを LibreOffice の headless で再計算し、#REF! などのエラーが0件、「在庫超過」「要確認」が0件であることを CI のテストで確かめる。
