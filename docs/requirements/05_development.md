# 開発の進め方

## リポジトリ構成と環境変数

GitHub の組織の公開リポジトリにする。pnpm workspace のモノレポで、振り分けロジックを画面から切り離して単体テストできるようにする。コードに秘密情報は入れず、テストデータ（fixtures）にも個人情報を入れない。

```
denpa-somu/
├─ apps/web/                 Next.js（App Router、output: 'export'）
│   ├─ app/(auth)/login
│   ├─ app/(staff)/          総務向け：dashboard, allocation, swaps, requests, stocks, stock, rules, settings, history
│   ├─ app/(group)/          団体向け：request, my
│   ├─ workers/              振り分けの Web Worker
│   └─ lib/supabase/         ブラウザ用クライアント
├─ packages/allocator/       allocate()、validate()、LP の組み立て（DB に依存しない）
├─ packages/exporter/        ExcelJS による xlsx、年度データの JSON
├─ packages/importer/        Googleフォーム回答の CSV 取り込み
├─ packages/shared/          zod スキーマ、型、定数（品目コードなど）
├─ supabase/migrations/      DDL、RLS、トリガー、RPC
├─ supabase/tests/           pgTAP による RLS・RPC のテスト
├─ supabase/seed.sql         品目・場所・R8 のデータ（個人情報なし）
├─ fixtures/r8/              R8 の在庫・正規化した申請・手作業の振り分け（テスト用）
└─ .github/workflows/        ci.yml、deploy.yml（GitHub Pages）、migrate.yml
```

| 環境変数・秘密 | 置き場所 | 用途 |
| --- | --- | --- |
| NEXT_PUBLIC_SUPABASE_URL | GitHub Actions の変数、.env.local | クライアント接続 |
| NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY | GitHub Actions の変数、.env.local | クライアント接続（公開してよい鍵） |
| SUPABASE_ACCESS_TOKEN、SUPABASE_DB_PASSWORD | GitHub Actions の secrets | migrate.yml で本番 DB にマイグレーションを適用するときだけ |

アプリは secret（旧 service_role）キーを使わない。GitHub Pages は組織名.github.io/リポジトリ名/ で公開されるので、Next.js の basePath をリポジトリ名に合わせ、Supabase Auth のリダイレクト URL にも登録する。ローカルは `supabase start`（Docker）で DB を立ち上げ、`supabase db reset` でマイグレーションと seed を流す。.env ファイルはコミットしない。

## ブランチ・レビュー・CI

- main が本番。main へのマージで deploy.yml が静的書き出しをビルドし、GitHub Pages に公開する。作業は `feat/<チケットID>-<内容>` ブランチで行い、PR で main に入れる
- 公開リポジトリなので、GitHub Free の組織でも保護ブランチ（1人の承認と CI の通過を必須）を使える
- PR ごとのプレビュー URL はない。画面の変更は PR にスクリーンショットを貼るか、レビュアーがローカルで確かめる
- migrations と RLS・RPC を変える PR は、管理者役の開発者が必ず見る。本番 DB への適用は、マージ後に手動実行のワークフロー（migrate.yml）で行う
- CI（ci.yml）で次を実行し、すべて通らないとマージできない：
  1. `pnpm lint` と `pnpm typecheck`
  2. `pnpm test`（Vitest：allocator・exporter・importer・shared）
  3. `supabase test db`（pgTAP：ロールごとに読める・書ける範囲、RPC の権限）
  4. Playwright（ログイン → 申請 → 自動振り分け → 確定 → 出力の通し）。Google ログインは CI で通せないので、ローカルの Supabase にだけメールとパスワードのテストユーザーを作って使う（本番ではメールログインを無効にする）
  5. `next build`（静的書き出しが通ること）
- コミットメッセージは Conventional Commits（feat: / fix: / docs: など）
- 仕様を変えるときは、先にこの要件定義書を直してから実装する

## 受け入れ基準とR8テストデータ

フェーズ1の完了条件は、R8 の正規化した申請で自動振り分けをしたとき、下の条件をすべて満たすこと。R8 の手作業の振り分け表と、運び元や置き換え先が一致しなくてよい（不可机・不可椅子の使い方も、距離で決めるので R8 とは変わる）。[概要](00_overview.md) の開発スケジュールの判断ポイントも、この基準で判断する。

**fixtures/r8 の作り方**

- 在庫：R8 の「机・椅子数え」の最終値。第一セミナーは使用不可
- 申請：R8 のフォーム回答に、R8 で決めた読み替えを当てた後・代替の前の数。例：SE企画の長机(3人掛)→キャスター机6、剣道部の机2・椅子1の追加、設営241、四役・休憩所・企業の代理入力分、企業以外の長机(3人掛)→長机(2人掛)。変換の一覧は fixtures/r8/README.md に書く
- 剣道部は「剣道部(飲食)」と「剣道部(非飲食)」の2団体に分ける
- 参考として、R8 の手作業の振り分け表（団体別集計）も入れておく

**R8 の実績（参考。アプリの結果と一致しなくてよい）**

| 品目 | 在庫 | 使用不可（第一セミナー） | 振り分け計 | 余り |
| --- | --- | --- | --- | --- |
| 机(木) | 506 | 0 | 506 | 0 |
| 不可机 | 41 | 0 | 35 | 6 |
| 椅子(木) | 493 | 0 | 359 | 134 |
| 不可椅子 | 40 | 0 | 13 | 27 |
| キャスター机 | 180 | 1 | 132 | 47 |
| 椅子(青) | 432 | 49 | 134 | 249 |
| 長机(3人掛) | 8 | 0 | 8 | 0 |
| 長机(2人掛) | 127 | 25 | 98 | 4 |
| 教卓 | 27 | 2 | 10 | 15 |

「振り分け計」には残すの行も含む。R8 は不可机6台を予備にしてキャスター机への置き換えを103台にしたが、アプリは予備を持たない。

**不変条件（Vitest）**

- [ ] 解ける（ok: true）。E001〜E006 が0件
- [ ] すべての団体・申請品目で、振り分け合計（代替を含む）が正規化した申請と等しい
- [ ] 設営の机(木)241台がすべて 1-1〜2-3 から出ている（S05）
- [ ] 不可机は模擬店にしか、不可椅子は休憩所と模擬店にしか割り当てられていない（S01・S02）
- [ ] 長机(3人掛)は企業にしか割り当てられていない（S03）
- [ ] キャスター机への置き換えは R8 の103台以下。不可机を先に使い切るので、R8 より少なくなるはず（レビューの再現実行では97台）
- [ ] 代替が起きない品目の合計が R8 と同じ：椅子(青)134、教卓 10、長机（3人掛＋2人掛）106
- [ ] 学科展示の机12・椅子4が第一多目的室の残すになっている（S08）
- [ ] W107（自室の備品を外へ出して運び込む）が0件
- [ ] 同じ入力で2回実行すると同じ結果になる。DB から読む順序を変えても、並べ替え後の入力が同じなら同じ結果になる
- [ ] 固定行・手動行を入れて再実行すると、その行は変わらず、二重に割り当てられない
- [ ] 第一セミナーを使用不可にして最小変更モードで再実行すると、第一セミナーから運んでいた行以外は変わらない（変わった行の数をテストで記録する）
- [ ] 了承を「拒否」にした団体には、再実行後にキャスター机への置き換えがない
- [ ] 申請を在庫より多くすると ok: false で、shortages に品目と不足数が入る。S05 が原因の入力では causes に S05 が入る
- [ ] ブラウザ（Chromium）で R8 入力の計算が2秒以内
- [ ] 出力した xlsx を LibreOffice で再計算して、数式エラー0件・「在庫超過」「要確認」0件、団体別集計の値がアプリの値と一致する

**画面の受け入れ（総務で確認）**

- [ ] 部員がスマホで1部屋の在庫を1分以内で入力できる
- [ ] 団体代表が説明なしで申請を提出できる（総務以外の2人以上で試す）
- [ ] 管理者が第一セミナーを使用不可にして最小変更で再実行し、出力までを5分以内で終えられる
- [ ] 団体代表は他の団体の申請を見られない。招待されていない人は何も見られない（Supabase の API を直接呼んでも）

fixtures には企業や学生のメールアドレスなどの個人情報を入れない。R8 のフォーム回答から変換するときに importer で除く。
