# 開発の進め方

## リポジトリ構成と環境変数

GitHub の組織の公開リポジトリにする。pnpm workspace のモノレポで、振り分けロジックを画面から切り離して単体テストできるようにする。コードに秘密情報は入れず、テストデータ（fixtures）にも個人情報を入れない。

```
GAapp/
├─ apps/web/                 Next.js（App Router、output: 'export'）
│   ├─ app/(auth)/           login、auth/callback（Google から戻る先）
│   ├─ app/(app)/            ログインが要る画面（共通レイアウトの中）。全員：/（ダッシュボード・ホーム）。机椅子：furniture（机椅子の状況）, allocation, swaps, requests, stocks, stocks/qr, stock, rules（ここまで総務向け）, request, my（団体向け）。共通：settings, history。機能のチケットは自分の機能のパスを足す（D-52）
│   ├─ components/           ui/（shadcn/ui の部品。手で置く）、common/（表・数の入力・理由の入力・エラーの帯など画面に共通の部品）、layout/・auth/・states（T04）、portal/（ダッシュボードの欄。T16）、画面ごとの部品（dashboard/〔机椅子の状況。T09 からの名前のまま〕・settings/・stock/ など）
│   ├─ workers/              振り分けの Web Worker（highs を読み込むのはここだけ）
│   ├─ public/               highs.wasm（predev・prebuild で highs からコピー。git に入れない）。PWA のマニフェストとアイコンは app/ のファイルの規約（manifest.ts・icon.png・apple-icon.png）
│   └─ lib/                  supabase/（ブラウザ用クライアント）、auth/（ログイン状態・今の年度の立場・年度の切り替え・ロールの段）、navigation（見出しごとのメニューと、画面を開ける立場）、modules/（機能の登録 registry.ts・ダッシュボードの型 portal.ts・ダッシュボードに出すものの一覧 providers.ts・機能ごとのフォルダ〔furniture/〕。D-52）、db/・rpc/（読み書きの補助と RPC の引数・返り値の zod）、errors（エラーの分類と日本語）、drafts（保存していない入力の下書き）、data/（画面ごとの読み書き。版を先に読むスナップショット）、allocation/（振り分け画面の純粋関数と Worker の呼び出し）、schemas/（入力の zod）
├─ e2e/                      Playwright。setup/（年度をまたぐ表を1回だけ入れる・ログインの保存）、support/（シナリオの年度・データセット・使い捨てのユーザー・スクリーンショット。ローカルの DB にだけつなぐ）、チケットごとの *.spec.ts、serial/（年度の作成・年度をまたぐ表・通しの流れ。並行のテストの後に別に流す）、fixtures/（E2E 専用の入力。個人情報なし）、basepath/（basePath で書き出したもののスモーク）、shots/（スクリーンショット）・manual/（手での確かめのデータ作り）・perf.spec.ts（4G の速さ）は CI では流さない
├─ scripts/                  copy-highs-wasm.mjs、build-e2e.mjs、e2e.mjs（並行のテストと serial を別に流す）、first-load-js.mjs、local-supabase-env.mjs、check-emails.mjs など
├─ packages/allocator/       allocate()、validate()、LP の組み立て（DB に依存しない）
├─ packages/exporter/        ExcelJS による xlsx、年度データの JSON
├─ packages/importer/        Googleフォーム回答の CSV 取り込み
├─ packages/shared/          zod スキーマ、型、定数（品目コードなど）。testing/ に fixtures の読み書きと合成データ（Node 専用）
├─ supabase/migrations/      DDL、RLS、トリガー、RPC
├─ supabase/tests/           pgTAP による RLS・RPC のテスト（_helpers/ にペルソナと権限表のテストの補助）
├─ supabase/seed.sql         品目・テスト用の場所（T02）→ R8 の年度・テスト用の団体とユーザー（T04）→ R8 のデータ（T05。fixtures/r8 から scripts/build-seed-r8.ts で生成した区間。個人情報なし。D-40 で R8 の元データを使わないことにしたので、今は作らない）
├─ fixtures/r8/              R8 の在庫・正規化した申請・ルール、手作業の振り分け（reference/。テスト用。D-40 により今は作らない。仕組みだけ残す）
├─ fixtures/synthetic/       R8 と合計が同じ合成データ（scripts で生成。シード固定。reference/ は振り分けの結果から生成）
└─ .github/workflows/        ci.yml、deploy.yml（GitHub Pages）、migrate.yml
```

| 環境変数・秘密 | 置き場所 | 用途 |
| --- | --- | --- |
| NEXT_PUBLIC_SUPABASE_URL | GitHub Actions の変数、.env.local | クライアント接続 |
| NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY | GitHub Actions の変数、.env.local | クライアント接続（公開してよい鍵） |
| NEXT_PUBLIC_BASE_PATH | deploy.yml（リポジトリ名から作る） | GitHub Pages の basePath。ローカルと E2E は空 |
| NEXT_PUBLIC_GOOGLE_HD_HINT | GitHub Actions の変数（任意） | Google のアカウント選択を学校のドメインに絞るヒント。値は `g.kumamoto-nct.ac.jp`（D-04）。拒否は DB のフック |
| NEXT_PUBLIC_ENABLE_TEST_LOGIN | .env.local、E2E のビルド（pnpm build:e2e） | ローカル専用のメール＋パスワードのテスト用ログイン。本番のビルドには設定しない（設定しても Supabase がローカルでなければ出ない） |
| SUPABASE_ACCESS_TOKEN、SUPABASE_DB_PASSWORD | GitHub Actions の secrets | migrate.yml で本番 DB にマイグレーションを適用するときだけ |

seed は seed.sql の1本。R8 の区間は `-- BEGIN R8 DATA` と `-- END R8 DATA` の間で、手で直さない。R8 の年度は T04 の部分が固定の id で作り、R8 の区間はその年度に足す。品目は code で引く。R8 の区間は、R8 の元データを使わないことにした（D-40）ので今は作らない。

アプリは secret（旧 service_role）キーを使わない。GitHub Pages は組織名.github.io/リポジトリ名/ で公開されるので、Next.js の basePath をリポジトリ名に合わせ、Supabase Auth のリダイレクト URL にも登録する。ローカルは `supabase start`（Docker）で DB を立ち上げ、`supabase db reset` でマイグレーションと seed を流す。.env ファイルはコミットしない。

## ブランチ・レビュー・CI

- main が本番。main へのマージで deploy.yml が静的書き出しをビルドし、GitHub Pages に公開する。作業は `feat/<チケットID>-<内容>` ブランチで行い、PR で main に入れる
- 公開リポジトリなので、GitHub Free の組織でも保護ブランチ（1人の承認と CI の通過を必須）を使える。承認できる人がほかにいない間は、管理者が PR の中で承認だけを迂回できる（CI は迂回できない。手順は README。決定は D-41）
- PR ごとのプレビュー URL はない。画面の変更は PR にスクリーンショットを貼るか、レビュアーがローカルで確かめる
- migrations と RLS・RPC を変える PR は、管理者役の開発者が必ず見る。本番 DB への適用は、マージ後に手動実行のワークフロー（migrate.yml）で行う
- CI（ci.yml）で次を実行し、すべて通らないとマージできない：
  1. `pnpm lint` と `pnpm typecheck`
  2. `pnpm test`（Vitest：allocator・exporter・importer・shared）
  3. `supabase test db`（pgTAP：表・列・制約、トリガー（監査、確定中の守り）、権限表の全セル（表 × 操作 × 年度の状態 × ロール）を期待値の表から確かめる、RPC の権限・状態・楽観ロック・版、関数の execute と表の権限の棚卸し）。テストは `supabase db reset` の後の seed が入った DB で流す。テスト用のデータは seed の品目を使い、seed とぶつからない名前とメールのドメイン（`@pgtap.test`）にする
  4. Playwright（`pnpm e2e`。ログイン → 在庫 → 申請・取り込み → 締切 → 自動振り分け → 確定 → 出力 → 確定の解除 → 最小変更の通しと、画面ごとのテスト）。setup で、年度をまたぐ表（テスト用のデータセットの場所と距離の上書き）を並行のテストより前に1回だけ入れ（入れると振り分け中のすべての年度の版が上がるため。属性が食い違えば止める）、立場ごとに1回ログインして状態を保存する。chromium（並行）はテストごとに「シナリオの年度」をローカルの DB に作って閉じる（年度の表だけに書く）。serial（年度の作成〔create_year_from は全年度の中で最新の年度からしか作れないので、1日目を seed の R8 より後にしたシナリオの年度から、使い捨てのテストユーザーで作る〕、年度をまたぐ表〔場所・品目・距離〕の変更〔テスト専用の名前の行だけを作って変え、最後に消す〕、通しの流れ）は、`pnpm e2e`（scripts/e2e.mjs）が chromium の後に別に流す（chromium が落ちても serial の結果を残す。どちらかが落ちれば失敗）。setup は最初に、前の実行が途中で止まって残ったシナリオの年度・テスト用の行・使い捨てのユーザーを消す。シナリオの年度と使い捨てのテストユーザーは e2e/support の補助が `pg` でローカルの DB（127.0.0.1・localhost 以外なら止める）に直接作り、アプリとビルドには入らない（D-36）。通しの流れで出した xlsx は LibreOffice で再計算して確かめる（e2e ジョブで LibreOffice を入れる）。本番と同じ basePath（/GAapp）で書き出したものを別に配り、計算エンジンの wasm・QR の URL・マニフェストとアイコンを確かめる短いテストも流す（timeout-minutes は 25）。スクリーンショット（`pnpm e2e:shots`）、手での確かめのデータ作り、4G の速さの測定は CI では流さない。Google ログインは CI で通せないので、ローカルの Supabase（CI ではログインに要るコンテナだけを起動する）にだけメールとパスワードのテストユーザー（管理者・総務部門長・総務部門員・団体代表〔店長〕・閲覧のみ・未招待。総務部門長は T15b で足す。総務副部門長はテストごとの使い捨てのユーザー）を使う。テストユーザーは supabase/seed.sql で auth.users に直接入れて作り（Before User Created フックは通らない）、メールは予約済みのドメイン（`@example.test`）にする。seed は本番に流さず、本番ではメールログインを無効にする（D-02）。画面のテスト用ログインは E2E 用のビルド（`pnpm build:e2e`）にだけ入れ、本番と同じビルドに入っていないことを `pnpm check:no-test-login` で確かめる
  5. `next build`（静的書き出しが通ること）
- コミットメッセージは Conventional Commits（feat: / fix: / docs: など）
- 仕様を変えるときは、先にこの要件定義書を直してから実装する

## 受け入れ基準とR8テストデータ

フェーズ1の完了条件は、R8 の正規化した申請で自動振り分けをしたとき、下の条件をすべて満たすこと。R8 の手作業の振り分け表と、運び元や置き換え先が一致しなくてよい（不可机・不可椅子の使い方も、距離で決めるので R8 とは変わる）。[概要](00_overview.md) の開発スケジュールの判断ポイントも、この基準で判断する。

（注：D-40 により R8 の元データは使わない。下の不変条件は合成データ fixtures/synthetic/r8like で確かめ、R8 の実績との一致〔R8 の103台以下、代替が起きない品目の合計が R8 と同じ、R8 の振り分け表から出した xlsx など、R8 の元データでしか確かめられないもの〕は確かめない。2027年5〜6月の R8 のデータでの検証をどうするかは、そのときにユーザーが決める。）

**fixtures/r8 の作り方**

R8 の元データは使わず、合成データ fixtures/synthetic/r8like で代用する（D-40、2026-10-29）。fixtures/r8 と seed の R8 の区間は今は作らない。次は、R8 の元データを使うことになったときの作り方で、仕組み（scripts/build-r8-fixtures.ts・`REQUIRE_R8_FIXTURES`）は残してある。


- 在庫：R8 の「机・椅子数え」の最終値。第一セミナーは使用不可
- 申請：R8 のフォーム回答に、R8 で決めた読み替えを当てた後・代替の前の数。例：SE企画の長机(3人掛)→キャスター机6、剣道部の机2・椅子1の追加、設営241、四役・休憩所・企業の代理入力分、企業以外の長机(3人掛)→長机(2人掛)。変換の一覧は fixtures/r8/README.md に書く
- 剣道部は「剣道部(飲食)」と「剣道部(非飲食)」の2団体に分ける
- 参考として、R8 の手作業の振り分け表（行と団体別集計）も reference/ に入れておく
- 形式：UTF-8 の CSV（場所・団体・在庫・申請・了承〔依頼した台数を含む〕・距離の上書き）と JSON（ルール。団体・場所は名前で書く）。列は packages/shared の zod スキーマで決め、知らない列があれば読み込みを失敗にする。場所・団体・ルールの id は名前から決まる UUIDv5（名前空間の値は packages/shared）で、seed と Vitest で同じ id になる（品目と年度の id は DB の値。品目は code で対応させる）
- 個人情報：備考・氏名・学籍番号・連絡先の列は持たない。団体名に個人名（研究室名の教員名など）があれば仮名にし、対応表はリポジトリの外（`R8_SOURCE_DIR`）にだけ置く。fixtures と seed にメールアドレス（予約ドメインのテスト用を除く）がないことをテストで確かめる
- 合成データ（fixtures/synthetic/r8like）：T00 のダミーの作り方を移したもの。在庫と需要の合計を R8 にそろえる（在庫は下の表、需要の合計 1,295）。不変条件はこちらで確かめる（D-40。fixtures/r8 を作ったときは両方に流す）。reference/（振り分けの行と団体別集計）は振り分けの結果から scripts で生成してコミットし、Excel 出力のテストに使う
- fixtures/r8 がないときは、R8 の不変条件のテストを飛ばし、飛ばしたことをテストの出力に残す。fixtures/r8 を入れた後は、CI の変数（`REQUIRE_R8_FIXTURES`）で、見つからなければ失敗にする
- 元データにないもの（場所の建物・階・種類・並び、団体の区分・使用場所・並び・提出のしかた、ルール、R8 で決めた読み替えと代理入力の数）は手で書いてコミットし、根拠を README に書く。元データから決まるもの（提出日時、在庫、申請、手作業の振り分け）は scripts/build-r8-fixtures.ts が `R8_SOURCE_DIR` から生成する。どのファイルがどちらかと列は、T06 の設計書（notes/T06-design/logic-design.md の 3.8）のとおり。団体名の匿名化の対応表は `R8_SOURCE_DIR` にだけ置く
- 提出日時：フォームで提出した団体はフォームのタイムスタンプ（同じ団体の最後の回答）、総務が代理入力した団体（企業・休憩所・四役・設営など）は R8 の申請締切の日時、未提出の団体は空（W105）
- 手作業の振り分け（reference/）：振り分け表で1団体の剣道部は、2団体の申請を並び順に満たすように行を割り振る（2団体の和が振り分け表と一致することを確かめる）。申請品目は、不可机→机(木)、不可椅子→椅子(木)、備考が「キャスター机に交換」のキャスター机→机(木)、企業の長机(2人掛)は長机(3人掛)の申請の不足分まで長机(3人掛)、ほかは品目と同じにする。団体別集計は、振り分け表の行の合計と集計シートの値が合わない団体を除き、除いた団体を README に一覧で書く（Excel 出力のテストは残った団体で比べる）
