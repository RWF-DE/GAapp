# 画面とAPI

## 画面仕様

画面は[概要](00_overview.md)の画面一覧に対応する。Next.js の静的書き出し（output: 'export'）で作るため、id をパスに埋め込む動的な URL は使わず、クエリ文字列で渡す（/stock?room=…）。画面の中の切り替え（タブ・品目・団体・行・絞り込み）もクエリ文字列に入れ、再読み込みと共有で同じ表示に戻れるようにする。サーバーのデータは TanStack Query で持ち、書き込みの後に関係するものを読み直す。UI 部品は shadcn/ui（ソースを手で置く）、表は TanStack Table。すべての画面で、読み込み中・データが空・権限なしの3状態と、読み込みの失敗（もう一度読み込むボタンつき）を表示する。年度の状態で書けないときは入力欄を無効にし、理由を帯で出す（「年度が確定中のため編集できません」など）。日時は Asia/Tokyo で表示する。データの多い画面には、最後に読み込んだ日時と「読み直す」を出す。招待されていない人がログインすると「総務から招待されていません」だけを表示する。

### 共通レイアウト（P-03）

- ログインが要る画面は共通レイアウトの中に置く。ログインしていなければ /login に送り、ログイン後に元のページへ戻す（戻り先は同じサイトのパスだけ）
- ログインのたび（ページを開いたときも）に `accept_my_invitations` を呼んでから、自分の year_roles・group_members を読む。今の年度は、既定ではロールか団体代表の行がある年度のうち1日目が最も遅いもの（最新の年度）。そうした年度が2つ以上ある人には、ヘッダーに年度の選択（1日目の新しい順。「R9（準備中）」）を出し、選んだ年度はそのタブの中でだけ覚える（新しいタブや部屋の QR から開いたときは最新の年度）。覚えた年度にロールも団体代表もなくなっていれば既定に戻す。年度は URL に入れない（部屋の QR の URL を年度によらず同じにするため。在庫入力は開いている年度に書く）。最新でない年度を開いているときは「最新でない年度（R8・終了）を表示しています」と、最新の年度に切り替えるボタンを帯で出す。在庫入力・申請・了承の回答では、最新でない年度に書く前に確かめる（D-31）
- どの年度にもロールも団体代表もなければ「総務から招待されていません」とログアウトのボタンだけを出す（ナビゲーションも年度も出さない）
- ヘッダーに今の年度と状態、表示名と立場、ログアウト。ナビゲーションは PC では左、スマホではメニューのボタンで開く。項目は開いている年度の立場で出し分ける（[概要](00_overview.md)の画面一覧のロール。admin は総務の画面すべて、staff は在庫入力・在庫一覧・申請一覧・振り分け（閲覧）、viewer は振り分け（確定後の閲覧）、団体代表は申請・自団体の振り分け、兼ねた人は両方）。URL を直接開いたときも同じ立場で出し分ける（合わなければ権限なしの表示）。表示の出し分けは見た目だけで、データは RLS と RPC が守る
- 画面の中では、読み込み中・データが空・権限なし（立場が合わない）の3状態の部品と、読み込みの失敗の部品を使う
- 印刷（部屋の QR のカード）のときはヘッダーとナビゲーションを隠す。ログアウトはその端末のセッションだけを終える（同じ人のほかの端末は抜けない）。ログアウトと利用者の切り替えでは、画面が持っているデータ（キャッシュ）を消す。保存していない入力の下書きは、手動のログアウトでは（保存していない入力があれば確かめてから）その人の分を消し、別の人がログインしたときは前の人の分を消す（共用の PC で前の人のデータを残さない）。セッションが切れて強制的にログアウトしたときは下書きを消さない（同じ人がログインし直せば戻せる）
- 権限や年度の状態が変わったと分かって立場を読み直すときは、読み直しの間も今の画面を出したままにする（入力・開いているダイアログを消さない。読み込み中の表示に置き換えるのは、最初の読み込みと利用者が変わったときだけ）
- 画面の中のリンクは、行き先の画面を開ける立場のときだけリンクにする（開けない立場には件数や文字だけを出す）
- 保存していない入力がある画面では、アプリの中で別の画面へ移る前と、年度を切り替える前に確かめる。ブラウザの戻る・タブの破棄・別のアプリへの切り替えは止められないので、入力をそのブラウザに下書きとして置き、開き直したときに戻せるようにする（保存に成功したら消す）
- 書き込みのボタンは、送っている間は押せなくする（二重に送らない）。通信が切れて保存されたか分からないときは、自動では送り直さない。読み直して決める決まりは書き込みの種類で分ける（「DB関数とブラウザ側の処理」の通信が切れたときの項）

### ログイン /login（PC・スマホ）

- 「学校の Google アカウントでログイン」のボタン。ブラウザの PKCE フローで、リダイレクト先は basePath 込みの /auth/callback/（Supabase の Redirect URLs に登録する）
- フックで拒否されたとき（学校以外のアカウント）は「学校の Google アカウントでログインしてください」と出す。URL に付いたエラーの文言はそのまま表示しない
- ローカルだけ、メール＋パスワードのテスト用ログイン（E2E 用。D-02）を出す。ビルド時のフラグがあり、Supabase の URL がローカルのときだけ出し、本番のビルドにはコードごと入れない
- ログイン状態はブラウザに保存し（supabase-js）、トークンは自動で更新する
- LINE などのアプリの中のブラウザで開いたと分かるときは、「アプリの中では Google でログインできません。Safari か Chrome で開いてください」と URL のコピーのボタンを出す（Google のボタンは隠さない）

### ダッシュボード /（PC）

- 総務（admin・staff）にはダッシュボード、団体代表・閲覧のみにはホーム（下）を出す。総務で団体代表も兼ねる人には、ダッシュボードの上に団体代表のカードを出す
- 表示：年度のステータス、受付期間（開始・締切）、最後に自動振り分けを保存した日時、申請の提出数／団体数（区分ごとの内訳と、未提出の団体の名前。申請一覧の「未提出だけ」へ）、在庫を数えた保管場所の数／保管場所の数（使用不可の部屋を除く。まだ数えていない場所と、在庫入力へのリンク）、検証の error・warning・info の件数と多いコード（振り分け中と確定中だけ。それより前は「振り分け前」と出す。振り分けの行がないと E003 がすべての申請に出て意味がないため）、キャスター机交換の了承状況（未依頼・依頼済み・了承・拒否の団体の数、依頼し直しが要る団体、拒否したので最小変更での再実行が要る団体。キャスター机交換の画面と同じ数え方。部員にはキャスター机交換の画面へのリンクを出さず、数だけを出す）、入力の誤り（設定の壊れたルール、消した団体・場所を参照したままのルールなど。あれば件数と一覧。ルールならそのコード）
- 年度の状態を進めるボタン（管理者のみ。部員には出さない）。理由の入力欄つき。確定と確定の解除では理由が必須
  - 準備中 →「受付開始」：締切（request_close_at）が未来に入っていないとエラーになるので、入っていなければボタンを無効にし、受付期間の入力（マスタ設定）へ案内する
  - 受付中 →「締切（振り分けを始める）」：締切の前なら「団体代表は申請を変えられなくなります」と確かめる
  - 振り分け中 →「確定」（下）
  - 確定 →「確定を解除」（団体への公開も止まると確かめる）、「終了」（読み取り専用になり戻せないこと、先に年度データと振り分け表を書き出すことを確かめ、書き出しのボタンを並べる）
- 確定ボタン：画面を開いたときに、ほかのデータより先に years.allocation_version を読み、その版で検証（validate）を実行する。error が0件で、入力の誤り（設定の壊れたルール、消した団体・場所を参照したままのルールなど。検証に渡せないもの）がなく、検証した版が今の版で、振り分け画面に未保存の変更がないときだけ押せる（押せないときは理由を出す。DB の確定の検査はルール違反を見ないので、壊れたルールのまま確定させない）。warning があれば件数と多いコードを見せ、確認のチェックを入れてから押す。確定のときは検証した版を `set_year_status` の `p_base_version` に渡す。conflict が返ったら、読み直して検証をやり直し、結果を見せてから、もう一度確定を押してもらう（自動では再送しない）。E001・E002・E005 が返ったら、その一覧を部屋・品目・団体の名前で出す。確定のボタンと流れは、ダッシュボードと振り分け画面で同じ部品にする
- 版の見張り：版（allocation_version）を 60 秒ごとと画面に戻ったときに読み、ほかの人の変更で進んでいれば「ほかの人が振り分けの入力を変えました」と「読み直す」を帯で出す（自動では読み直さない）
- ホーム（団体代表。スマホも）：代表する団体ごとに、申請の状況（「提出済み（日時）」「未提出」）、締切、申請の画面へのボタン。キャスター机への交換の依頼があれば、自団体の振り分けの画面へのボタン。確定後は「振り分けが決まりました」と自団体の振り分けの画面へのボタン
- ホーム（閲覧のみ）：確定・終了なら振り分け表へのリンク。それより前は「振り分けが確定すると、ここから見られます」

### 在庫入力 /stock?room=…（スマホ）

- 表示：場所名、前回入力者と日時（その部屋で最後に保存した人と日時）、品目ごとの行（品目名、数、前年の数）。前年の数は前年度（複製元）の同じ部屋の数（previous_year_stocks）で、前年度がなければ列を出さない
- 操作：＋－ボタンと数字入力（0〜10000 の整数）、「保存」（画面の下に固定）。保存は部屋の全品目（0 を含む）を1回で書く（同じ数でも数え直した記録が残る）。保存すると DB が counted_by（保存した人）と counted_at（保存した日時）を入れる（画面から送らない）。保存の直前にその部屋を読み直し、読み込んだ後にほかの人が保存していれば、その人と時刻、相手の数と自分の数を並べて「上書きする」「読み直す」を選んでもらう。通信が切れて保存の応答が届かなかったときは、入力を残して「保存できたか分かりません。もう一度「保存」を押すと、確かめてから送ります」と知らせる（確かめるためのボタンは置かない）。もう一度「保存」を押すと同じく読み直し、すでに入力と同じ数が保存されていれば送らずに「保存されていました」とする（応答が届かなかった自分の保存は、ほかの人の保存として扱わない）。数を変えた・下書きを戻した・「保存」を押した後は、保存が決まるまで、裏で読み直した行で入力を置き換えない（ほかの人が保存していれば「ほかの人が保存しました」と知らせ、ほかの人の数にするのは利用者が選んだときだけ。入力がほかの人の数と違う間は、読み込んだときの数へ戻しても保存していない入力として扱う。下書きを捨てても入力は置き換えない）。書けなくなった（読み取り専用になった）ときは、読み直した数を出し（入力は下書きに残る）、「保存できたか分かりません」の知らせ・ほかの人の保存の確かめ・振り分けの合計の確かめを閉じ、確かめの途中でも送らない（また書けるようになっても知らせは出ない。開き直して下書きを戻せば、「保存」で確かめてから送る）。「保存できたか分かりません」は、このほかは次の保存が決まるまで消さない。保存の後は「次の部屋へ」（並び順で次の、まだ数えていない保管場所）を出す。保存していない入力があるまま離れるときは確かめ、入力は下書きとして残す（カメラで次の QR を読んだ・別のアプリへ行った後に開き直しても戻せる。下書きを消すのは、保存したとき・捨てたとき・読み込んだ行に下書きの数が書かれていたときだけ。ほかの人の数を読み直しても、戻していない下書きは残す。下書きを戻さずに「保存」を押した後に保存していない入力になったとき〔ほかの人が先に保存していた・保存できたか分からない〕は、「保存」を押した入力を選んだものとして、戻していない下書きをその入力で置き換える。入力に保存していないものがなくなったときは、書く中身がないので入力の分を書かない）。開いている年度が最新でないときは、最新の年度に切り替えるボタンを大きく出し、保存の前に「最新でない年度（R8）に保存します」と確かめる
- 場所の選び方：一覧から選ぶか、部屋に貼った QR（/stock/?room=… の URL）を読む。room がないときは保管場所の一覧（建物ごと、名前で絞れる、各部屋に「数えた（日時・人）」か「まだ」と使用不可の印）を出す。room が保管場所の一覧にない（消した部屋・形が違う）ときは「この場所は見つかりません」と一覧へのリンクを出す
- 状態：年度が allocating 以降なら部員は読み取り専用（「振り分けが始まったので、在庫は総務管理者だけが直せます」）。管理者は数え直しを入力でき、入力すると検証をやり直す。振り分け中に、振り分けの合計より少なくなる品目があれば、保存の前に「保存すると振り分けに在庫超過（E001）が出ます。振り分け画面で直してください」と確かめる。確定中は、振り分けの合計より少なくなる数は保存できない（「確定を解除してから」と表示する。DB の守りと同じ条件を画面でも先に確かめる）。終了した年度は読み取り専用。使用不可の部屋は先頭に「今年は使用不可」と理由のメモを表示する（数えることはできる）
- 端末：スマホ（幅 390px）を基本にする。ボタンは 44px 以上、数字の欄では数字のキーボードを出す

### 在庫一覧 /stocks（PC）

- 保管場所×品目の表。各セルに今年の数と前年との差（「12（+2）」）、行と列の合計。使用不可の部屋は灰色にして印をつけ、合計は「使用不可を除く」と「全部」の2つを出す。部屋の名前から在庫入力へ
- まだ数えていない場所（W104 と同じ。使用不可の部屋を除く）を表の上に一覧で出す
- 部屋に貼る QR の印刷（/stocks/qr。`?rooms=<id>,<id>` で絞れる。既定は保管場所すべて）：A4 に 2列×4段のカード（場所名、建物・階、QR、URL の文字、「スマホのカメラで読み、Safari か Chrome で開いてください」）。QR の URL は basePath を付けた公開の URL の `/stock/?room=<id>`（年度を入れない。開くにはログインが要る。LINE などのアプリの中のブラウザでは Google でログインできない）

### 申請 /request（スマホ）

- 表示：団体名、使用場所（なければ「校内に分散」）、締切日時（残りの日数）、その団体の区分で申請できる品目だけの入力欄（初期値は今の申請の数、なければ0）、備考欄（数には影響しないと明記）、提出の状況（「提出済み（日時）」「未提出」）。区分で申請できない品目に 0 でない申請が残っているとき（企業以外の長机(3人掛)など）は、入力欄の下に読み取り専用の行で出す（「長机(3人掛) 2台（長机(2人掛)として扱います。変えるときは総務へ）」。提出では送らない品目なので、団体代表は直せない）
- 操作：「提出」で確認（0 でない品目の一覧。すべて0なら「何も借りない申請として提出しますか」）をしてから、全品目と備考を RPC `submit_requests` で1回で保存し、submitted_at を記録する（日時は DB が入れる）。提出は毎回、送る前に自団体の申請と提出の記録を読み直す。読み直した値が入力と同じなら送らずに「提出されていました」で終え、編集を始めた後にほかの人（提出の記録は書いた人が自分でない、申請の行は数が編集を始めたときの値とも入力とも違う）が変えていれば、上書きしてよいか確かめる。自分の書いたもの（前に送って応答が届かなかった提出。提出の記録の書いた人が自分で、申請の行の更新時刻がその記録と同じ）はほかの人の変更としない。比べる元（編集を始めたとき〔編集せずに「提出」を押したときはその時〕の申請と提出の記録）で入力欄と提出の欄を出し（画面の値と比べる元を同じ時点にそろえる。送る値も同じ）、画面の裏の読み直し（通信が戻ったとき・下書きを戻した後など）では変えない。裏で届いた行に比べる元より新しいほかの人の変更があれば、入力は置き換えずに「編集を始めた後に、ほかの人がこの団体の申請を変えました。変わったもの：品目（前 → 今）、提出日時、備考」と知らせ、「ほかの人の値を読み込む」を押したときだけ、変わった品目と備考をその値にする（ほかの入れた数と書き換えた備考は残す）。知らせと読み込みで「変わった」とするのは値が変わったものだけ：品目は数が変わったもの（行が書き直されても数が同じ品目〔ほかの人の初めての提出で 0 の行が入った品目など〕は挙げず、入れた数を残す）、提出の記録は提出日時と備考を分けて変わったものだけを出す（備考を変えない出し直しでは、書き換えた備考を残す。どちらも同じ出し直しは「提出の記録」）。画面の読み込みも提出の記録の書いた人（updated_by）を読み、自分の提出（応答が届かなかったものを含む）で書かれた行と記録は知らせない。編集する前は、届いた行をそのまま出す。比べる元は下書きにも入れる（下書きを戻した後の提出も、それと比べる）。送る前の読み直しで比べる元を読み直した記録にするときは、読み直した値と同じ入力だけを外し、ほかの入力（編集を始めたときの値に戻した数・備考を含む）は残す。応答が届かず提出できたか分からないときは、入力を残して「提出できたか分かりません。もう一度「提出」を押すと、確かめてから送ります」と出す（もう一度押すと、上の読み直しで決まる。読み直しが通信できなければ送らない）。締切前なら何度でも修正できる。申請できない区分の品目は DB でも拒否する（E006。企業以外の長机(3人掛)は除く）。数は 10000 まで、備考は 2000 字まで
- 状態：準備中と受付開始の前は入力欄を無効にし、「受付の前です」「受付は {日時} からです」と表示。締切後と振り分け中以降は読み取り専用で「変更は総務へ」と表示。提出が状態のエラーで拒否されたら、年度を読み直して表示を合わせる。年度の状態が受付中のまま（端末の時計がずれていて、DB は受付期間の外と判断した）なら、読み取り専用にして「締切を過ぎました（または受付の前です）。端末の時計がずれている可能性があります」と出す（端末の時計に頼らない）。保存していない入力は下書きとして残し、離れるときは確かめる。開いている年度が最新でないときは、提出の前に確かめる。複数団体の代表なら団体を切り替える（`?group=<id>`）

### 申請一覧 /requests（PC）

- 表示：団体×品目の表（行は団体の並び順、列は品目の並び順、団体名の列を固定）と品目ごとの合計、区分フィルタ（`?category=`）、「未提出だけ」「備考ありだけ」（`?filter=`）、未提出団体の一覧、提出日時、備考がある団体に印（押すと備考を出す）。その団体の区分で申請できない品目のセルは「—」（0 でない申請が残っていれば、その数を灰色で出して印をつける。企業以外の長机(3人掛)は「長机(2人掛)として扱う」）。締切までの残り（締切後は「変更には理由が要ります」）。部員は読み取りだけ
- 操作：セルを直接編集（管理者）。編集したセルは「未保存の変更」になり、「保存（N件）」でまとめて送る。締切前（準備中と、受付中の締切前）は直接書き込み（行ごとの updated_at で楽観ロック）、締切後（受付中の締切後と振り分け中）は理由の入力を必須にして RPC で団体ごとに保存する。保存は毎回、送る前に表を読み直す：DB がすでに入れた数のセルは送らずに「保存されていました」とし、編集した後にほかの人が変えたセル（数が編集したときの値とも入れた数とも違う）があれば、送らずに一覧を出して「上書きして保存する」か「読み直す」（読み直した値に戻して印をつける）かを確かめる（セルは書いた人を記録しないので、前に送って応答が届かなかった自分の保存の後に入れ直したセルも、数で決めて確かめる）。表を読み直したとき（「読み直す」・通信が戻ったとき・下書きを戻したとき・代理入力や取り込みの後）は入れた数を捨てない（DB が入れた数と同じになったセルだけ未保存から外す。ほかの人の変更かは保存のときの読み直しで決める）。読み直した表で、未保存のセルの数が編集したときの値とも入れた数とも違えば、入力は置き換えずに一覧で知らせ、「変わったセルを読み直した値に戻す」を押したときだけ戻して印をつける。一度入れたセルは、編集したときの数に戻しても未保存として残す（表が古いままだと DB の今の数と違うことがあるため。表の数と同じセルも未保存として色をつけ、「保存（N件）」の件数と離れるときの確かめに含める。押すと保存の前の読み直しで決まる）。「上書きして保存する」の読み直しでまた変わっていれば、送らずにダイアログを開いたまま最新の値で確かめ直す。応答が届かず保存できたか分からないときは、入力を残して「保存できたか分かりません。もう一度「保存」を押すと、確かめてから送ります」と出す（読み直しが通信できなければ送らない）。締切前の書き方が DB に拒否され、年度の状態が受付中のままなら（端末の時計のずれ）、締切後の書き方に切り替える（編集したセルは残す）。編集したセルは下書きとして残し、離れるときは確かめる。確定中と終了後は読み取り専用
- 企業・休憩所の代理入力（管理者）：団体の行から申請と同じ入力欄を開く。休憩所は前年度の申請の数（previous_year_requests。団体名で対応）を初期値にできる。比べる元は最初に触ったとき（数・備考を変えた・前年の数を入れた・送った）の表の行で、触る前は裏で届いた表の行をそのまま出す。触った後に裏で届いた行に比べる元より新しいほかの人の変更があれば、入力は置き換えずに知らせ、「ほかの人の値を読み込む」を押したときだけ変わった品目と備考をその値にする（申請と同じ。値が変わったものだけを挙げ、自分の提出は知らせない。表の提出の記録も書いた人を読む）。締切前は `submit_requests`、締切後は `update_requests_after_deadline` に提出を付ける（理由が必須）。保存は締切の前後とも毎回、送る直前にその団体の申請（updated_at）と提出の記録（submitted_at・備考・updated_at・書いた人）を読み直す（`submit_requests` は楽観ロックを取らないため）。読み直した値が入力と同じなら送らずに「保存されていました」で閉じる。比べる元からほかの人が変えていれば（提出の記録は書いた人が自分でない、申請の行は数が比べる元の値とも入力とも違う。自分の提出で書かれた行は除く）送らずに読み直して（読み直した値と同じ入力だけを外し、比べる元の値に戻した数を含むほかの入力は残す）、上書きしてよいか確かめる（確かめた後に送るときも読み直し、また変わっていれば確かめ直す）。応答が届かず保存できたか分からないときは入力を残して知らせ、もう一度押すと上の読み直しで決まる。分からないまま閉じるときは「保存できたか分かりません。閉じると入力は消えます（表を読み直します）」と確かめ、閉じたら表を読み直す。締切後の備考は、書き換えたときだけ送る（ほかの人が変えた備考を上書きしない）
- 提出済みにする（管理者）：締切前は提出の記録を直接（提出日時は DB が入れる。何かの値を送ると DB の時刻に置き換わる）、締切後は `update_requests_after_deadline` の submission で。どちらも送る前に提出の記録を読み直し、すでに提出済みの団体には書かない（書くと最初の提出日時が今に変わるため。応答が届かなかった後に押し直したときも、これで決まる）。未提出に戻す操作は出さない（D-07・D-19）

- タブで切り替える（`?tab=years|rooms|items|groups|distance|users|export`）。終了した年度では、ロールを外す・団体代表を外す・招待の取り消し・新しい年度の作成以外は読み取り専用（年度末に終了してから翌年の年度を作るため）。削除は、実際に消えたことを確かめてから「削除しました」と出す（権限や年度の状態が変わって消えなかったときは、読み直して知らせる）。建物・表示名・備考などの任意の欄は、空欄なら「なし」として保存する
- 年度：作成（最新の年度からの複製。最新の年度の管理者だけができ〔その年度が終了していてもよい〕、作った人が新しい年度の管理者になる。年度名は空にできず、1日目は複製元の1日目より後）、申請の受付期間（受付開始の前に締切を入れる）。年度名・1日目・受付期間の変更（1日目は 2000-01-01〜2200-12-31 で、前の年度より後・次の年度より前。受付中は締切を空にできない）。作るときは、複製されるもの（団体・ルール・使用不可の設定）とされないもの（在庫・申請・振り分け・了承・ほかの人のロール・招待）を画面に書く。作った後は、付け替えられずに無効になったルールの数とルール画面へのリンクを出し、新しい年度に切り替える
- 場所・品目・団体：表で追加・編集。団体は CSV 取り込み可。場所・品目は全年度に効くことを書く（開いている年度の管理者が直せる）。品目のコードは作った後に変えない（ルールがコードで参照するため）。場所の今年の使用（使用不可と理由のメモ）は年度ごと。使われている場所（在庫・振り分け・団体の使用場所・どれかの年度の今年の使用）は消せない。振り分け中の年度で場所を使用不可にするとき、その場所からの固定・手動の行があれば、振り分け画面の部屋の見出しから行う（先に行を直すため）。団体を消すと申請・振り分け・団体代表・招待も消えることを確かめる。団体・場所を参照している有効なルールがあれば、削除の確認にそのコードを出し、先にルール画面で無効にするか参照を直すまで削除できない（ルールの団体・場所の参照には外部キーがなく、消すと参照の切れたルールが残って検証ができなくなるため。無効のルールの参照は件数だけ添える）。団体名は Excel の集計に使える名前だけ（D-27。年度の中の重複を含めて保存の前に確かめる）。団体の CSV は見出し `団体名,表示名,区分,飲食,使用場所,別名,並び順` で、プレビュー（追加・変更・変わらない・エラーの件数と行）の後に1回で保存する（削除はしない）
- 距離：建物間の距離の上書き（0〜20）、場所ごとの追加コスト（0〜20）。変えると次の自動振り分けから効く
- ユーザー：招待（メール・ロール・団体）、ロールの変更と外す（年度の最後の管理者は外せない。終了した年度でも外せる）、招待の取り消し（未使用のものだけ。終了した年度でも）、団体代表を外す。招待でその場でロールが付かなかったとき（アカウントがまだない、または今のメールを本人のものと確かめられない。D-17a）は「この人が学校の Google アカウントでログインしたときに付きます」と出す。メールアドレスは管理者のこの画面だけに出す
- データの書き出し：年度データ（JSON。無効なルール・メモ・別名・備考を含む。メールアドレスは含めない）と振り分け表（Excel）。年度末のバックアップに使う

### ルール /rules（PC）

- 一覧：コード・種別・内容の文（例「設営の机(木)は 1-1・1-2・… からだけ出す」）・有効・メモ。`?code=<コード>` でその行を開いて目立たせる（振り分け画面の原因・入力の誤りから来る）。有効なルールのうち参照が切れたもの（消した団体・場所を指すもの）と、「残す」の部屋が今年使用不可のもの（room_years.usable = false。振り分けの前処理が E002 で止める）に印をつける
- 種別ごとのフォーム（団体・場所・品目は選択式。団体・場所は id、品目はコードで保存）、有効／無効、メモ。保存の前と有効にする前に、params の形と、参照・ほかの有効なルールとの重なりを確かめ（packages/shared の ruleRowSchema・checkRuleRefs）、エラーを欄の下に出す。「残す」の部屋が今年使用不可なら、場所の欄の下に知らせる（保存は止めない。場所の使用はマスタ設定で年度ごとに変えるため）。編集で何も変えていなければ、保存を押しても確かめるだけで送らない（update で振り分けの版を上げない）
- R8 の初期ルール（S01〜S08）のひな形から追加できる（まだないコードだけ。団体・場所が要るものは選んでもらう）
- 削除はしない。使わなくなったルールは無効にしてメモに理由を書く（無効のルールも次の年度に引き継がれる）
- 振り分け中は「ルールを変えると、振り分け画面で再実行が要ります」と出す。確定中は「確定を解除してから変えてください」とし、メモだけ直せる（確定中にルールを変えると、公開中の振り分けの検証が黙って変わるため。DB は書き込みを許すが画面で止める）。終了した年度はメモだけ直せる

### 履歴 /history（PC、管理者のみ）

- audit_logs を表・団体・期間・した人で絞り込んで、新しい順に表示する（50件ずつ「さらに読み込む」。絞り込みは URL に入れる）。期間は Asia/Tokyo の日付
- 列：日時・操作（追加・変更・削除）・表・対象（団体・部屋・品目の名前。消えた団体は記録の中の名前）・変更（変わった列の前と後）・理由・した人（アプリの外の変更は「SQL・seed」）
- 場所・品目・距離（年度をまたぐ表）の履歴は、開いている年度の管理者に見せる

### CSV取り込み（申請一覧・マスタ設定から）

- 取り込めるのは模擬店・部門・企業の3種類の Googleフォームの回答。種類ごとに列の対応表を持つ
- 模擬店フォームの団体名は「飲食模擬店を運営しますか？」の答えで2つの列に分かれるので、空でない方を使う。groups.name と aliases で対応付け、合わなかった行は一覧で示して手で対応させる
- 企業フォームは団体名が入っていない（R8 ではすべて「オプション 1」）ので、取り込み時に手で団体を選ぶ
- 同じ団体の回答が複数あるときは、タイムスタンプが一番新しいものを使い、古いものは画面に出して確認させる。一番新しい回答が取り込まない行（列のずれ・数が読めない）になっているとき（取り込まない行のうち、タイムスタンプと団体名が読めて団体名がその団体だけに当たり、読めた回答より新しいものがあるとき）は、その団体を自動では取り込まず、プレビューに「新しい回答が読めない」団体として行番号・日時・理由を出し、既定では上書きしない（管理者が選べば、読めた回答のうち一番新しいもので上書きする）。タイムスタンプか団体名が読めない行は、取り込まない行に出すだけ
- 列がずれている行（見出しのない列に値がある行）は取り込まず、一覧で示す
- 品目の列名はフォームでの表記（items.aliases）で品目に対応させる。企業以外の長机(3人掛)は長机(2人掛)に読み替える（S03）。読み替えた後は団体・品目ごとに合計して1行にする（長机(3人掛)と長机(2人掛)の両方を申請した回答で、同じ品目の行が2つにならないように）
- フォームのタイムスタンプを、その団体の提出日時（request_submissions.submitted_at）として保存する（Excel の団体別集計の「申請順」に使う）。取り込みは管理者だけの RPC で行い、DB はそのときだけ渡した日時を保つ（団体代表の提出は今までどおり DB の時刻）
- メールアドレスは、どの列にあっても（見出しのない列も含めて）パターンで見つけて捨て、保存もログ出力もしない
- 文字コードは UTF-8 を先に試し、読めなければ Shift_JIS で読む（Excel で保存し直した CSV のため）。どちらでも読めなければ、その旨だけを出す
- 流れ：種類とファイルを選ぶ → 読み取り → その種類の区分の団体に対応させる → プレビュー（回答・対応した・対応しない・取り込まない・古い回答の件数、対応しない行を手で団体に対応させる欄、団体ごとの CSV の数と今の数と提出日時の比較、長机の読み替えの印、新しい回答が読めない団体）→ 理由を確かめて保存。取り込まない行は、行番号と理由だけを出す（中身は出さない。新しい回答が読めない団体には、その行の日時も添える）
- 保存は団体ごとに `update_requests_after_deadline`（締切の前後によらない。提出日時を残すため）で、その団体の申請全体を送る（CSV にない品目は 0）。申請できない品目（E006）は送らず、団体ごとに印を出す（送るとその団体の全部が拒否されるため）。団体ごとに成否を出し、終わったら申請一覧を読み直す
- 団体ごとに送る直前に提出の記録（提出日時・備考・updated_at）を読み直し、プレビューを作った後に変わっていた団体は送らない（行の楽観ロックは requests の行にしかかからず、数を変えない出し直し・備考だけの変更・「提出済みにする」では行の updated_at が変わらないため。2.3）。結果には「取り込みの前に、ほかの人がこの団体の申請を変えました」と出し、読み直した表で取り込み直すと Q2 の既定で決め直す
- 上書きの既定は「CSV のタイムスタンプがアプリの提出日時より新しい団体だけ」にし、管理者が団体ごとに選び直せる（Q2）。同じ時刻の団体（同じ CSV を取り込み直したとき）は「同じ時刻（取り込み済み）」と出し、既定では上書きしない。新しい回答が読めない団体も、既定では上書きしない
- プレビューの数は取り込んだ後の数を出す（申請できない品目で送らないものは、今の数のまま「変えない」と出す）
- 備考が 2000 字を超える回答は、プレビューで示し、2000 字に切って保存する（超えたまま送るとその団体の全部が拒否されるため）。切った団体は結果にも出す
- 理由の既定は「Googleフォームの回答の取り込み（{種類}）」（編集できる）。ファイル名は入れない（理由は履歴に残り続け、ファイル名には人の名前が入りうるため）
- ファイルの中身は画面の中にだけ持ち、閉じたら消す（保存もログ出力もしない）
- マスタ設定の団体の CSV は別の形（「マスタ設定」）

## DB関数とブラウザ側の処理

サーバーを持たないので、Route Handler と Server Action は使わない。読み取りと、理由の要らない書き込み（在庫入力、締切前の申請一覧のセル編集、マスタの編集）は、画面から Supabase クライアントで直接行い、RLS で守る。理由が要る書き込みと、複数の表をまとめて変える書き込み（申請の提出を含む）は DB 関数（RPC）で行う。重い計算とファイルの作成は管理者のブラウザで行う。

**DB関数（RPC）**

**ブラウザ側の処理**

| 名前 | 置き場所 | 動作 |
| --- | --- | --- |
| allocate(input, solver) | packages/allocator | 振り分けの計算（Web Worker で実行。solver は Worker の中で1回だけ読み込んだ highs のインスタンス） |
| validate(data, rows) | packages/allocator | 検証コードの一覧を返す（data は年度のデータ、rows はその年度の全行） |
| exportAllocationXlsx({ yearLabel, data, rows }) | packages/exporter | R8 様式の Excel（data は年度のデータ、rows はその年度の全行。余り・計は exporter が計算する） |
| exportSwapsXlsx({ yearLabel, data, rows }) | packages/exporter | キャスター机交換依頼一覧（了承が要る代替の行と了承の状況） |
| exportYearJson(yearExport) | packages/exporter | 年度データの書き出し（バックアップ。メールアドレスは含めない） |
| parseFormCsv(kind, csv, items) | packages/importer | Googleフォーム回答の読み取り（品目の列は items の aliases で対応。メールアドレスを捨てる） |
| resolveResponses(parsed, groups, items, manual) | packages/importer | 読み取った回答を団体に対応させ、申請（読み替えの後、団体・品目ごとに1行）と提出（フォームのタイムスタンプ）を作る。合わない行・古い回答を返す |

- RPC は SECURITY DEFINER にして `search_path = ''` を設定し、関数の最初でロールを確かめる。次に年度の行をロックし（`for no key update`）、ロールをもう一度確かめてから状態を確かめ、入力を確かめてから理由を置いて書き込む。入力はブラウザで zod、DB では関数の中でもう一度確かめる
- エラーは `raise exception`（SQLSTATE P0001）で返し、message にコード、detail に該当する行の id などを JSON で入れる（メールアドレスは入れない）。PostgREST は HTTP 400 で `{ code: 'P0001', message, details }` を返す。コードは forbidden（ロールがない。対象が見つからないときも）、not_found、invalid_state（状態が違う、確定中に変えられない）、conflict（版・updated_at が違う、重複）、invalid_input（形や参照が違う、上限を超える）、reason_required、検証コード（E001・E002・E005・E006）。RPC の中で起きた形の誤り（jsonb の中の uuid・日付など）と CHECK 違反も invalid_input にして、生の SQLSTATE は返さない。ただし、RPC のトップレベルの型つきの引数（uuid・enum・date・integer）は PostgREST が関数の前に変換するので、形が違うと 22P02・22007 などがそのまま返る（関数の中では直せない）。画面は zod で先に確かめ、22 で始まる SQLSTATE は「入力の形が違う」として扱う。画面で日本語に直して表示する
- 楽観ロックの updated_at は、受け取った文字列をそのまま返す（Date に変換しない）
- 振り分けの行を渡す JSON は、03 の AllocationRow と同じ camelCase（sourceRoomId、groupId、itemId、requestedItemId、count、isKeep）にする
- 書き込みがデッドロック（SQLSTATE 40P01。PostgREST は HTTP 500 で返す）で失敗したときは、何も保存されていない（1リクエスト＝1トランザクション）ので、入力を残したまま「ほかの人の保存と重なりました。もう一度保存してください」と出す。HTTP 500 を一律に扱わず、エラーの code で分ける
- highs-js の wasm は振り分け画面を開いたときだけ読み込む（その画面のコンポーネントで `new Worker(new URL('…worker.ts', import.meta.url))` を作り、Worker の中で highs を読み込む）。wasm は highs の `highs/runtime`（highs の package.json の exports。`require.resolve('highs/runtime')` が build/highs.wasm を指す。`highs/package.json` は exports にないので引けない）を `apps/web/public/highs.wasm` にコピーして静的ファイルとして公開し（git には入れず .gitignore に書く）、locateFile で basePath を付けた URL（`${origin}${basePath}/highs.wasm?v=<highs の版>`）を渡す。コピーは apps/web の predev と prebuild の両方で行う（`pnpm dev` でも 404 にならないように）。basePath を付け忘れると GitHub Pages で 404 になり、`CompileError: expected magic word` で落ちる。読み込みに失敗したら、次の実行で読み直す（失敗を覚えたままにしない。読み直しの URL に回数を付け、404 のキャッシュを避ける）。Worker は1つだけ作り、画面を離れて戻っても使い回す（ログアウトで止める）。`next build --webpack` は highs.mjs の `node:module` で失敗するので使わない
- validate と Excel の作成は主スレッドで行う（R8 規模で validate は数十 ms、Excel の作成は 0.1 秒ほど）。ExcelJS を含む exporter は、出力するときに読み込む（動的 import。最初の読み込みを重くしない）
- 画面は、エラーを code（P0001 の message と details、22 で始まる SQLSTATE、42501、23505・23503・23514、40P01、PGRST301・PGRST302・PGRST303 と HTTP 401、通信の失敗）で分けて日本語にし、読み直すか・入力を残すかを決める。分け方と文言は apps/web/lib/errors.ts の1か所に置く（D-33）。details にある団体・部屋・品目・行の id は、画面が持っている名前に直して出す。JWT のエラー（PGRST301〜303・401）は、セッションの更新を1回試し、だめならその端末のセッションを消してからログインの画面へ送る（消さずに送ると、ログインの画面が「ログイン済み」としてすぐ戻すため）
- 直接の更新と削除は、変わった行を返させて確かめる。RLS で拒否された update・delete はエラーにならず 0 行で成功するので、0 行なら読み直して「ほかの人が変えた・消した」か「権限か年度の状態が変わった」かを分ける
- 通信が切れて応答が届かなかった書き込みは、自動で送り直さない。書き込みの種類で次の3つに分ける。どれも、確かめるためだけの状態（押せない保存のボタンなど）は (B2) のほかには持たない
  - (A) 数を絶対値で書く書き込み（在庫・申請）：保存のたびに、送る前に今の行を読み直して決める（入力と同じ値になっていれば送らずに「保存されていました」）
  - (B1) 楽観ロックの更新（updated_at）と、一意のキーのある insert（マスタ・ルール・今年の使用）：応答が届かなかったその場で行を1回読み直し、入力と同じなら「保存されていました」とする。決められなければ入力を残し、もう一度の保存はふつうに送ってよい。前の送信が通っていれば DB が updated_at の違い（conflict）か重複（23505）で止めるので上書きにならず、止まった後に行を読み直して入力と比べる（同じなら保存されていた、違えばほかの人の変更として扱う）
  - (B2) save_allocation_rows（行の追加に冪等の鍵がなく、確かめずに送り直すと二重にできる）と、ほかの RPC（save_auto_allocations・確定・了承の回答）：版などで保存されたかを読み直して確かめてから送り直す
